# 2026-10-21 工作日志

## 任务概述
分析并重构智调鸿枢项目架构,解决核心解耦性和统一性问题。

## 关键问题识别

### 1. 接通程度不一致
- 云端购物固定使用 `REMOTE_CLOUD` (S01)
- Worker路径只接入图片裁剪 (S02-S04)
- 第二手机是独立演示机制,不经过完整算法 (S05)
- 三条路径协议/选择逻辑/资源准入不统一

### 2. 写死业务逻辑违背解耦性
- `ShoppingTaskService` 硬编码购物任务
- `DeviceDispatchService.crop()` 专门处理裁剪
- 无法接入其他AI任务(分类/翻译等)

### 3. 设备画像机制缺失
- 设备能力散落各处,无统一注册中心
- Phone/Worker/Cloud使用不同协议
- 无动态插拔支持

### 4. 宏观/微观调度不清晰
- 宏观调度应选择"哪个设备执行"
- 微观调度应配置"设备内如何执行"
- 当前边界模糊

## 重构方案核心

### 三层架构
```
云端宏观调度 (选设备)
  ↓
设备微观调度 (配置资源)
  ↓
硬件层执行 (CPU/GPU/NPU)
```

### 核心组件

1. **UnifiedDeviceRegistry**
   - 统一设备注册中心
   - 支持动态注册/注销
   - TTL自动过期
   - 按capability查询

2. **UnifiedTaskScheduler**
   - 通用AI任务调度器
   - 接收 `AITaskProfile`
   - 查询设备并调用算法
   - 返回 `DeviceAssignment`

3. **AI任务画像**
   ```typescript
   {
     capability: "image.crop.v1",
     modelRequirements: {...},
     resourceRequirements: {...}
   }
   ```

4. **设备画像**
   ```typescript
   {
     deviceId, deviceType,
     capabilities: [],  // 动态发现
     resourceSnapshot: {...},
     hardwareProfile: {...},
     executionHistory: [...]
   }
   ```

## 关键技术决策

### 为什么不汇总所有设备硬件?
- 每个设备是独立执行单元
- 宏观调度比较"整体能力",不是"单个核心"
- 不做虚拟CPU池

### 设备画像TTL策略
- Phone: 30-60秒 (状态变化快)
- Worker: 5分钟 (相对稳定)
- Cloud: 10分钟 (容量变化慢)

### Capability版本管理
- 带版本号: `image.crop.v1`, `image.crop.v2`
- 设备可同时支持多版本
- 任务匹配时严格检查版本兼容性
