# HarmonyOS 受约束策略闭环实施方案

更新日期：2026-09-21。状态：本地 V1 已实现并进入验证；P0-P3 的代码链路及 P4 的受控试验保护机制已接入，尚未完成真机基线、质量评价或自动策略放量。第 1-12 节保留设计目标，第 13 节记录 V1 初版；结合新拉取实现的保留/调整见第 14 节及 [当前整合验收](testing/07-resource-experiment-integration.md)。

关联文档：[AI 任务语义调度件工作要求](07-AI任务语义调度件工作要求.md)、[AI 任务语义调度 SDK：接入与实现](08-AI任务语义调度SDK-接入与实现.md)。

## 1. 目标与问题边界

本方案为鸿蒙手机应用内的 AI 任务调度 HAR 增加一个可审计、可回滚的策略优化闭环。它要解决的是：在 App 已声明的业务能力范围内，结合任务语义、用户反馈和当前手机状态，为 AI 任务选择更合适的执行计划。

本方案不修改 HarmonyOS 内核调度器，不控制其他应用的线程、CPU 频率、GPU/NPU 频率或全局进程优先级。最终的物理资源分配仍属于操作系统；HAR 只控制接入它的应用内 AI 工作何时提交、采用哪个已验证配置、是否暂停、取消或丢弃结果。

调度件不能承诺在所有手机和所有状态下都更快。它必须保证的是：

- 不越过 App 声明的质量、隐私和业务边界；
- 不越过已验证的设备保护边界；
- 新策略出现劣化时可停止使用并回退；
- 每个实际执行计划、策略版本和回退原因均可审计。

## 2. 设计结论

### 2.1 不调任意单参数，调已验证的执行配置包

候选集规模、推理线程数、检索维度、模型档位和后台批次大小相互影响。调度件不得根据一个“偏慢”反馈，将任意数值从 2700 改成 1374，或独立地把线程数改为 3。

应用应在初始化阶段注册少量经过验证的 `ExecutionProfile`。一次调度决策选择一个完整配置包；参数联动由 App 在配置包中提前定义和验证。

购物搜索的示例配置包可以是：

| Profile ID | 质量档 | 检索候选集 | TaskPool 分区/线程配置 | 适用意图 |
|---|---:|---:|---:|---|
| `SEARCH_FAST` | `LIGHTWEIGHT` | 500 | 1 | 用户等待、设备受热或低电量时的快速返回 |
| `SEARCH_BALANCED` | `BALANCED` | 1200 | 2 | 常规本地搜索 |
| `SEARCH_HIGH` | `HIGH_ACCURACY` | 2700 | 2 或已验证的 4 | 用户明确要求质量且设备余量充足 |

表中数值只是后续真机基准的候选值，不是当前项目已经证明的最优值。每个档位必须由实际执行器支持；若当前文本 Embedding 仍总是执行完整 256 维前向推理，低候选集或低检索维度只能宣称降低后续检索计算，不能宣称按比例减少模型推理耗时。

### 2.2 App 定义能力边界，HAR 选择合法计划

App 声明“能做什么、哪些组合有效、最低业务质量是什么”；HAR 根据手机实时状态和学习到的预测，选择“本次应做什么”。HAR 不解析原始图片、文本或业务对象来猜测这些事实。

需要区分三类约束：

| 约束类别 | 责任方 | 示例 | 是否允许学习模块修改 |
|---|---|---|---|
| 业务硬约束 | App | `LOCAL_ONLY`、最低质量、高质量强制模式、不可降级任务 | 不允许 |
| 设备保护约束 | HAR 与状态适配器 | 临界热状态、内存压力、低电量、前后台状态 | 不允许突破，只能更保守 |
| 可学习偏好 | 策略模块 | 目标响应时间、档位偏好、预计时延、结果被消费概率 | 可在范围内校准 |

### 2.3 手机本地执行，云端只做非实时优化

用户点击拍照识别、文本搜索等前台操作时，`SchedulerService` 必须在手机本地根据已缓存的策略版本、当前 `HarmonyDeviceStateAdapter` 快照和 App 契约快速生成执行计划。实时路径不能等待云端大模型，也不能把原始图片、文本、向量或模型输出上传后再决定本次调度。

在测试阶段，可选云端服务用于汇总经用户授权且已脱敏的遥测、离线比较配置包、生成下一版策略建议。它不是实时控制面，也不应由大语言模型直接输出线程数、候选集或调度命令。云端大模型最多用于分析自由文本反馈、归纳异常现象或辅助生成测试报告；最终下发的必须是结构化、受约束、版本化的策略。

## 3. HarmonyOS / ArkTS 实现映射

本节将方案转化为当前工程可实施的鸿蒙侧模块，不新增未经验证的内核控制能力。

| 设计角色 | HarmonyOS 工程位置或机制 | 责任 |
|---|---|---|
| 应用接入面 | `scheduler` HAR 的 `SchedulerClient` | 注册模板/执行配置包、提交任务、发送业务信号 |
| 任务数据契约 | `SchedulerTypes.ets` | `TaskTemplate`、`TaskContext`、`TaskSignal`、`TaskTelemetry` 与新增的策略类型 |
| 策略决策 | `SemanticPolicy.ets`、`SchedulerPolicy.ets` | 筛选合法配置包、预测成本、生成执行计划与原因码 |
| 调度运行时 | `SchedulerService.ets`、`TaskQueue.ets` | 入队、出队前重评估、执行、取消、策略版本审计 |
| 鸿蒙设备状态 | `HarmonyDeviceStateAdapter.ets`、`DeviceStateController.ets` | 读取项目实际验证可用的电量、热状态、内存和 Ability 前后台信息；未知值按保守策略处理 |
| 应用真实负载 | `ShoppingTaskService.ets`、MindSpore Lite 和 `TaskPool` 执行器 | 将计划转换为本地模型推理、向量检索或分批后台工作 |
| 用户反馈 UI | App 页面，例如 `Index.ets` / 独立 ArkUI 组件 | 决定是否展示轻量选择题；HAR 只建议，不直接绘制或打断 UI |
| 本地策略存储 | App 私有持久化存储或受控配置仓 | 保存已验证策略版本、有限遥测摘要和回滚标记；不保存原始业务输入 |
| 测试 | Hypium 单元测试、调度验收测试、真机实验 | 验证状态机、配置合法性、回滚、性能与质量取舍 |

## 4. 新增数据契约

### 4.1 `TaskCapabilityManifest` 与 `ExecutionProfile`

在不破坏现有 `TaskTemplate` 接口的前提下，新增能力声明。建议先以可选字段实现并保留旧模板兼容路径。

```ts
interface ExecutionProfile {
  id: string;
  modelTier: ModelTier;
  candidateCount?: number;
  workerCount?: number;
  batchSize?: number;
  allowWarmup: boolean;
  supportsForeground: boolean;
  supportsBackground: boolean;
  estimatedQualityLevel: ModelTier;
}

interface TaskCapabilityManifest {
  profiles: ExecutionProfile[];
  defaultProfileId: string;
  fallbackProfileId: string;
  profileTransitions: ProfileTransition[];
}
```

`profileTransitions` 用于表达相邻可切换关系，例如 `SEARCH_BALANCED -> SEARCH_FAST`。策略不得一次跨过未验证的档位，也不得选取执行器不支持的配置。对运行中的任务，只有执行器明确提供检查点或安全重配置能力时，才允许在分块边界应用新计划；不可中断的 MindSpore Lite 调用仍等本次调用返回后再切换。

### 4.2 体验目标与结果失效边界分离

现有 `deadlineMs` 和 `freshnessMs` 不应承担全部用户体验语义。建议在 `TaskContext` 增加以下可选字段：

| 字段 | 语义 | 使用规则 |
|---|---|---|
| `targetLatencyMs` | 希望用户感受到的响应目标 | 用于排序、预热和档位选择；不能因为用户曾等待更久就自动放宽 |
| `softDeadlineMs` | 超过后视为体验风险升高的时间 | 触发更保守的后续决策或反馈邀请，不直接终止合法任务 |
| `deadlineMs` | 最晚可接受完成时间 | 保持现有兼容语义，作为强约束参与准入与超时处理 |
| `freshnessMs` | 结果失去业务价值的时间 | 到期后丢弃迟到结果，避免覆盖新的 UI 状态 |

未声明新字段的旧 App 继续沿用当前 `deadlineMs` / `freshnessMs` 行为，HAR 不得虚构用户体验阈值。

### 4.3 `FeedbackRequest` 与 `TaskSignal`

HAR 不拥有应用页面，也不应自行弹出 ArkUI 对话框。策略仅返回一个可忽略的 `FeedbackRequest`，由 App 决定是否和如何展示。

```ts
enum FeedbackKind {
  RESPONSE_TIME = 'RESPONSE_TIME',
  RESULT_UTILITY = 'RESULT_UTILITY',
  DEVICE_COMFORT = 'DEVICE_COMFORT'
}

interface FeedbackRequest {
  taskRunId: string;
  kind: FeedbackKind;
  suggestedAfter: 'RESULT_DISPLAYED' | 'PAGE_EXIT' | 'NEXT_IDLE';
  options: string[];
  expiresAtMs: number;
}
```

App 将用户答案转换为新的 `TaskSignalType.USER_FEEDBACK`，并只上传结构化选项值。拍照识别可使用“很快 / 可接受 / 偏慢 / 未得到结果”和“结果有用 / 不够准确 / 无关”两类问题。不要在相机取景或模型推理的关键路径中阻塞页面；每次最多询问一个问题，并按任务类型、用户、日期和异常次数限频。

`PAGE_LEFT`、`INPUT_REPLACED`、`CANCEL`、`RESULT_DISPLAYED`、`RESULT_CONSUMED` 和 `RESULT_IGNORED` 仍是重要自动信号，但它们只能表示可能的体验风险，不能等价于用户主观评价。

### 4.4 遥测最小化与关联

每条样本以 `taskRunId` 关联，不采集原始图片、文本、Embedding、商品列表、模型输出或用户身份文本。建议保留：

- 能力名、配置包 ID、策略版本、是否为影子/试验/正式执行；
- 提交、开始、结束、排队、执行和端到端时延；
- 输入规模桶、候选集档位、线程/分区配置与实际执行器回报；
- 已验证可获取的电量、热状态、内存、前后台和队列快照；
- 成功、失败、取消、超时、结果消费和用户结构化反馈；
- 预测值、实际值、置信度、原因码、回退事件。

## 5. 受约束决策流程

每次节点出队前，`SchedulerService` 应重新调用策略。决策顺序固定如下：

```text
读取手机状态快照
  -> 校验 App 硬约束与设备保护约束
  -> 枚举该任务声明的 ExecutionProfile
  -> 剔除不支持、不可达或违反约束的配置包
  -> 预测每个合法配置包的 P50/P95 时延、内存/热风险与质量代价
  -> 计算业务效用并选取一个配置包、排队/暂停/取消/拒绝动作
  -> 执行时监控保护条件，必要时在安全边界回退
  -> 记录计划、实际结果和反馈，校准预测器
```

效用函数不必在 V1 追求神经网络形式，但必须分开记录其组成：用户等待和可见性、目标响应时间压力、结果失效风险、质量损失、预计能耗、热风险、内存风险与业务重要度。用户反馈用于校正“满意度/质量代价”，设备遥测用于校正“资源成本”；二者不能互相替代。

当“速度偏慢”和“结果不准确”同时出现时，策略不得擅自无限压缩计算量。它只能：选择 App 已声明的折中档位、执行已验证的预热或并发整理动作，或者将“快速结果 / 高质量结果”的选择交还 App。

## 6. 调整方向、范围与联动控制

### 6.1 调整范围

范围由 `TaskCapabilityManifest` 限定：策略只能选择配置包及其已声明转移。建议的初期规则是一次最多跨一个相邻配置包，并在一个观察窗口内保持稳定；不能在连续任务间因单个反馈反复升降档。

连续数值确有必要时，例如后台分块大小，也必须声明最小值、最大值、步长、默认值和兼容关系，并经过执行器验证。前台 AI 推理优先使用离散配置包，便于解释、测试和回滚。

### 6.2 调整方向

方向由“哪一类约束或体验目标失败”决定，而不是由单一耗时指标决定：

| 观察到的组合 | 优先动作 | 禁止的错误动作 |
|---|---|---|
| 前台等待且预计超出目标，设备余量正常 | 尝试相邻快速配置包、减少后台竞争、预热后续节点 | 忽略质量下限或直接提升到未验证并发 |
| 高热、低电量或内存压力 | 暂停/分块后台工作、选择低开销配置包、必要时拒绝低价值任务 | 为追求速度继续加线程或强行保留高质量模式 |
| 结果不准确反馈增加，时延可接受 | 选择更高质量配置包或保持默认档 | 只因“速度不错”继续降低候选集 |
| 页面已离开、输入已替代、结果已过期 | 取消或丢弃迟到结果 | 继续执行并更新已失效页面 |
| 预测置信度低或状态未知 | 使用默认/回退配置包并记录原因 | 假设设备状态正常后激进试验 |

### 6.3 参数联动

一个 `ExecutionProfile` 是参数联动的基本单位。比如降低候选集可能需要同时选择特定检索维度、限制 TaskPool 分区数或关闭可选重排；这些关系必须写入配置包，而不是由 `SemanticPolicy` 写死购物业务规则。

策略评估每个配置包时必须把联动后的总成本作为整体预测。不能先按延迟选最低候选集，再单独按吞吐把线程数调高，从而生成 App 从未验证过的组合。

## 7. 用户反馈闭环

### 7.1 何时询问

反馈 UI 必须服从 App 页面节奏。是否参与取决于这一步能否调整调度参数，而不是是否成功。推荐触发条件包括：首次有效结果展示后、长尾时延后任务仍成功完成、结果被用户使用后、任务以超时/取消/失败等非成功终态结束（含用户等太久离开）后的下一次前台空闲时机，以及预测不确定度较高的少量抽样任务。

不应在以下情形提问：正在相机取景、正在等待模型结果、用户已经连续被询问、涉及敏感内容且未取得同意。任务离开页面时当下没有可交互 UI，此时不应强弹，而应把询问延后到用户回到前台的空闲时机，不能直接丢弃该信号。

### 7.2 如何解释答案

用户的“偏慢”不是把 `targetLatencyMs` 直接改为本次实际等待时长。HAR 应在相同任务类型、输入规模桶、设备状态桶和配置包下逐步估计“用户认为可接受”的概率曲线；速度目标取满意概率开始显著下降前的保守点。单次答案只增加一条带权样本。

用户“未得到结果”需要结合成功/失败、页面离开、重试和结果展示记录判断。自动行为信号与选择题信号均只影响可学习偏好，不得覆盖 App 的硬质量约束。

## 8. 四阶段上线方式

### 阶段 A：被动观测

目标是建立当前基线。保留现有执行计划，不因反馈或预测改变真实执行，只记录任务、设备状态、实际耗时、结果消费和低频用户反馈。输出每类任务的 P50/P95、取消率、结果使用率、热状态分布和样本覆盖情况。

### 阶段 B：影子模式

影子策略生成“本次本应选择的配置包和动作”，但 `SchedulerService` 仍执行基线配置。审计记录必须同时写入 `baselineProfileId`、`shadowProfileId`、原因码和预测差异。

影子模式只能验证：数据是否足够、候选配置是否合法、决策覆盖率、预测校准程度以及是否频繁提出不可执行建议。它不能证明影子配置真的更快或更受欢迎，因为未执行配置的反事实结果不可观测。

### 阶段 C：小范围受控试验

在影子结果稳定后，对可逆、低风险动作做真实试验，例如取消过期预热、降低后台任务优先级或在批次边界让出 `TaskPool` 工作。对质量有明显影响的模型/候选集降级，必须先有质量评价数据。

试验分流应以策略版本、任务类型、设备状态桶和稳定哈希确定，而不是对同一任务重复执行两遍。每个试验必须定义基线、处理组、最长试验期、非劣阈值和自动停止条件。

若某个用户只执行一次任务，无法在该用户上证明新旧策略的因果差异。该用户首次使用应走已验证的默认配置和硬保护规则；该次反馈只作为后续样本，不触发立即个性化。跨用户匿名先验、开发阶段真机基准或后续多次任务，才可缩短冷启动时间。

### 阶段 D：受控自动调度

仅当受控试验满足预先定义的性能、质量和稳定性条件时，才将配置包选择开放给自动策略。默认仍保留 `fallbackProfileId`、策略版本开关、异常熔断和一键停用能力。第一批自动动作应是后台和过期任务处理，不应先让前台识图在未知手机上激进降质。

## 9. 云端测试控制面（可选）

### 9.1 适用范围

测试阶段可部署一个低频、异步的优化服务。手机在任务结束后上传经过授权且脱敏的遥测摘要；服务按任务画像、设备状态桶和配置包聚合，输出下一版候选策略。手机仅在下次启动、空闲或策略刷新时拉取已签名/校验的结构化策略；本次前台任务绝不等待网络决策。

### 9.2 云端输出格式

云端输出应是可验证数据，而非自然语言：

```text
policyVersion
  -> capability
  -> applicableDeviceStateBucket
  -> allowedProfileIds
  -> preferredProfileId
  -> confidence / minimumSampleCount
  -> rolloutPercent
  -> nonInferiorityThresholds
  -> fallbackProfileId
  -> expiresAt
```

手机侧在采用前再次校验能力名、配置包存在性、质量下限、隐私策略、策略签名/完整性、有效期和本地设备保护条件。任何校验失败、网络不可用或策略过期都回退到 App 默认策略。

### 9.3 大模型的受限角色

云端大模型可以帮助开发者阅读自由文本意见、聚类异常日志或提出待审核的实验假设。它不能直接写入 `ExecutionProfile`、改变 `accuracyFloor`、突破 `LOCAL_ONLY`，也不能直接下发本地实时调度命令。结构化优化器、统计检验和人工审核才是策略发布的主体。

## 10. 本地保护、回滚与性能验收

### 10.1 本地熔断

每个策略版本和配置包组合必须有局部熔断器。出现以下任一条件时，停止使用新策略并回退：

- 执行器返回不支持的模型档位、线程/分区或后端；
- 临界热状态、内存压力或 App 定义的质量硬约束不满足；
- 连续错误、超时、取消确认异常或策略/实际配置不一致；
- 处理组相对基线在预设窗口内超过延迟、质量或失败率劣化阈值；
- 策略来源、版本、有效期或完整性校验失败。

熔断器由手机本地执行，不依赖网络。回退应在尚未启动节点时切换到 `fallbackProfileId`；已经运行的不可中断推理只允许等待当前调用返回、停止后续节点或丢弃过期结果，不能伪造“已强制停止”。

### 10.2 验收指标

对每个配置包和策略版本，至少记录：端到端 P50/P95、排队时延、执行时延、成功/失败/超时率、结果使用率、用户速度/质量反馈、实际模型档位、TaskPool 分区/线程配置、热状态和回退次数。

性能验收采用“非劣于基线”而非“必然更快”的原则。具体数值阈值应由首次真机基准后按任务类别写入版本化测试计划，不能在无数据时虚构百分比。任何速度收益都必须同时报告质量、取消率、错误率和设备状态，避免以降质换速度却只展示时延。

## 12. 测试顺序与完成条件

1. 先完成 ArkTS 类型契约、配置包校验和策略单元测试，再接 UI 反馈。
2. 使用当前文本 Embedding + 本地向量检索作为真实工作负载，先测默认、快速和高质量配置包是否确实可执行。
3. 在同一台鸿蒙手机上建立无后台负载、有后台 `TaskPool` 负载、不同热/电量状态下的基线数据。
4. 开启被动观测和影子模式，检查策略输入完整性、建议可执行性和预测误差；不宣称优化效果。
5. 只对低风险动作做小范围真实试验；达到预定义非劣标准后再扩大。
6. 最后再评估是否值得引入云端策略优化；没有跨设备样本或未完成授权时，保持本地规则与本地校准即可。

本方案完成的最低条件不是“部署了一个云端大模型”，而是：App 能声明受控配置空间；手机本地可生成可解释执行计划；用户反馈和任务遥测可安全关联；影子、试验和正式模式不混淆；任何新策略均有硬约束、审计和本地回退。

## 17. 体验提问简化与优先级（2026-09-22）

复核后撤销首次搜索的内部参数题。普通用户不需要判断目标毫秒数、模型档位或质量底线，搜索直接使用 App 默认约束。用户随后明确：温度、内存和卡顿属于客观遥测，完全不需要问用户。最终撤销这些题目，也不以采集缺失为提问理由；资源保护继续自动执行，帧卡顿采集的缺口保持明确。

TaskSignal 增加可选、白名单校验的 AppExperienceObservation。成功结果展示后，实测软截止超时优先询问“这次等待能否接受”，应用明确报告质量不确定时才询问“是否符合需求”；已知信息或无相关疑点时不出题。当前购物 App 上报结果准备耗时，尚无已校准质量置信度，不伪造质量疑点。点击消费只用于减少提问，不当作满意标签。

一次回答不修改当前任务，不越过 manifest、质量、硬截止、冷却和熔断。读取已有状态或判定无需提问不消耗配额，优先级不能越过日最多 2 次、同能力/任务类型每天 1 次、间隔 30 分钟和有效期 2 分钟。反馈内容与调度盘入口说明见 [实时调度仪表盘与提问诊断](13-实时调度仪表盘与提问诊断.md)。
