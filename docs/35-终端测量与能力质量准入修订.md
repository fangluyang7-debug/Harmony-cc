# 终端测量与能力质量准入修订

日期：2026-10-29。分支：`codex/scheduling-data-pipeline`。本页更新文档 33、34 中的手机计时、质量批准和失败恢复规则。

## 逐条评析

| 反馈 | 核实与处理 |
| --- | --- |
| 手机换网络后样本重新累计，往返估计十分钟过期 | 成立。新增纯执行计时，执行估计保留 24 小时；准入按能力、设备、执行器版本和测量范围累计 30 天，网络不参与准入计数。旧客户端的混合 `computedMs` 不转换成纯执行样本 |
| 非裁剪能力由全局质量布尔值批准 | 成立。新增能力质量注册表；注册的评测器负责该能力，无评测器时查询数据库中的逐能力、设备、版本人工决定。缺失、过期或撤销均不批准 |
| 核心引用购物模块，裁剪 schema 带业务名称 | 成立。契约和结果类型移到 `core/capabilities`。裁剪契约版本升为 2，输入输出改为 `image.raster.v1`；Worker 暂时兼容旧 `shopping.image` 上传 |
| 少量近期失败冻结自动路径 | 成立，但只调整近期比例仍不足以解除长期失败门槛。近期至少 5 条才使用 24 小时比例；连续 3 次失败打开断路器。带每日配额的显式后台校准可在最后一次尝试 60 秒后作为恢复探测；前台真实失败率和断路器保持生效 |
| 执行器 `finally` 等待全部反馈写入 | 删除普通执行路径中的重复 `flush()`；维护校准保留落库屏障。`RuntimeWorkScope.run()` 仍等待已跟踪写入，所以不能声称用户响应完全不等数据库 |
| 5% CANARY 需要约 600 个工作流 | 这是满足其他条件、每次都产生合格样本时的期望量级，不是保证。规划器还可能拒绝无收益设备。旧 `crop()` 改为按用户、输入摘要和参数稳定分组；同一输入反复调用不会产生独立试验机会 |
| 固定执行版本、前缀长度、频繁网络采集 | 已调整：版本来自 `RemoteTaskAdmission` 注册信息；样本键显式解析版本；网络事件使缓存失效，正常读取缓存，每 30 秒补采一次 |

## 设备类别与连接方式

手机、PC、平板等都是候选终端。新增 `connectionMode` 区分 `LOCAL`、`HTTP_LEASE`、`POLL_RELAY`，连接开销按协议处理。设备类型仍用于已有冷启动先验；本轮没有重写所有设备类型估计，也没有把轮询适配器升级成长连接代理。

宏观规划始终比较完整成本：输入传输、排队、计算、发布及返回、协调开销和不确定性余量。删除了 `coordinator-roundtrip` 将传输置零的特殊处理。可信适配器可以声明输入的实际副本位置，规划器据此选择路径；缺失有效链路时不能选择该远端路径。

## 分段计时的实际含义

### HTTP 租约协议

分别记录上传、执行器返回的执行时间、下载和端到端总时间。租约申请、查询、释放及其他协议等待记为 `coordination` 剩余项，宏观层额外计入。协调样本尚不可用时采用 100ms 先验，这不是实测值，需在真机测试中检查误差。

### 当前轮询中继协议

端侧使用单调时钟测量：

- `inputTransferMs`：对象存储 GET 的耗时。
- `executionMs`：ImageKit 解码、裁剪、缩放、JPEG 打包的耗时。
- `executorVersion`：注册的执行器版本，目前为 `imagekit-crop-v2`。
- `networkId`：任务前后的网络摘要；任务中切网时不保留链路样本。

服务端保留端到端总时间，并计算：

```text
relay-return = 端到端时间 - inputTransferMs - executionMs
```

`relay-return` 包含等待轮询、排队、哈希与 base64 处理、结果上传、数据库操作和结果消费。它是当前协议无法独立拆分的“回传与协调剩余项”，不冒充纯网络上传耗时。该范围与直接下载、上传和执行成本分开保存、拟合，规划时计入一次。

输入链路标记为 `object-store:<origin摘要> → 终端`，回传链路为 `终端 → cloud-runtime`。存储 origin、网络对和连接方式进入链路标识，签名 URL 的查询参数不进入键。多个业务可复用同一路径；不同存储源不混桶。

纯执行历史跨网络保留，传输和回传剩余项使用短有效期。端到端审计数据单独保存，不再拿它充当计算时间。旧版客户端缺少分段字段，不能提供新执行证据；已选择的目标版本与结果版本不一致时拒绝结果。

**仍需解决的冷启动环节：** 独立网络探测器和自动校准任务源尚未接入。闲置后执行历史不会消失，但链路到期仍需校准或新测量才能重新规划远端。保留执行样本解决了“重新攒 30 次”的问题，不等于已经实现无人干预的网络恢复。

## 网络指纹

HAR 摘要只使用承载类型与去重后的地址前缀，删除 `netId`、接口名和完整主机地址。IPv4 使用接口声明的网络掩码，IPv6 主机部分至少去到 /64；承载类型或前缀变化使链路换桶。监听网络可用、丢失、能力和连接属性事件，补充 30 秒缓存刷新与 500ms 采样上限。

相同私有网段可能存在于不同 Wi-Fi，运营商也可能提供 /32 地址。前缀摘要不能唯一证明物理网络身份，仍要靠链路短有效期和实际传输修正，不能作为授权凭证。

## 质量审批与部署

`CapabilityQualityRegistry.register(capability, evaluator)` 为能力注册评测器，Nest 提供共享实例。内置裁剪评测继续使用固定测试集与 PSNR 策略；必须配置并取得有效评测结果，全局 `qualityPassed`、设备 `qualityVerified` 不再替代它。

无评测器的能力使用 `RuntimeCapabilityApproval`，主键为能力、设备、执行版本；保存批准或撤销、审核人、原因、时间和到期时间。维护命令读取明确的决定，不从执行成功次数推断质量：

```json
{
  "capability": "text.count.v1",
  "deviceId": "terminal-a",
  "executorVersion": "text-v1",
  "approved": true,
  "reviewer": "maintainer",
  "reason": "固定文本测试集已验证",
  "expiresAt": "填写未来且不超过30天的ISO时间"
}
```

在仓库根目录执行 `npm --workspace services/api-server run quality:approve -- <approval.json>`。将 `approved` 改为 `false` 可撤销。该入口只供维护使用，不向设备心跳或普通用户请求开放；已注册评测器的能力不能用此命令绕过评测。

部署前生成 Prisma Client，并通过 `db:init` 应用新增的 `000013_capability_approval`。升级 API、Worker 和 HAP 后，针对新执行版本重新做质量校准；本轮没有运行生产数据库升级或部署。

## 验证与后续边界

本轮实际检查：后端 41 个测试套件、326 项测试通过；Worker 3 项测试通过；后端构建、协议一致性、调度核心类型检查、HAP 与 HAR 构建通过。HAP/HAR 未签名，尚未安装真机；数据库迁移在临时测试库验证，未修改生产数据库。Claude Code 只读复审调用返回 403（可用额度不足），没有取得独立复审结论。

回归覆盖逐设备、逐能力、逐版本批准与撤销，稀疏失败及恢复探测，网络切换、十分钟后保留执行历史、旧计时拒绝复用、总耗时分段核对、缺失链路回退和网络前缀归一化。HTTP Worker 集成测试使用真实进程、真实质量评测和真实传输。非购物能力测试验证通用分桶及独立质量准入，尚不等于第二个 App 的手机与 PC 联调验收。

统一手机通用执行器、主动网络探测、descriptor 缓存、长连接推送、artifact 结果回传和第二个 App 真机接入仍需后续实现。当前 HAP 构建与主机测试不能替代这些验收。
