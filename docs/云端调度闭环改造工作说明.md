# harmony-agent 云端调度闭环改造工作说明

> 适用仓库：`Cixin`
>
> 目标分支：`codex/cixin-multi-device-runtime`
>
> 目标目录：`harmony-agent`
>
> 本文用于主聊天中的后续代码改造，不是当前实现状态的声明。

## 一、必须遵守的产品结论

鸿蒙商品检索的正式业务链路必须运行在 Zeabur 上。手机端只负责采集用户输入、采集图片、读取系统设备画像、提交任务画像、接收调度结果和展示结果。

鸿蒙应用中随仓库携带的商品 JSON、MindSpore Lite 商品向量索引、本地 ANN 检索和本地商品搜索，只能保留为离线诊断、模型自检或测试夹具，不能再作为正式商品检索路径。正式运行时不得因为云端不可用而静默退回到本地商品数据库；必须返回可识别的云端不可用、超时或调度阻断状态。

所有由应用发起的业务任务都必须经过统一路线：

```text
用户操作
  -> 应用任务画像
  -> 设备画像与链路画像采集
  -> 鸿蒙端调度器评估
  -> 选择本地/云端执行器
  -> 执行器真正执行
  -> 结果、时延、资源和失败原因反馈
  -> 必要时重规划或向用户提示
```

“生成了计划”不能作为“任务已执行”的替代。计划必须绑定一个真实执行器；执行器必须返回结果和遥测；失败、超时、取消和回退都必须进入运行记录。

## 二、当前需要纠正的真实问题

### 1. 鸿蒙端仍把本地商品检索当作正式路径

`apps/harmony/entry/src/main/ets/services/ShoppingTaskService.ets` 当前注册并执行：

- `query_prepare`
- `text_encode`
- `vector_retrieve`
- `product_search`
- `index_warmup`

这些执行器依赖 `DataInitService` 和 `NeuralEmbeddingIndex`，会读取随 App 打包的商品数据和本地向量。它们不能继续作为鸿蒙商品检索的正式入口。

需要把正式的 `product_search` 改为云端任务：手机端调度器根据任务画像和设备画像决定是否调用 Zeabur API，云端 API 再访问 Zeabur 持久化数据库、COS、云端模型和商品检索服务。

### 2. 当前云端模型代理仍指向本地地址

以下代码存在 `10.0.2.2:3010`、`127.0.0.1:3010` 等本地代理地址：

- `apps/harmony/entry/src/main/ets/services/ModelSearchService.ets`
- `apps/harmony/entry/src/main/ets/services/ModelEngineRegistry.ets`

这些地址不能用于正式手机测试。应统一改为可配置的 Zeabur HTTPS API 基址，不能把 Zeabur 域名、密钥或测试地址写死在业务服务中。

### 3. 服务端任务图没有覆盖完整业务链路

`services/api-server/src/core/runtime/image-search-task-graph.ts` 当前只创建：

```text
quality-check -> crop -> embedding -> vector-search
```

这不足以描述正式云端商品检索。完整任务图至少应覆盖：

```text
接收任务
  -> 上传/确认 COS 资产
  -> 图片质量检查
  -> 主体裁剪与标准化
  -> 类别识别
  -> 详细商品画像
  -> 查询向量生成
  -> Zeabur 数据库/向量索引召回
  -> 价格、库存或平台信息查询
  -> 结果融合与排序
  -> 生成结构化回答
  -> 返回结果与遥测
```

任务图中的每个节点都必须有完整 `TaskIntent`，包括输入引用、输出类型、依赖关系、时延约束、隐私约束、质量要求、费用约束和云端路由观测。对于图片任务，任务图不能携带 COS 签名 URL 或密钥，只能携带资产引用和路由元数据。

### 4. 服务端 Runtime 目前只有规划，没有通用执行器

`services/api-server/src/core/runtime/scheduler.service.ts` 的 `plan()` 会生成 `ExecutionPlan`，但 `RuntimeRunService` 没有按照 `executionOrder` 遍历 assignment 并调用执行器的通用 runner。

`SearchDebugController` 的当前行为是：

1. 创建 Runtime 记录。
2. 附加任务图并生成计划。
3. 直接调用 `SearchDebugService.run()`。
4. 把业务时间线写回 Runtime。

这说明 Runtime 目前只是业务执行旁边的观测层。需要增加真正的执行层，使正式会话和图片搜索都走统一的 Runtime 执行入口。业务服务仍然拥有业务逻辑，但必须作为 Runtime 注册的工作流执行器被调用，不能由 Controller 绕开调度器直接调用。

### 5. 云端执行器被保守标记为不可用

`services/api-server/src/core/runtime/cloud-platform-adapter.service.ts` 当前即使读取到云模型配置，也会返回：

- `available: false`
- `CLOUD_PROVIDER_SPECIFIC_PROBE_NOT_IMPLEMENTED`
- `supported: false`

这会导致调度器永远拒绝云端候选。需要实现真实探测：

- Zeabur API 自身 readiness 探测。
- COS 配置、签名读写和最小对象读写探测。
- 云模型健康探测和模型能力探测。
- 云端商品检索数据库可读探测。
- 探测超时、失败和缓存时间。

探测成功只能说明执行器具备运行资格，不能直接伪造真实性能样本。性能样本仍应通过真实执行产生，并按执行段、上传段、COS 读段、排队段、下载段分别记录。

## 三、目标架构

### A. 鸿蒙 App 层

鸿蒙 App 不直接访问数据库、COS 密钥或商品数据文件。App 只持有：

- Zeabur API 公网 HTTPS 基址。
- 必要的用户认证或设备认证信息。
- 当前设备画像。
- 当前任务画像。
- Runtime runId、taskId 和结果引用。

App 的任务提交接口应抽象为业务无关的调度客户端，例如：

```ts
submitTask(profile, inputRef): WorkflowHandle<Result>
```

商品检索只是一个任务能力，不应让 UI 直接依赖 `NeuralEmbeddingIndex` 或本地商品数组。

### B. 任务画像层

每次用户操作都要创建完整任务画像，至少包括：

- `taskId`、`toolId`、输入引用、输出类型。
- 任务类型：前台实时、用户主动、后台批处理。
- 时延目标、硬截止时间、质量下限、能源预算、费用预算。
- 隐私等级和是否允许云端。
- 输入大小、输入是否在设备/COS/Zeabur 卷/外部 API。
- 结果希望回到设备、COS、Zeabur 卷还是外部 API。
- 依赖节点和失败处理策略。
- 当前设备画像快照。
- 当前网络链路画像快照。

云任务还必须提供 `cloudRoutes[]`，字段至少包括：

- 执行器 ID。
- 输入驻留和输出去向。
- 传输方式和传输授权。
- 输入输出字节数。
- 往返时延、上下行带宽。
- COS 或 Zeabur 存储读写时延。
- 云端排队时延。
- 费用估计。
- 签名访问过期时间。
- 观测来源和观测时间。

### C. 鸿蒙调度器层

鸿蒙端调度器负责使用手机真实设备状态做第一层决策：

- 温度、内存压力、电量、CPU/GPU/NPU 可用性。
- App 前后台状态和用户是否等待结果。
- 网络 RTT、上行带宽、下行带宽和连接状态。
- 任务复杂度、数据大小、隐私和质量目标。

调度器输出必须是明确的本地或云端执行计划。云端计划必须包含 provider、超时、重试、并发上限和是否允许本地回退。

商品检索正式任务的默认策略是云端优先或云端唯一，原因是商品数据库、COS 图片和云端检索能力都在服务端。只有明确标记为离线诊断/模型自检的任务才允许使用本地索引。

### D. 执行器层

至少实现两个真实执行器：

1. `cloud-shopping-api`
   - 由鸿蒙端执行。
   - 按计划向 Zeabur 发起 HTTPS 请求。
   - 支持文本检索、图片资产引用、会话创建、候选刷新和结果读取。
   - 记录上传、请求、排队、响应、下载和失败信息。

2. `zeabur-shopping-workflow`
   - 由服务端 Runtime 执行。
   - 负责调用现有业务服务完成图片质量、COS 资产、模型、向量召回、候选融合和回答生成。
   - 不能让 Controller 直接调用业务服务绕过 Runtime。

执行器必须返回结构化结果，例如：

```json
{
  "status": "succeeded",
  "runId": "run_xxx",
  "taskId": "image-search-xxx",
  "resultRef": "session:xxx",
  "data": {},
  "telemetry": {
    "uploadMs": 0,
    "storageReadMs": 0,
    "queueMs": 0,
    "executionMs": 0,
    "downloadMs": 0
  }
}
```

### E. 服务端数据层

Zeabur 上的 API 服务使用挂载持久卷上的数据库；商品图片使用 COS；应用通过 HTTPS API 访问二者。手机不能直连数据库，也不能持有 COS SecretId、SecretKey。

服务端配置必须支持：

- Zeabur `PORT` 和 `0.0.0.0` 监听。
- 持久化数据库连接。
- COS 私有桶上传和签名读取。
- 云模型和商品检索提供商配置。
- readiness 对数据库、COS 和关键云服务进行检查。

## 四、建议的实施顺序

### 第 1 步：废弃鸿蒙正式本地商品链路

- 修改 `ShoppingTaskService`，正式 `search()` 不再读取 `DataInitService`、`NeuralEmbeddingIndex` 和本地商品向量。
- `EntryAbility` 不再把本地商品数据库初始化作为正式搜索前置条件。
- 保留本地模型和数据文件，但明确标记为 `offline_diagnostic`。
- 目录、注释、文档和 UI 中不要再把“本地商品库”称为正式商品库。

### 第 2 步：实现鸿蒙端 Zeabur 调度执行器

- 新增独立的云端 API 客户端，不把 URL 写在多个服务中。
- 新增云端商品检索任务模板，使用 `InferenceLocation.REMOTE_CLOUD`。
- 在 `EntryAbility` 注册远程执行器配置。
- 让远程执行器真正调用 Zeabur API。
- 将设备画像和任务画像随请求发送给云端，不能只发送一个搜索字符串。
- 处理超时、取消、重试、服务不可用和结果过期。

### 第 3 步：补全服务端任务图

- 重写 `image-search-task-graph.ts`，构造完整云任务图。
- 为文本会话、图片会话、候选刷新、价格查询、回答生成分别提供任务图工厂。
- 任务图工厂只生成画像，不决定最终执行器。
- 由调度器依据画像、设备状态和云路线进行选择。

### 第 4 步：实现服务端 Runtime Runner

- 新增执行器注册接口和执行器注册表。
- 新增按 `ExecutionPlan.executionOrder` 执行的 Runner。
- 校验依赖节点是否成功后再执行后继节点。
- 每个 assignment 都必须有开始、成功、失败、取消或超时状态。
- 将业务服务封装为执行器适配器。
- 修改正式 Controller，使其调用 Runtime Runner，而不是直接调用 `SessionsService` 或 `SearchDebugService`。

### 第 5 步：实现云端真实探测

- 用 Zeabur readiness、COS 最小探测和云模型最小请求实现 `CloudPlatformAdapterService`。
- 把探测结果短时间缓存，避免每个任务重复发送探测请求。
- 探测失败时将候选明确标记为不可用，并给出原因。
- 不用 `available: true` 或固定延迟伪造健康状态。

### 第 6 步：统一遥测和调度盘数据

- 手机端上报设备资源画像、任务选择、云端链路分段时延和结果状态。
- 服务端记录 Runtime run、task graph、execution plan、assignment、telemetry 和 replan。
- 调度盘读取真实 Runtime 数据，不再使用静态演示数值作为主要状态。

## 六、验收标准

下面的条件全部满足后，才能认为本轮改造完成：

1. 鸿蒙 App 执行一次商品文字检索时，网络请求到 Zeabur API；没有访问本地商品 JSON、`NeuralEmbeddingIndex` 或本地 ANN。
2. 鸿蒙 App 执行一次图片检索时，图片通过云端资产接口进入 COS/服务端链路；App 不直接访问数据库或 COS 密钥。
3. App 发送的请求中包含任务画像、设备画像、runId/taskId 或等价的运行关联信息。
4. 调度器先生成计划，再由远程执行器发起 HTTP 请求；日志中能够看到计划选择和真实执行结果。
5. 服务端接收任务后构造完整任务图，并由服务端 Runner 按依赖顺序执行或明确阻断。
6. 云端执行器健康探测成功后才可被选中；探测失败会阻断云候选并返回原因。
7. 任务成功、失败、超时、取消和回退都能在 Runtime run 中查询到。
8. 云端任务遥测至少能区分上传、存储读取、排队、模型/检索执行、存储写入和下载时延。
9. `npm run api:build`、服务端单元测试和鸿蒙调度器类型检查通过。
10. 项目日志明确记录：本地正式商品链路已废弃，Zeabur 云端链路已接管，哪些功能已真实执行，哪些仍受外部云服务配置影响。

## 七、不能接受的完成方式

- 只增加 `cloudRoutes` 字段，却不在任务图中填充。
- 只返回 `ExecutionPlan`，没有任何 Runner 或执行器调用。
- 让 Controller 先直接执行业务，再把执行时间线写成“调度执行”。
- 将 `available: false` 永久作为云端实现。
- 将本地商品向量检索作为云端失败时的静默回退。
- 把设备温度、内存和电量画像当成云任务完整画像；云任务必须额外描述网络、存储、传输、排队、费用和授权。
- 把签名 URL、COS 密钥或模型 API 密钥放进任务图、App 包或前端代码。

## 八、改造后的核心判断

`original_app` 的价值是提供正式业务 API、数据库、COS 和云模型链路的参考实现；`harmony-agent` 要做的是在这个业务链路外面增加可执行的端侧调度层，并让服务端业务也进入统一 Runtime 执行框架。二者不是二选一：业务能力属于应用/服务，资源选择和执行控制属于调度件。

最终应达到：应用只描述“我要完成什么”和“输入在哪里”，调度件根据手机设备状态与端云链路选择执行位置，执行器负责真正调用本地或 Zeabur 能力，业务结果和资源反馈再回到调度件。
