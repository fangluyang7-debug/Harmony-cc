# HarmonyOS 真机联合调试计划

编制日期：2026-09-28（Asia/Shanghai）。状态：待按阶段执行。

本计划供项目成员与其他 agent 接力使用。实时状态以[调试进度](真机联合调试进度.md)为准；本文件定义步骤和验收要求，不代表这些步骤已经通过。

## 1. 目标与边界

1. 跑通真机 -> Zeabur API -> 云数据库/COS -> 模型服务 -> 真机结果展示的正式链路。
2. 在电脑浏览器观察手机资源、调度计划、任务终态和网络耗时，保留可追溯证据。
3. 验证文本、图片、筛选/刷新、连续操作、取消和前后台恢复，修复实际复现的问题。
4. 用分场景实测数据评估超时、并发、网络画像与成本预测，形成可回退的参数候选。
5. 区分“代码已改”“检查通过”“已装机”“真机通过”“云端已部署”，不混用完成状态。

正式商品搜索当前是 REMOTE_CLOUD；本地商品数据和离线执行器不能替代云端成功结果。云端商品总量须从云端核验，不能从本地准备行数推断。手机面板用于辅助诊断；日常调试主观察界面是电脑监控页。电脑现有监控页是只读接收器，不应假定它已经支持远程修改手机策略。

本阶段不以空闲状态的一张截图调整热保护、内存保护、电池阈值，也不以模型推荐名称替代实际开通、返回和执行记录。

## 3. 多人协作规则

| 角色 | 工作范围 | 交付 |
|---|---|---|
| 真机操作人 | 独占本轮手机 UI、安装、前后台和网络切换 | 截图、布局、步骤、运行编号 |
| 客户端负责人 | 页面、鉴权提示、生命周期、云端执行器 | 最小修复、回归结果、HAP 标识 |
| 云端负责人 | 用户鉴权、数据库、COS、模型执行、运行关联 | 脱敏服务日志、runId、阶段耗时、部署版本 |
| 调度负责人 | 约束原因、网络画像、参数分析 | 基线分组、候选参数、对照结果 |
| 记录人 | 维护进度与证据索引 | 每轮结论和下一接手步骤 |

- 一次只有一人控制真机；其他人可读代码或分析已导出的证据。
- 修改文件前在进度表登记负责人和范围。同一文件避免同时编辑；先读当前 diff，保留已有改动。
- 安装包、重启 App、重启监控或切换网络前通知同轮执行人，记录操作时间，防止打断采样。
- 不清理其他人的进程、日志、应用数据或未提交修改。确需清数据时先记录影响并与操作人协调。
- `.env`、模型 Key、COS 凭据、JWT、维护令牌、密码、监控配对码不写入共享 Markdown 或提交。
- 接手者先读进度，再确认现场状态；上一次服务启动、PID、IP、配对码均可能失效。

## 4. 阶段 A：打通观察与前置条件

### A1. 电脑监控配对

1. 检查端口和当前服务是否已存在，优先复用正在采样的实例；没有实例时运行 `npm run monitor:dev`。
2. 电脑打开 `http://localhost:8765`，使用当前服务终端显示的配对码完成认证。
3. 手机“我的 -> 电脑实时监控”填写电脑可达地址与同一配对码，保存并开启推送。
4. 验证电脑出现新快照，设备状态持续更新，时间戳前进；至少观察 60 秒。
5. 验证后台暂停、回前台恢复、关闭推送停止更新。用时间戳区分旧快照和实时数据。
6. 不通时依次检查地址/端口、认证、手机 foreground 标记、HTTP 可达性、局域网隔离和防火墙；一次只改变一个因素。

验收：电脑能收到真实手机快照及终态事件，重连行为符合设计；关闭监控不阻塞业务。配对失败不得标记为监控通过。

### A2. 云端前置条件

1. 确认手机云端地址已保存，页面能区分“未配置”“未登录”“鉴权过期”“服务不可用”。
2. 使用团队指定测试账号登录；不要把服务维护令牌或模型 Key 当作手机用户凭据。
3. 云端负责人确认数据库、COS、模型依赖和商品可检索状态，记录检查时间与服务版本。
4. 用一条确定存在的商品查询做冒烟测试，将手机 taskId 与云端 runId 关联。
5. 若失败，保存 HTTP 状态/脱敏业务码、调度终态、路由准备结果；不得只依据页面泛化文案认定是资源阈值问题。

验收：至少一条正式搜索返回可展示商品并有可关联云端运行；前置错误能显示具体可操作提示。

## 5. 阶段 B：功能与生命周期矩阵

每条记录输入类别、步骤、预期、实际、终态、taskId/runId、证据路径、执行人及版本。测试账号和输入只使用团队允许的数据；原图和搜索原文不混入共享遥测。

| ID | 场景 / 步骤 | 验收重点 |
|---|---|---|
| F01 | 解锁启动、进入首页和“我的” | 无崩溃；云端配置与登录状态准确 |
| F02 | 首页快捷词“500以内跑鞋” | 输入确定，正式请求可追踪；过滤结果可核验 |
| F03 | 手动中文输入、键盘搜索、发送按钮分别提交 | 无重复提交；键盘弹出后按钮位置正确；记录自动化误点与应用缺陷的区别 |
| F04 | 耐克/华为等品牌预算查询 | 仅在云端存在对应数据时验证召回；数据缺失和执行失败分开 |
| F05 | 图片选择 -> 搜索 -> 展示 | COS/图片处理/视觉与 embedding 阶段实际执行可追踪 |
| F06 | 取消图片选择、无权限、合法空输入 | 不误创建任务，不卡住加载状态 |
| F07 | 高质量模式前后对照 | 记录实际模型与阶段变化；不能仅凭 HIGH_ACCURACY 标签推断 Pro 被调用 |
| F08 | 商品详情、返回、排序/刷新、清单 | 已实现操作可正常往返；云端读取/刷新有对应结果 |
| F09 | 连续 A/B/C 三次提交 | KEEP_LATEST 行为正确，旧结果不覆盖新结果，无悬挂活动任务 |
| F10 | 请求中切标签页或离开结果页 | 取消/继续语义与产品设计一致，终态完整 |
| F11 | 请求中后台 -> 前台 | UI、任务和监控恢复一致；不重放产生副作用的 POST |
| F12 | 断网、恢复网络、请求超时 | 明确失败/取消；重连后新请求成功，无虚假本地结果 |
| F13 | App 重启、退出登录、切换云端地址 | 旧 token/路由不串用；会话持久化行为与设计一致 |
| F14 | 反馈关闭/开启、满足门槛后回答 | 同意、频控、任务关联和回执正确；不将未回答视作满意 |
| F15 | 监控停止/恢复、错误配对码 | 认证有效；业务与监控故障隔离，无凭据泄漏 |

图片/模型调用存在实际费用，控制样本规模。弱网可复现测试须记录实现方式；不能将真实弱网与模拟注入混为一组。高温、低电和低内存先用单元测试验证保护逻辑，真实状态自然出现时再测，不主动制造设备危险状态。

## 6. 阶段 C：遥测字段与证据采集

| 类别 | 必须记录 | 解释限制 |
|---|---|---|
| 设备 | SOC、充电、热等级、前后台、CPU、可用/总内存、数据来源 | 热等级不等于摄氏温度；可用内存不等于 App RSS |
| 请求 | 用例 ID、operation、高质量开关、taskId/runId、终态/错误码 | 不导出 token 或任意请求头 |
| 调度 | 策略版本/模式、候选与选中路由、约束拒绝原因、并发与队列 | 计划配置和实际执行分开 |
| 网络 | RTT、有效上下行、TTL、网络代次、预测传输/总耗时 | 无观测填未知，不能填 0 |
| 执行 | 客户端端到端、请求、服务端排队/计算、上传/下载（有则填） | 不把含排队的耗时当纯计算耗时 |
| 模型 | 各阶段实际 provider/model、重试/降级、调用计数 | 手机标签不能证明云端模型路由 |
| 结果 | 展示/消费/忽略、质量核验、取消与超时 | 不只统计成功样本，保留失败分母 |

建议证据目录：`artifacts/phone-live/<日期>-<执行人>-<轮次>/`；旧平铺文件保留。共享前筛查截图、布局和日志中的账号、密码、输入、地址和配对信息。监控当前仅在内存保留有限近期数据，长实验必须先确认脱敏导出方案，不能等服务退出后再取证。

HDC 屏幕截图使用设备支持的 `.jpeg` 后缀；布局文件虽然名为 `.xml`，现有 `uitest dumpLayout` 输出实际是 JSON，应使用 JSON 解析器。

```powershell
& $hdc shell snapshot_display -f /data/local/tmp/debug-case.jpeg
# 将文件接收到本轮已创建的证据目录后再引用
& $hdc shell uitest dumpLayout -p /data/local/tmp/debug-case.xml -b Micro.12.myapplication -a
& $hdc shell pidof Micro.12.myapplication
# 下方 <APP_PID> 用本次实际 PID 替换；不要使用 PowerShell 保留变量 $PID
& $hdc shell hilog -x -P <APP_PID>
```

设备显示时钟与电脑时钟此前存在差异。每轮同时记录设备/主机时间，关联任务优先用 ID；耗时优先使用同一进程的时长字段，不直接相减跨设备墙钟。

## 7. 阶段 D：参数收束方法

### 7.1 当前源码起点（执行时重新核对）

`ShoppingTaskService.ets` 当前声明：正式云端搜索、KEEP_LATEST、截止/超时 150000 ms、远端最大并发 2、maxRetries 1、禁止本地 fallback；估计延迟 10000 ms、估计内存 48 MB。上述是代码配置，不是实测最佳值；maxRetries 不意味着业务 POST 可安全重放。

先确认实际路径：应用任务入口 -> SchedulerClient / SchedulerService -> 实际生效策略 -> 路由准备与 CloudShoppingExecutor -> 云端调度/模型。旧 SchedulerPolicy 的本地档位常量不应被当成所有正式请求的控制点。

### 7.2 采样分组

1. 先收集正常网络、充电、前台的基线：文本普通/高质量、图片分别分组；冷启动首请求与预热请求分开。
2. 每组建议至少 10 条有效样本做初步判断；这是本轮实验建议，不是自动校准的充分条件。
3. 需要报告 P95 时尽量达到每组 30 条并标明数量，小样本分位数仅作探索；先完成小批验证再扩量。
4. 记录失败、取消、超时及其分母，按云端版本、策略、网络、输入大小、设备状态分桶；不混合不兼容样本。
5. 只改变一个参数，对照相同用例；确保实际样本来自改变后的 HAP/服务版本。

### 7.3 决策与回退

| 参数方向 | 必需依据 | 修改限制 |
|---|---|---|
| 客户端/云端超时预算 | 总耗时分布、阶段耗时、超时占比 | 预算覆盖完整链路；先定位慢阶段，不能仅无限增大超时 |
| 并发与排队 | 1/2 并发对照、延迟、取消、CPU/内存、服务限流 | 不超过实际执行器及服务承载能力 |
| 路由 TTL / 网络切换 | 实测画像寿命、切网后失效与重测行为 | 旧网络样本不得继续影响新网络选择 |
| 初始成本与 EWMA | 同组预测误差、样本数量、冷/热差异 | 未观测数据保持未知；失败时长不作为成功计算时长学习 |
| 模型场景选择 | 实际模型执行、质量评估、费用/延迟 | 明确视觉、embedding、关键复核各自任务；不降低质量底线冒充提速 |
| 电量/内存/热保护 | 多状态、持续采样和保护测试 | 单台空闲手机基线不足以放宽保护阈值 |

每个参数提案记录旧值、新值、单位、影响路径、样本组、收益、回归风险和回退方法。OBSERVE 阶段先积累证据，CANARY/ACTIVE 仅在质量与稳定性门槛满足后考虑。验收无改善或失败率/质量恶化时撤回本轮参数变更。

## 8. 修复与验证流程

每个缺陷：复现 -> 确认原因 -> 最小修复 -> 针对性测试 -> 构建 -> 明确安装版本 -> 原用例复测 -> 相邻回归 -> 更新进度。源码变更不能直接标记为手机修复成功。

按修改范围选择现有检查，不要求每次全部执行：

```powershell
npm run cloud-shopping:typecheck
npm run cloud-shopping:test
npm run scheduler:typecheck
npm run algorithm:test
npm run concurrency:test
npm run placement:test
node scripts/test-network-monitor.mjs
# 原生测试与构建使用已验证的 DevEco 路径；此操作会生成构建产物
./scripts/native-check.ps1 -StudioHome 'E:\DevEco\DevEco Studio' -Task all
```

后端修改另运行相关 API 测试并记录部署版本。已有历史测试报告不能证明本轮 dirty tree 已通过。

## 9. 阶段退出条件

- A：电脑遥测真实可见，云端登录与至少一次正式搜索通过。
- B：功能矩阵逐条有结论；阻断项修复并在同一版本复测，未实现项明确列为缺口。
- C：设备、任务、云端阶段能够关联，关键字段有真实值或明确未知原因。
- D：形成分组基线和参数提案；不足以调参时交付“保持原值 + 缺失证据”，不强行给最佳阈值。
- 最终交接：进度表、缺陷表、版本/证据索引、检查结果、未完成项和下一条操作齐全。
