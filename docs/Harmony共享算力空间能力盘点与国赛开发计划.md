产品目标以 [Harmony 团队共享算力空间功能设计方案](Harmony团队共享算力空间功能设计方案.md) 为准。当前代码基线为 `codex/scheduling-data-pipeline` 分支的 `5c63ee3`，包括协作人最近对成本数据、终端计时和能力质量准入的修订。

下一阶段主线是独立的团队共享算力产品：成员创建空间、接入设备、提交通用任务，系统按授权和团队规则协调执行。购物应用退为历史示例和必要的回归对象，新功能不再依赖商品、购物会话、购物推荐或购物专属模型服务。

现有基础可复用，但完整产品流程尚未形成。优先交付一个真实可演示的闭环，再扩展资源预约、公平性策略和更多任务类型。决赛时间、开发人数及真机配置暂未确定，因此采用依赖清晰的里程碑，不承诺未经验证的日期或工期。

## 一 现有能力与功能差距

“已有基础”表示代码和相关回归存在，不等同于团队产品已交付或已完成真机验收。上一轮本地验证通过后端构建、41 个测试套件的 326 项测试、3 项 Worker 测试、协议一致性和调度核心类型检查；这些结果不证明真实多设备的性能收益。

| 目标功能 | 当前基础 | 主要缺口 | 国赛闭环要求 |
|---|---|---|---|
| 创建空间与邀请成员 | 用户、认证和手机配对基础 | 团队空间、成员关系、角色、邀请有效期与撤销；现有配对不是团队入群 | 独立账号创建空间，其他账号扫码加入 |
| 设备接入与归属 | 设备目录、心跳、状态有效期、维护注册和撤销 | 普通成员自助绑定、独立设备凭据、跨网络主动连接、可见的接入状态 | 新设备无需手改服务器配置即可出现在空间中 |
| 设备主人控制共享 | 端侧资源感知、槽位限制、取消与温度等部分检查 | 共享范围、时段、额度、暂停、排空、主人活动保护的统一产品规则 | 主人可暂停共享，服务器和设备端共同执行限制 |
| 通用任务提交 | 通用能力契约、任务图、输入输出引用、内部派发入口 | 面向成员的任务模板、提交与上传接口、独立任务中心 | 从手机或电脑提交任务，无需购物会话 |
| 异构设备执行 | CPU Worker 支持裁剪和向量范数计算；手机有裁剪实验路径 | 通用手机执行器、真实 GPU 执行器、按能力描述模型与后端 | CPU 与 GPU 承担不同步骤，展示实际执行设备 |
| 自动选择设备 | 能力、质量、成本、隐私、资源与链路检查；运行后反馈 | 将团队授权与队列规则纳入决策；自动接入校准；取消固定云端基线依赖 | 合法设备中做选择；没有可用设备时明确等待 |
| 批量并行与跨设备接力 | 多节点任务图、依赖结果传递、后续节点重新规划 | 当前派发主要按顺序执行，缺少持久化就绪队列与跨设备批量并行 | 两台 CPU 设备可同时处理不同分片，随后进入 GPU 阶段 |
| Leader 优先分配 | 局部优先级、任务紧急程度和策略字段 | 团队成员队列、GPU 优先保障、闲置借用、预约、额度、公平性 | B 提交任务后，其任务在规定的分片边界优先获得 GPU |
| 统一控制台 | 调度调试页面、运行事件、状态快照和原因记录 | 团队总览、成员权限、设备卡片、任务分工和面向用户的解释 | 页面实时对应真实任务状态，并展示分配原因 |
| 离线恢复与取消 | 租约、过期结果拦截、取消、有限回退及部分分块恢复 | 通用持久化任务状态、跨设备重试、协调者重启恢复、结果去重结算 | 退出设备后剩余分片转移；已完成结果保留 |
| 结果与数据授权 | 制品引用、内容哈希、所有者校验和部分存储 | 通用文件类型、团队范围授权、临时执行访问、下载及保留规则 | 同组成员不能自动读取他人输入和结果 |
| 贡献统计与审计 | 性能反馈与局部运行记录 | 持久化用量账本、成员贡献、策略变更审计、重试去重 | 展示成员贡献及 CPU/GPU 分项用量 |

## 二 协作人修改的复用方式

保留并继续使用以下四组能力，避免重新建设同类逻辑：

1. **成本记录与复用。** 使用原始反馈、内存估计和版本隔离，分别统计执行、传输、协调和完整往返；任务换输入或设备换网络时，只失效对应范围的记录。
2. **独立质量准入。** 质量证据按能力、设备和执行版本管理。性能好不代表结果正确，设备通过裁剪评测也不代表可以直接执行其他能力。
3. **试运行与恢复探测。** 保留受限校准、小流量试运行、失败断路器及有额度的恢复探测。将维护命令背后的能力接入产品流程，不通过伪造样本或关闭质量检查实现“一键可用”。
4. **能力契约与设备执行边界。** 复用输入输出、成本参数、模型兼容性、租约、取消和结果校验，逐步统一手机、CPU 和 GPU 的接入行为。

新 GPU 能力需要自己的执行实现和质量验证包；现有裁剪评测不能替代它。首次接入应显示“已连接、能力检测中、验证中、就绪、需要处理”等真实状态，成员加入空间与设备可执行任务是两个不同步骤。

## 三 从购物应用转向通用平台

### 产品入口

手机主入口调整为“空间、任务、我的设备”；电脑控制台围绕“总览、设备、任务、成员与规则、贡献记录”组织。购物入口退出主导航，不继续作为任务提交的前提。

新任务模板先覆盖通用视觉素材处理，再增加一个输入输出不同的独立模板验证扩展性。图片任务可以作为首个演示，但不绑定商品类别、商品数据库或购物推荐。

### 系统职责

| 层次 | 职责 | 与现有代码的关系 |
|---|---|---|
| 团队空间与权限 | 成员、邀请、设备授权、角色、策略版本、审计 | 新增业务域，复用账户认证 |
| 任务中心 | 提交、文件、持久化状态、任务分片、结果与通知 | 复用契约和制品概念，补齐通用接口与状态管理 |
| 团队队列 | 决定谁的哪些就绪任务先获得资源 | 新增跨成员调度；不能用单工作流放置器替代 |
| 设备选择 | 在已授权候选中，根据能力和完整成本选择设备 | 扩展现有宏观调度与质量、成本模块 |
| 设备代理 | 连接、资源上报、本地准入、实际执行、停止与结果回传 | 复用 Worker 和 HAR，补 GPU 与通用手机执行器 |
| 可视化与计量 | 状态流、原因解释、用量与贡献 | 复用事件机制，新增团队权限过滤与持久化记录 |

最小数据边界包括空间、成员、邀请、设备、设备授权、能力安装、任务、任务分片、执行尝试、输入输出制品、策略、用量和审计事件。任务提交者、设备主人、空间负责人应为独立身份，不得为跨成员执行而移除现有所有者校验。

有效授权为设备主人允许范围、空间规则、任务数据授权的交集。访问控制同时覆盖查询、事件订阅、文件下载和执行领取，不能只限制页面按钮。设备只获得当前授权任务所需的输入访问能力。

### 优先处理的耦合

| 现有位置 | 需要改变的方向 |
|---|---|
| `PhoneDispatchService` 和 `CloudPhoneDispatchPage` | 从购物裁剪专用协议与实验页面，转向通用任务领取、执行和设备管理 |
| `ArtifactStoreService` | 将购物数据编码和图片类别留在旧适配层，通用制品不依赖 `shopping-payload` 或商品资产 |
| `RuntimeRunService` | 现有运行记录包含内存 Map，需建立重启后可恢复的任务事实记录 |
| `DeviceDispatchService.dispatch()` | 将顺序派发能力接入持久化就绪队列，支持独立分片并行和尝试级恢复 |
| `cloud-runtime` 与 `CLOUD_BASELINE` | 区分协调服务与计算设备；云端执行作为可选节点，不能是通用任务运行的必要条件 |
| 现有两套任务图及运行接口 | 明确一个产品任务契约和状态来源，通过适配复用旧接口，避免形成第三套并行事实来源 |

逐步隔离旧购物模块，不在建立新闭环前进行大规模删除。新主流程的验收应在未配置购物模型接口、未导入商品数据的情况下通过。

## 四 国赛版本范围

### 必须完成

- 创建空间、邀请加入、独立账号、负责人和成员权限。
- 手机与电脑的成员入口，CPU 与 GPU 设备自助接入。
- 设备主人共享范围、暂停、排空与退出；不满足共享条件时停止新增分配。
- 通用任务提交、输入上传、状态查询、取消、结果获取。
- CPU 批量并行、真实 GPU 推理和跨阶段结果衔接。
- GPU 优先保障 B、其他成员闲置借用、分片边界让出。
- 设备离线后的剩余分片重新分配与重复结果拦截。
- 实时团队控制台、调度原因、贡献和审计记录。
- 自动能力验证及链路测量流程，首次接入和闲置后恢复无需修改后台数据。
- 第二个独立任务模板，经相同任务接口接入，验证通用性。

### 完成闭环后扩展

完整预约日历、多种资源保障策略、复杂公平性算法、精细额度、更多操作系统及模型、手机长时间后台贡献、更多能力的质量评测插件、端到端耗时分位数预测。

### 本轮不作为路演承诺

任意应用无需适配即可使用远端资源、多台设备显存自动合并、任意进程实时迁移、任意模型无损抢占、所有任务均能加速、所有设备长期满载。

## 五 里程碑与退出条件

每个里程碑都应提供可操作页面或设备流程及对应验收记录。界面开发从首个里程碑开始，避免最后才把底层模块拼成演示。

### M0 冻结任务契约并验证硬件路径

确定新主入口、任务与状态契约、首个能力包和演示资源拓扑。核对可用 GPU 的型号、显存、运行环境及模型需求，在实际设备上执行一个固定输入并获取可检查的输出。

首个任务建议为“批量视觉素材整理”：CPU 负责格式统一与预处理，GPU 负责视觉分类或标签分析，最后汇总可浏览的结果。具体模型由实际 GPU 验证决定，不在硬件未知时承诺模型规模。

第二模板建议为“批量文本统计报告”，用不同输入输出验证平台没有将图片和购物写死。它用于接入验证，无需人为包装成有明显加速收益的任务。

**退出条件：** 固定输入在真实 GPU 上完成计算；CPU 和 GPU 步骤的输入输出约定明确；运行证据能区分真实 GPU 执行和 CPU 回退；不依赖购物系统。尚无 GPU 时允许继续设计和 CPU 开发，但 GPU 路演链路保持未验收。

### M1 空间与设备接入

实现空间、成员、邀请、角色及设备所有权；提供电脑端接入引导和手机空间页面。设备主动连接协调服务，完成认证、心跳和能力报告；负责人不需要为每台个人电脑配置公网入口。

加入空间后，设备主人再确认是否共享，以及共享范围。普通成员可以只使用资源。初版角色至少覆盖负责人、管理员、成员、观察者的权限边界，界面可按路演需要突出负责人和成员。

**退出条件：** 三个独立账号能完成创建与加入；邀请码过期和撤销生效；成员可绑定两台设备；空间外账号不能读取设备与任务；撤销设备凭据后不能继续领取任务。新设备在界面中展示检测与验证进度。

### M2 通用任务最小闭环

建立通用任务 API、持久化状态、制品上传下载、分片与执行尝试记录。先完成“手机提交 → 一台 CPU 设备执行 → 手机获取结果”，同步上线任务列表、任务详情与设备卡片。

将 HTTP 请求生命周期与任务生命周期分开。页面关闭或刷新不丢任务；取消后迟到结果不能把任务改回成功。手机提交和手机贡献算力分别实现，不要求提交者贡献设备。

**退出条件：** 在没有商品数据和购物接口配置时完成任务；任务、输入和结果受成员权限保护；重启协调服务后仍能查询任务并对账执行状态；重复提交或重传结果不会产生重复完成记录。此阶段即接入第二模板的最小任务，尽早检验接口通用性。

### M3 真实 CPU 与 GPU 协同

新增 GPU 执行器的注册、能力描述、模型版本、显存需求、冷热状态和执行反馈；将质量验证、性能校准和链路探测接入设备就绪流程。

把任务拆成有依赖的分片：允许就绪分片在多台 CPU 上并发；预处理完成的分片进入 GPU 队列，最终汇总结果。先实行 GPU 独占槽位，避免把资源声明当作显存隔离保证。

两台 CPU 资源可以由一台独立 CPU 电脑与 GPU 电脑上的独立 CPU 槽提供，必须分别计量并控制争用。若演示两台独立电脑故障转移，则需实际提供两台可替代设备。

**退出条件：** 同一批任务的不同分片实际重叠运行；GPU 步骤有模型输出、设备与后端记录；模型不兼容或显存不足时显示具体阻塞原因；新设备校准完成后自动进入候选集；链路过期后能重新测量，恢复合法调度。

### M4 团队规则与设备主人保护

在设备选择之前增加团队任务队列，支持按成员和任务优先级分配。实现“B 优先、空闲可借用”，并加入基本的等待补偿或保障机会，避免普通成员无限等待。

定义清晰的让出语义：B 提交后停止向借用者派发新 GPU 分片，已运行分片在安全边界完成或停止，然后分配给 B。长任务需先划分有界分片；不能仅调整优先级字段就宣称已经抢占。

设备主人暂停采用“停止新增并排空”；另提供明确的强制停止操作及影响提示。先在确定支持的平台落实空闲检测和资源限制，无法强制约束的指标不得显示为已兑现的硬额度。对手机落实可测的充电、电量、温度和共享状态检查。

**退出条件：** A 正在借用 GPU 时，B 的任务在约定分片边界获得执行机会；控制台显示规则、等待原因和实际让出时间；主人暂停优先于团队安排；普通成员无法改策略；成员被移除后，其待执行工作和凭据按规则失效。

### M5 故障恢复与一致结算

对每个分片维护独立尝试和租约状态，设备失联后重新安排可重做的纯计算任务。保留已提交结果，对旧设备迟到回执进行隔离；停止请求未确认时，不能把原物理槽位显示为空闲。

批量图片采用分片级重做，不承诺恢复任意模型的中间状态。通用恢复流程区分“继续、重做、等待替代设备、人工处理”。取消和负责人撤销权限时，不应通过重试重新执行已禁止的工作。

用量按实际执行尝试记录，包含失败和重试消耗；任务完成数按最终提交结果去重。共享在线时长、CPU 槽秒、GPU 执行秒分别统计，不能将它们混称为硬件核心利用率。

**退出条件：** 主动暂停和强制断网两种情况均有真实演练；剩余分片转移，已完成分片不重复交付；协调者重启后恢复对账；没有替代 GPU 时显示等待，不伪装成功；取消后的迟到结果不发布。

### M6 控制台整合与路演验收

整合空间总览、成员、设备、任务图、分片进度、规则、结果及贡献视图。事件展示包含状态、时间和可理解的原因；断线重连通过快照和事件序号校正，避免界面与实际执行脱节。

完成独立手机任务入口和电脑控制台的交互打磨，打包设备接入流程，准备固定测试素材与运行前检查。至少一个完整流程在全新空间中执行，避免依赖开发者预先写入的任务与权限数据。

**退出条件：** 九步路演脚本连续完整演练三次；每次有真实执行、规则变化、设备退出、结果及审计记录；再完成一次重启恢复和一次越权访问检查。演练次数是交付门槛，不是可用性统计保证。

## 六 开发顺序与工作分工

主依赖为 `M0 → M1 → M2 → M3 → M4 → M5 → M6`。GPU 可行性验证在 M0 提前开展，恢复和授权语义在 M1、M2 就确定，M5 再完成故障场景，避免末期返工。

人员条件允许时，可按以下工作流分工；它们是职责划分，不假设已有四名开发者。

| 工作流 | 主要交付 | 依赖 |
|---|---|---|
| 空间与任务服务 | 成员、邀请、权限、任务状态、队列、文件授权、审计 | M0 契约；与客户端同步联调 |
| 设备与执行能力 | PC 代理、手机执行接入、GPU 能力、设备保护、测量与验证 | M0 硬件路径及接入协议 |
| 手机与控制台 | 创建加入、设备共享、任务提交、进度结果、规则与贡献 | M0 状态契约；从 M1 开始逐步接真实接口 |
| 集成与验收 | 固定任务包、权限测试、断线恢复、现场脚本、测量记录 | 从 M2 起持续验证每个闭环 |

如果只有两名开发者，可先按“空间任务及控制台”和“设备执行及手机端”分工，再根据现有技能调整。工期应在 M0 硬件验证和 M2 首个闭环后估算，不用测试通过数量推算开发完成比例。

最先交付的三个可审查增量：

1. 确定通用任务契约，跑通真实 GPU 固定输入，建立新空间入口骨架。
2. 完成两个独立账号加入同一空间、绑定设备、暂停共享和权限隔离。
3. 手机提交非购物任务，CPU 执行并持久化结果；随后以相同接口接入 GPU 和第二模板。

每个增量包含与改动相符的自动检查和实际操作说明。已有 326 项测试作为回归基线，新增测试聚焦跨成员授权、状态竞争、资源争用、恢复与结果正确性。

## 七 国赛脚本与验收映射

主故事使用通用视觉素材，成员 A 从手机提交批量任务，成员 B 获得 GPU 优先保障。两台具备 CPU 能力的设备和一台具备 GPU 能力的设备参与；其中 GPU 电脑可同时提供受限 CPU 槽。手机作为真实入口，轻量计算贡献按真机验证结果加入，不用虚构手机参与率。

| 演示步骤 | 观众看到的动作与结果 | 对应里程碑 | 验收证据 |
|---|---|---|---|
| 创建空间 | 负责人创建空间并展示二维码 | M1 | 新空间与有效邀请 |
| 成员及设备加入 | 独立账号扫码，设备卡片出现并变为就绪 | M1、M3 | 成员身份、设备心跳、能力验证结果 |
| 设置共享规则 | 主人设置共享，负责人指定 B 优先 | M4 | 策略记录及设备端实际限制 |
| 手机提交任务 | A 上传素材并提交 | M2 | 真实输入、任务记录及提交者 |
| 自动协同 | 两台 CPU 处理分片，GPU 接力，页面显示流转 | M3 | 不同设备的执行时间区间和阶段输出 |
| B 插入紧急任务 | 借用分片在边界让出，B 开始执行 | M4 | 入队、让出、开始时间与原因 |
| 设备退出 | 暂停或断开一台 CPU 设备，剩余工作转移 | M5 | 失联检测、旧尝试状态、新执行设备 |
| 结果回到手机 | A 收到状态通知并查看汇总 | M2、M6 | 最终结果、实际内容及下载授权 |
| 查看贡献 | 展示成员分工、资源消耗和管理记录 | M5、M6 | 来自真实尝试的计量与审计 |

第二模板在彩排验收中必须通过，可在路演中用短演示或任务列表展示。它应复用同一空间、队列、权限、文件和结果接口，不通过另写一套服务证明“通用”。

## 八 质量与现场可靠性要求

性能对比在相同素材、模型、质量标准和授权设备集合下进行。分别比较固定可行设备组合、简单队列、Harmony 策略；涉及 GPU 必需能力时，不能拿无法完成任务的纯 CPU 路径作速度基线。记录总完成时间、成员等待时间、传输量、失败重做量及对设备主人工作的影响，冷热启动分别展示。

界面区分预计值和实测值，无足够数据时显示“估计中”或范围；不能用进度动画代替执行反馈。小样本展示逐次结果，不预先承诺提速比例。

协调服务可部署到已有独立 Harmony Railway 项目，用户设备承担 CPU/GPU 工作。部署内容包括任务状态与文件的持久保存、设备连接、访问控制和断线恢复验收；是否需要具体托管功能，在部署阶段核实。不要将已创建空项目视为服务已部署。

路演场地需提前验证网络、登录、设备连接和文件访问。模型和验证素材提前准备，避免现场下载。可准备预先验证的局域网协调模式作为备用部署，复用同一产品与任务协议；现场切换应停止旧会话并从清晰状态重新演示，不承诺云端任务无缝迁移。录屏只作为明确标注的备用说明。

仍待确定的输入：决赛日期、可投入人数、手机系统与型号、电脑系统、GPU 型号与显存、现场网络条件。这些输入决定排期与模型选择，不改变团队共享算力空间的产品主线。
