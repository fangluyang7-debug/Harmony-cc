## 2026-11-07 三设备 CPU 演示调整

用户确认当前设备为 Windows 电脑、鸿蒙电脑和鸿蒙手机，Windows 无独立显卡，本轮暂停 CUDA 图像检索。工作分支为 `codex/real-device-acceptance`。沿用局域网协调者、统一 SDK 派发、能力准入、真实结果与追踪要求，本轮演示任务改为批量文档分析。下面的原图像方案保留供后续实施。

Windows 同时运行协调者和 PC 代理，两台鸿蒙设备运行原生贡献代理。入组按配对凭据验证身份，再根据系统能力和实测资源准入，不设置型号白名单。鸿蒙电脑按 `2in1` 声明支持范围；系统版本、所需 API、签名、前后台与网络仍须实际检查。[华为设备类型说明](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/module-configuration-file/)

1. 按 [局域网启动说明](../../scheduler-v2/LOCAL-COORDINATOR-20261031.md) 启动 Windows 协调者。在控制台创建专用空间，为每台设备生成各自的接入邀请。页面中的配对 JSON 或下载的 invitation.json 已包含贡献额度，复制全文到鸿蒙代理的配对页面。Windows 按页面命令使用该邀请。每份设备邀请只供对应设备使用，成员邀请码用于账号入组。
2. 两台鸿蒙设备安装相同版本的独立代理包。有线连接用于安装和诊断；控制与数据传输使用三端可互通的局域网地址。保持原生代理前台，等待能力校准完成，核对三个实际设备及各自的 text.count.v1 目标。当前手机/鸿蒙电脑的扫码功能仍待设备验证，本轮使用配对密钥 JSON 路径。
3. Windows 注册独立来源 App。使用 `services/pc-agent/dist/app-register-main.js <agent.json> <policy.json> <app.json>`，policy 的 allowedContracts 包含 text.count.v1，maxConcurrent 至少为 3；其他额度字段参照既有 App 注册配置。凭据文件留在测试机。
4. 从调度盘/空间设备快照取得三个真实的执行 targetId。执行 `node scripts/prepare-document-demo.cjs .test/document-demo <Windows目标> <鸿蒙电脑目标> <手机目标>`，生成 12 份不同长度的合成文档和独立算术答案。这是明确标注的演示数据，可替换为有独立正确答案的真实文档。
5. 执行 `node scripts/compare-team-execution.cjs <app.json> .test/document-demo/workload.json .test/document-comparison.json`。三个固定目标各自完成同一批文档，团队模式由规划器自动选址；所有模式并发数均为 3，轮换执行顺序，重复 3 轮。输入、参数、预算、源 App 和结果检查保持一致。报告不保存配对凭据或文档正文。
6. 比较每轮全部结果返回的批次墙钟时长，使用中位数，与最快单设备模式比较。每条结果保存实际 deviceId、targetId、traceId、摘要和耗时。失败停止后续批次，已有任务依据 jobId 对账；不自动重提交未知投递。只有团队至少实际使用两台设备、所有结果正确且比最快单设备更快时报告 MEASURED_SPEEDUP。若团队只选一台，显示 SINGLE_DEVICE_SELECTED；较慢显示 NO_SPEEDUP。三台同时计算并非每个任务最优，需要在现场记录参与设备和瓶颈。

计时边界为 SDK 注册输入至完整结果返回，包含传输和轮询。固定目标模式也经过协调者，因此这是协作系统内的单设备对照，不等同于零调度开销的原生本地程序。当前工具记录性能数据，调度盘展示实际任务去向和轨迹；专门的演示排行榜尚未实现。禁止凭本机逻辑代理测试承诺三台物理设备加速。未达加速条件时保留结果，再针对传输量、任务粒度和设备占用调整并复测。

正式基线仍为 API 22。本轮核对两台物理设备实际 API 均为 24，使用独立 API 24 工程完成签名安装和测试；正式 API 22 编译与真机运行继续待验。安装证据与基线差异见上述实测报告。
