# AI 任务语义调度件工作要求

## 1. 文档目的

本文定义鸿蒙手机端 AI 资源感知调度中间件的后续工作要求。目标不是重复操作系统的线程调度，而是在应用可见的业务语义层，决定 AI 工作是否执行、何时执行、以何种质量执行，以及何时暂停、取消、合并或丢弃结果。

适用范围为接入本调度 SDK 的应用内 AI 工作负载。调度件不修改鸿蒙内核调度器，不越过应用沙箱自动发现其他应用的 AI 操作。

## 2. 当前能力与定位

当前项目已具备基础应用内调度能力：

- 以 `TaskRequest` 提交前台实时、用户触发、后台批处理任务。
- 根据电量、温度、内存、队列深度和近期时延生成执行计划。
- 输出模型档位、CPU 线程数、后端偏好、队列动作及可解释原因码。
- 提供优先级队列、等待老化、排队取消和后台任务暂停接口。
- 使用 MindSpore Lite 在端侧执行文本 Embedding 推理，并完成本地商品向量检索。

当前限制也必须如实保留：

- App 需要手动声明任务类型、能力名、时延预算等信息；调度件不能自动理解任意 App 的 AI 操作。
- `metadata` 尚未进入任务画像和策略评估。
- 优先级目前由任务类型硬编码映射，尚未形成动态业务效用评估。
- 模型档位当前主要对应 256/64/16 维检索，尚未验证多独立模型、NPU 或 GPU 的实际切换。
- 后台任务尚未完成真正的检查点式暂停、恢复和任务合并。

## 3. 设计原则

1. 调度所需信息应完整，但不要求上传全部原始业务数据。
2. 系统状态和计算成本由 SDK 自动采集；用户价值和业务约束由 App 显式表达。
3. 安全、隐私、质量下限和设备保护属于硬约束，不交给学习模型或云端模型猜测。
4. 实时路径不依赖云端大模型决策；云端能力只可用于离线分析、模板建议或非实时辅助。
5. 信息不足的任务按保守策略执行，不得伪装为已被充分理解的任务。

## 4. SDK 接入要求：统一入口与三层任务契约

不得为每一种 AI 操作设计彼此孤立的大量接口。应提供统一 `SchedulerClient`，通过任务模板、任务实例和运行信号三层组合表达业务语义。

### 4.1 任务模板 TaskTemplate

App 在初始化时注册稳定的能力画像，一次注册，多次复用。模板至少包含：

- `capability`：稳定能力标识，例如 `image_product_search`。
- `workflow`：由多个 AI 节点组成的任务图或顺序关系。
- `qualityLevels`：质量/资源降级阶梯，例如完整模型、轻量模型、规则兜底。
- `interruptibility`：不可中断、可取消重启、可检查点恢复。
- `duplicatePolicy`：保留全部、合并同类、仅保留最新任务。
- `privacyPolicy`：仅端侧、允许脱敏上云、允许远端处理。
- `dependencies`：前置节点、后置节点及失败处理规则。
- `resourceHints`：模型版本、输入规模范围、预计内存或候选集规模。

### 4.2 任务实例 TaskContext

App 每次发起任务时传递本次实际约束，至少包含：

- `deadlineMs`：最晚可接受完成时间。
- `freshnessMs`：结果失去价值的时间窗口。
- `userVisible` 与 `userWaiting`：是否直接影响当前用户界面。
- `accuracyFloor`：本次任务可接受的最低质量档位。
- `inputShape`、`inputTokens`、`candidateCount` 或等价的输入规模指标。
- `requestReplaced`：是否已被后续输入替代。
- 任务关联的工作流、父任务或依赖任务标识。

### 4.3 运行信号与遥测 TaskSignal / TaskTelemetry

SDK 与执行器自动采集以下信息：

- 模型版本、模型大小、支持的后端和实际线程数。
- 输入 token 数、图像尺寸、batch 大小、候选集规模。
- 排队时延、执行时延、峰值内存、后端、成功、失败、超时和取消原因。
- 可公开获取的设备温度、电量、内存、应用前后台状态。

App 应补充只有业务层才知道的事件：

- 用户离开页面、继续输入或明确取消。
- 结果已经展示、被消费、被忽略或被后续任务替代。
- 本次操作是否进入高质量/不可降级模式。

## 5. 工作流与执行器要求

调度单位不应只是一条孤立模型调用。SDK 必须支持以任务图表达复合 AI 操作，例如：

```text
图像商品搜索
  -> 图像预处理
  -> 主体检测
  -> 图像向量提取
  -> 向量检索
  -> 结果重排
```

每个节点必须能够声明依赖关系、可取消性、检查点能力和降级方案。调度件至少应支持：

- 工作流级取消：用户离开或请求被替代时取消不再有价值的节点。
- 同类合并：连续搜索、推荐预取等任务按键合并或只保留最新实例。
- 过期丢弃：超过 `freshnessMs` 的结果不再占用后续渲染和重排资源。
- 协作式检查点：后台任务在安全点保存进度、让出资源并在合适时恢复。
- 任务出队前重评估：排队期间设备状态变化后必须重新生成执行计划。

## 6. 策略评估要求

### 6.1 不再以固定优先级作为最终决策

`FOREGROUND_REALTIME`、`USER_INITIATED`、`BACKGROUND_BATCH` 仅可作为初始先验，不能直接等价于最终优先级。最终调度应分解为以下独立维度：

- 业务重要度：任务失败或降级的业务影响。
- 截止时间压力：预计完成时间与 `deadlineMs` 的差值。
- 结果新鲜度：结果到达时是否仍具有价值。
- 用户可见性与等待状态：用户是否被当前任务阻塞。
- 质量底线与降级阶梯：允许牺牲多少效果以换取时延或功耗。
- 可取消性、可合并性和依赖阻塞关系。
- 预测资源成本：时延、内存、能耗和热风险。
- 当前设备余量：温度、电量、内存、队列和近期性能反馈。

### 6.2 决策顺序

策略必须按以下顺序工作：

1. 校验硬约束：热保护、低电量、内存临界、隐私、质量底线和网络策略。
2. 预测候选方案的时延、能耗、内存及截止时间违约概率。
3. 按业务效用、截止时间压力和设备风险排序，选择执行、排队、合并、暂停、降级、取消或拒绝。
4. 在执行完成后，以实际时延、资源消耗和结果消费情况校正预测。
5. 当预测置信度不足时采用保守计划，并记录原因。

### 6.3 可学习但必须可控

允许用端侧轻量模型学习资源预测，例如预测完成概率、时延、热风险和结果被消费概率。其输入应为结构化遥测与任务画像，输出应可校准、可解释。

不得让云端大模型直接进入 80ms、100ms 等实时调度闭环。云端大模型可用于：

- 根据开发者业务描述生成初版任务模板建议。
- 离线分析运行日志、发现异常画像和提出参数建议。
- 对未知的低实时性任务提供辅助分类建议。

云端建议必须经过本地硬约束校验，并可被 App 或调度策略拒绝。

## 7. MindSpore Lite 的职责

MindSpore Lite 是端侧模型推理运行时，不是本调度件的策略模型。当前项目中的 `.ms` 神经模型负责把文本编码为 Embedding 向量，并对本地商品向量进行检索。

MindSpore Lite 推理、向量检索和索引更新都属于需要被调度的 AI 工作负载。调度件负责为它们选择执行时机、质量档位、线程数、后端、队列动作与取消策略；模型运行时负责实际加载权重与执行推理。

## 8. 最低验收标准

- 提供统一 SDK 入口，并实现模板、实例、信号三层任务契约。
- 至少在购物搜索演示中实现一个多节点任务图。
- 支持用户输入替代时取消旧任务、保留最新任务和过期结果丢弃。
- 支持后台任务的真实分块检查点、暂停和恢复。
- 对排队任务在出队前重新评估设备状态和执行计划。
- 不再仅依据三类 `taskType` 固定优先级；至少纳入截止时间、新鲜度、用户等待状态和预测成本。
- 记录预测值与实际值，输出可审计的决策原因和评估指标。
- 在真实手机上验证至少三类场景：实时交互、用户主动搜索、后台预热。

## 9. 术语边界

本项目的创新点是应用可见的 AI 任务语义调度，而非取代操作系统调度器。操作系统决定线程和进程获得底层计算资源；本调度件决定业务 AI 工作是否仍值得执行、以何种质量执行、何时让出资源，以及结果是否仍值得交付给用户。
