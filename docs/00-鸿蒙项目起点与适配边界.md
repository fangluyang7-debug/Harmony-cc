# 鸿蒙项目起点与适配边界

> 历史记录：本文保存 2026-09-18 从此芯项目分离代码时的方案。产品定位、原生实现来源与必做范围已由 [2026-09-19 作品说明与开发基线](02-作品说明与开发基线-鸿蒙手机资源感知调度中间件.md) 替代；下文“待定”和“沿用方向”不代表当前决策。

日期：2026-09-18。比赛、目标设备、HarmonyOS／SDK 版本：待定。当前成果是独立代码起点，不是已完成的鸿蒙应用。

## 1. 沿用的产品方向

保留通用端云 Agent Runtime 与购物参考插件，沿用“从验证过的执行流程提取可复用技能”的设计方向。技能 Compiler／Validator／Registry／Resolver 当前仍属待实现方案；不能因迁移设计文档而宣称已开发。

## 2. 当前可复用与待适配部分

| 部分 | 当前处理 | 下一步 |
|---|---|---|
| Runtime 契约、工具注册、调度、事件 | 复制 NestJS 实现用于桌面／服务端 | 完成真实执行闭环，再评估原生迁移边界 |
| 购物模块、数据库 schema 与迁移 | 复制代码，未复制数据库或商品样例 | 独立初始化并导入确认来源的数据 |
| Web 控制台 | 复制并改为鸿蒙开发入口，使用独立端口 | 作为调试和参考界面，不冒充原生 UI |
| Python 图像 Worker | 复制接口与代码，未复制模型 | 用实际机器验证；鸿蒙端另选适配路径 |
| HarmonyOS Adapter | 保留原有不可用占位实现 | 确定 SDK 后实现真实设备能力和通信 |
| 原生应用 | 预留 `apps/harmony` | DevEco／ArkTS／ArkUI 工程及真机联调 |
| P1／NOE 内容 | 设计参考快照中保留来源 | 不作为鸿蒙硬件能力或赛事要求 |

当前部署关系：

```text
Web 调试端（现在） / HarmonyOS 原生端（待开发）
                    ↓
独立 NestJS 开发／服务端：Runtime + 购物模块 + 独立数据库
                    ↓
可选图像 Worker / 实际配置的云模型与数据源
```

这只是迁移阶段的联调结构。比赛若要求鸿蒙端主控、离线技能或端侧推理，必须把相应能力移植并在真机验证；不能仅用原生页面调用 Node 服务就宣布满足这些要求。

## 3. 适配顺序

1. 确认赛事规则、参赛产品形态、设备和 SDK；独立核对参赛材料与差异化要求。
2. 安装本目录依赖，构建服务与调试端，明确哪些接口已可用、哪些仍被资源阻断。
3. 创建原生工程，先跑通图片／文本输入、API 通信、状态展示与异常反馈。
4. 按目标设备决定本地推理、状态持久化及工具执行桥接，保持无法观测的能力为未知。
5. 开发并验证技能编译闭环，使用新输入和失效反例评估，再形成鸿蒙版本设计与演示。

先做可验证主链路；跨设备协同、卡片、更多设备形态等能力是否纳入，待赛题与团队资源明确后决定。
