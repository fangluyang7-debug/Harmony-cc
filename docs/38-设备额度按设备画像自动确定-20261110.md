# 38 · 设备额度按设备画像自动确定（2026-11-10）

## 问题

桌面调度中心生成设备邀请时，写死了 2 个 CPU 槽位、1 GiB 运行内存（`apps/runtime-desktop/desktop.js`）。
鸿蒙调度件把邀请里的额度当作上限显示，于是任何手机配对后都只看到 1024 MiB，与真机实际的运行内存无关。
鸿蒙端早已通过 `hidebug.getSystemMemInfo()` 读到总运行内存和可用内存，但这些测量值从未回传给协调中心，也没有参与额度决定。

注意两种容量的区别：

- **存储空间**（例如 1 TB）：存照片、视频、安装应用，不参与任务执行，不计入额度。
- **运行内存（RAM）**：任务执行真正占用的资源，额度以此为准。

## 方案

额度分两步确定：

1. **邀请阶段（临时额度）**。协调中心仍在邀请里给出 2 槽位 / 1 GiB，但把设备设置标记为 `capacityMode: 'auto'`。
   旧版调度件只认邀请里的额度，所以邀请结构保持不变。
2. **连接后（自动额度）**。调度件每次轮询 `/v2/device-settings` 时附带本机测量值
   `measured: { cpuThreads, totalMemoryBytes }`（未知的填 `null`）。协调中心据此推导上限、重新确认物理预算、
   写回设备设置，并在同一响应里返回新额度；调度件采纳为新的上限并持久化。

推导规则（`services/coordinator/src/spaces.ts` 的 `autoContribution`）：

| 项目 | 规则 |
| --- | --- |
| 预留内存 | max(1 GiB, 总运行内存的 25%)，留给系统与日常应用 |
| 内存上限 | 总运行内存 − 预留，向下取整到 64 MiB，下限 64 MiB，上限 1 TiB |
| CPU 槽位 | 硬件线程数的一半，至少 1，最多 64；未上报则保留当前值 |

示例：8 GiB 手机 → 预留 2 GiB，可贡献 6 GiB；2 GiB 设备 → 预留 1 GiB，可贡献 1 GiB。

运行时仍按原有逻辑动态收缩：鸿蒙端 `limits()` 取 `min(上限, 已占用 + max(0, 当前可用内存 − 预留))`，
所以额度是上限，不是承诺；可用内存不足时只会贡献更少。

缩小上限时若已有预留超出新上限（`BUDGET_RECONCILIATION_REQUIRED`），协调中心保留旧上限，待预留结清后下一次轮询再收缩。

## 改动位置

- 协调中心：`spaces.ts`（`capacityMode`、`measuredCapacity`、`autoContribution`、`deviceSettings` 接收测量值）、
  `app.ts`（`/v2/device-settings` 读取 `measured`）、`allotments.ts`（`budget()` 读回已有绑定）。
- 鸿蒙调度件：`apps/harmony/scheduler/.../NativeAgent.ets` 每次 tick 上报 `totalRam`，`adoptCeiling` 采纳并持久化新上限
  （用户曾手动调低的贡献只做钳制，不会被抬高）；`Index.ets` 显示本机运行内存与说明。
  鸿蒙目前未上报 CPU 线程数（系统 API 不提供），CPU 槽位保留邀请值。
- Windows 调度件：`services/pc-agent/src/host.ts` 上报 `os.availableParallelism()` / `os.totalmem()`，采纳自动上限后
  通过 `host-main.ts` 回写 `contribution.json`，桌面「贡献上限」面板随之更新。
- 桌面与网页：`desktop.js` 邀请默认 `capacityMode: 'auto'`；`team-space-web/app.js` 新增「额度方式」选择（自动 / 固定）。

## 验证

- `services/coordinator/test/spaces.test.cjs`「automatic capacity follows the hardware a paired device reports」：
  临时额度、无测量不变、非法测量（CPU 为 0、带存储字段）被拒、8 GiB / 2 GiB / 512 MiB 三档推导、幂等、固定额度设备忽略测量。
- 真机：手机配对后，调度件「贡献上限」页应显示本机运行内存，并在首次连接后把 1024 MiB 替换为按上表推导的值。
