## 一、问题一解析：「接通程度不一致」与「可信 CPU Worker 路径」是什么意思？

### 1.1 原文含义澄清

> "当前并没有一个覆盖所有设备、所有任务、所有硬件的统一调度闭环。可复用算法、业务接入和演示路径已存在，但接通程度不一致。尤其需要区分可信 CPU Worker 路径与云端配对手机路径。"

**「接通程度不一致」的具体含义：**

当前项目中存在三条执行路径，它们的完整程度并不相同：

| 路径 | 涉及代码 | 接通程度 |
|---|---|---|
| ① 手机本地 HAR 路径 | `apps/harmony/scheduler/` | 调度逻辑完整，但尚未完整迁移到当前仓，且部分执行器（图片、详情重排）只返回占位值而非真实计算 |
| ② 可信 CPU Worker 路径 | `services/device-worker/` + `services/api-server/src/core/runtime/device-dispatch.service.ts` | 协议完整（descriptor→lease→execute→receipt），真实硬件上有 image.crop.v1 能力，但目前仅该一个能力，且**与当前购物工作流的真实集成存在写死耦合**（见问题二、三） |
| ③ 云端 Zeabur 工作流路径 | `services/api-server/` + `ShoppingTaskService` | 购物工作流通过该路径在 Zeabur 云端执行，是当前唯一真实跑通全链路的路径，但它与业务（购物）强绑定 |

"接通程度不一致"的意思是：这三条路径的实现深度差异很大——路径③是真实跑通的，路径②协议层完整但任务类型单一、与上层调度未完全打通，路径①本地调度逻辑最完整但与另外两条的数据/控制面尚未统一。

**「可信 CPU Worker 路径」是什么：**

指部署在 PC 或边缘主机上的 `device-worker` 服务。它：
- 通过 `/v1/descriptor` 汇报自身能力（如 `image.crop.v1`）、可用槽位和内存
- 通过 `LeaseManager` 进行原子准入（槽位 + 内存 + fencing token）
- 由云端 `DeviceDispatchService` 在发起前通过 `WorkflowPlacementPlanner` 比较「本机云端执行」与「派发到 Worker 执行」的端到端成本
- 要求持有服务端颁发的 Bearer Token，这就是"可信"的含义

它的问题在于：目前只有 `image.crop.v1` 一种能力真实接入，且这个能力是专门为购物图片裁剪服务的（见问题三根因）。

## 二、问题二解析：「正式购物入口固定使用云端执行器」违背解耦初衷

### 2.1 根因定位

查看 `apps/harmony/entry/src/main/ets/services/ShoppingTaskService.ets`，关键问题在 `template` 字段的硬编码：

```typescript
// 问题代码：写死了 inferenceLocation = REMOTE_CLOUD，写死了 provider = 'cloud-shopping-api'
private readonly template: TaskTemplate = {
  capability: 'product_search',
  inferenceLocation: InferenceLocation.REMOTE_CLOUD,
  remoteOptions: { provider: 'cloud-shopping-api', allowLocalFallback: false },
  // ...
};
```

这导致：
1. 所有通过 `ShoppingTaskService` 提交的任务，不管当前设备和网络状况如何，全部走云端
2. `allowLocalFallback: false` 明确关闭了本地回退
3. 这个 Service 本身的名字就叫 `Shopping`，天然和业务耦合

但你设计这个中间件的初衷是：**调度件不感知具体业务是什么，只负责把 AI 任务画像和设备/硬件画像做匹配，然后分发执行**。

### 2.2 改造方案

**原则：中间件层完全不出现任何业务词汇（shopping / product / cart 等），业务通过「接入契约」声明需求，调度件通过「画像匹配」决策。**

#### Step A：从 ShoppingTaskService 中剥离调度决策

`ShoppingTaskService` 不应该自己决定 `inferenceLocation`，应该改为：只声明任务的**能力需求、质量要求、隐私约束和截止时间**，由调度件根据当前设备画像决定在哪里执行。

修改前（当前）：
```typescript
// ShoppingTaskService 自己写死执行位置
inferenceLocation: InferenceLocation.REMOTE_CLOUD,
```

修改后（目标）：
```typescript
// ShoppingTaskService 只声明"我需要什么能力、什么质量、什么隐私约束"
// 不声明"我要在哪里执行"
const taskHint: AppTaskHint = {
  capability: 'product_search',
  qualityFloor: 0.8,
  privacyPolicy: PrivacyPolicy.REMOTE_ALLOWED,
  deadlineMs: 15000,
  // 不包含 inferenceLocation / provider
};
// 执行位置由 TaskProfileResolver + GlobalScheduler 决定
```

#### Step B：新增 AppTaskHint 接口（接入契约）

在 `contracts/scheduling/v1/` 新增或扩展接口：

```typescript
// 这是 App 接入时声明的最小 Hint，不含任何执行决策
export interface AppTaskHint {
  capability: string;              // 需要什么算法能力（app 侧声明）
  inputType: 'text' | 'image' | 'audio' | 'structured';
  estimatedInputBytes?: number;
  qualityFloor: number;            // 最低质量要求（0~1）
  privacyPolicy: PrivacyPolicy;    // 隐私约束
  deadlineMs: number;              // 用户可接受的最大延迟
  interruptibility: Interruptibility;
  userVisible: boolean;            // 是否是用户等待的前台任务
}
```

`TaskProfileResolver` 拿到这个 Hint 后，结合已注册执行器的能力声明、当前设备画像、历史样本，完整填充 `ResolvedTaskProfile`（含 `inferenceLocation` 的建议，但这是 Resolver 的输出，不是 App 的输入）。

## 三、问题三解析：`image.crop.v1` 是写死的还是从 App 读取的？

### 3.1 根因定位

查看 `services/api-server/src/core/runtime/device-dispatch.service.ts`：

```typescript
// 问题代码：crop 方法被直接定义为服务固定方法
async crop<T>(bytes: Buffer, parameters: {...}, local: ()=>Promise<T>): Promise<QueryImageCropResult> {
  // ...
  const nodes = [{
    id: 'crop',
    capability: 'image.crop.v1',   // ← 写死的 capability
    // ...
  }];
}
```

`image.crop.v1` 是在 `DeviceDispatchService` 的 `crop()` 方法里**直接硬编码**的 capability 名，不是从接入的 App 画像中读取的。

更进一步，`QueryImageCropResult` 接口也是 shopping 模块专用的（`query-image-content-adapter.interface`），这让 `DeviceDispatchService` 直接依赖了购物业务类型，彻底破坏了底层调度件应有的业务无关性。

### 3.2 根本问题

`DeviceDispatchService.crop()` 这个方法根本不应该叫 `crop`，也不应该存在这样一个业务专用入口。正确的做法是：

**Worker 节点汇报它有 `image.crop.v1` 这个能力 → `WorkflowPlacementPlanner` 收到 App 声明的某个工作流 Node 需要 `image.crop.v1` 能力 → Planner 将该 Node 分配到具有该能力的 Worker**

这整个过程不需要在 `DeviceDispatchService` 里写一个叫 `crop()` 的专用方法。

### 3.3 改造方案

#### Step A：消除 DeviceDispatchService 中的业务专用方法

将 `DeviceDispatchService.crop()` 替换为通用的 `dispatch()` 方法：

```typescript
// 修改前：业务专用
async crop(bytes: Buffer, parameters: CropParams, local: ()=>Promise<CropResult>): Promise<CropResult>

// 修改后：通用 dispatch，能力类型由调用方声明
async dispatch(request: GenericDispatchRequest): Promise<GenericDispatchResult>

// GenericDispatchRequest 结构：
interface GenericDispatchRequest {
  workflowId: string;
  nodeId: string;
  capability: string;       // 由上层传入，不写死
  inputArtifactRef: ArtifactRef;
  parameters: Record<string, unknown>;
  qualityRequirements: QualityRequirements;
  deadline: number;
  localFallback: () => Promise<GenericDispatchResult>;
}
```

#### Step B：Device Worker 能力注册协议泛化

当前 `device-worker/lease-manager.mjs` 只实现了 `image.crop.v1`。需要将其改造为：
- Worker 在启动时通过配置文件声明自己有哪些 capability
- `/v1/descriptor` 返回这些 capability 列表
- 对每个 capability，声明其输入/输出 schema、内存需求、典型耗时
- `DeviceDispatchService` 仅通过 Planner 的 capability 匹配来选择 Worker，不在代码里写死

## 四、问题四解析：从演示机制到完整调控系统的架构重构

这是最核心的一个问题，涉及整个系统的层次设计。你的目标是：

> **云端宏观调控（读取所有接入设备画像）→ 选择设备 → 每个设备内部微观调控（硬件资源选择）→ 接入的 App 通过画像声明 AI 任务需求 → 统一调度算法完成全局分配**

### 4.1 系统分层重新定义

下面是对原项目的系统分层重新定义，这是整个改造的出发点：

```
┌─────────────────────────────────────────────────────────────────┐
│ 层 0：外部 App 接入层（业务无关，通过画像声明）                   │
│  - 任何 App 在接入前/接入时生成「AI任务画像」                    │
│  - 声明：需要什么能力、质量下限、隐私要求、截止时间              │
│  - 不声明：在哪台设备执行、用哪个硬件、用几个线程               │
└──────────────────────────────┬──────────────────────────────────┘
                               │ AppTaskHint（标准化接入契约）
┌──────────────────────────────▼──────────────────────────────────┐
│ 层 1：云端全局调度层（宏观，决定任务去哪台设备）                  │
│  - GlobalScheduler / WorkflowPlacementPlanner                   │
│  - 维护「多设备画像注册表」（每台接入设备的能力、资源、负载）    │
│  - 维护「链路画像」（设备间带宽、RTT）                          │
│  - 输入：AppTaskHint + 多设备画像 + 链路画像                    │
│  - 输出：PlacementDecision（分配给哪台设备的哪个执行器）         │
└──────────────────────────────┬──────────────────────────────────┘
                               │ PlacementDecision（含剩余预算）
┌──────────────────────────────▼──────────────────────────────────┐
│ 层 2：设备内微观调度层（本地，决定在设备内如何用硬件）           │
│  - 每台设备上的 LocalScheduler（手机用 HAR，Worker 用 Lease）   │
│  - 维护「本机硬件画像」（CPU/GPU/NPU 可用情况、热状态、内存）   │
│  - 输入：PlacementDecision + 本机实时硬件画像                   │
│  - 输出：ExecutionPlan（几个线程、哪个后端、分几块）            │
└──────────────────────────────┬──────────────────────────────────┘
                               │ ExecutionPlan
┌──────────────────────────────▼──────────────────────────────────┐
│ 层 3：执行器层（真实计算）                                        │
│  - MindSpore Lite CPU / TaskPool / CPU Worker / 云端执行器      │
│  - 执行完成后回传 ExecutionReceipt（实际耗时、配置、质量）      │
└─────────────────────────────────────────────────────────────────┘
                               │ ExecutionReceipt（双向反馈）
┌──────────────────────────────▼──────────────────────────────────┐
│ 层 4：双层反馈闭环（更新画像、校准成本模型）                      │
│  - 内层反馈：更新本机硬件画像和成本模型                         │
│  - 外层反馈：更新多设备画像和全局成本模型                       │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 设备画像注册机制（外层：云端宏观可见性）

**设计目标：外部硬件设备是可以自由插拔的，云端能实时感知接入设备的增减和状态变化。**

#### 4.2.1 设备画像结构

```typescript
// 推荐新增到 contracts/scheduling/v1/ 中
export interface DeviceProfile {
  // 设备身份（不可变）
  deviceId: string;                    // 全局唯一，由设备首次注册时生成
  instanceId: string;                  // 本次启动实例 ID（重启后更新）
  deviceType: 'phone' | 'pc' | 'edge-host' | 'cloud';
  
  // 静态能力（软件版本变更才更新，TTL 较长）
  capabilities: CapabilityDescriptor[]; // 每项能力的详情
  runtimeVersion: string;
  adapterVersion: string;
  trustedSince: number;                // 首次被信任的时间
  
  // 动态资源状态（高频更新，TTL 较短，例如 5s）
  availableSlots: number;
  availableMemoryBytes: number;
  cpuLoadPercent: number;
  thermalLevel: number;                // 0-3：COOL/WARM/HOT/CRITICAL
  batteryLevel: number | null;         // null 表示不适用（PC/服务器）
  isCharging: boolean | null;
  
  // 画像质量元数据
  observedAt: number;                  // 最后一次观测时间（单调时钟）
  ttlMs: number;                       // 超过 TTL 视为过期，降级或排除
  source: 'REAL' | 'MOCK';
}

export interface CapabilityDescriptor {
  id: string;                          // 如 'image.crop.v1', 'text.embed.v2'
  inputSchema: string;                 // JSON Schema ID
  outputSchema: string;
  supportedBackends: ('CPU' | 'GPU' | 'NPU')[];
  maxMemoryBytes: number;
  typicalLatencyMs: number;            // 来自实测，有样本后更新
  qualityVerified: boolean;
}
```

#### 4.2.2 设备注册与心跳协议

在 `services/api-server` 中新增 `DeviceRegistryService`：

```
设备启动 → POST /v1/devices/register (完整画像)
           ← { deviceId, sessionToken, refreshIntervalMs }

定期心跳 → PUT /v1/devices/{deviceId}/heartbeat (动态资源状态)
           ← { ok } 或 { deregister: true }

设备停止 → DELETE /v1/devices/{deviceId} (主动注销)

云端感知 → DeviceRegistryService.listActive() 返回当前在线设备列表
         → DeviceRegistryService.onDeviceJoin/onDeviceLeave 事件
```

这样云端就能实时感知「外部硬件可以自由插拔」的动态变化，而不是像当前 `RUNTIME_DEVICES_JSON` 那样通过环境变量静态配置。

#### 4.2.3 从静态配置到动态注册的迁移

当前问题：`DeviceDispatchService.devices()` 通过 `process.env.RUNTIME_DEVICES_JSON` 静态读取设备列表，每次修改都需要重启服务。

改造路径：
1. `RUNTIME_DEVICES_JSON` 保留作为「初始种子设备」（向后兼容）
2. 新增 `DeviceRegistryService` 维护动态注册表（内存 + 可选持久化）
3. `DeviceDispatchService` 改为从 `DeviceRegistryService.listActive()` 获取候选设备
4. 设备画像超过 TTL 自动降级为不可信（不会误用已下线设备的画像）

### 4.4 App 接入画像生成机制

**设计目标：外部 App 在接入前或接入时需要生成 AI 任务画像，标清楚 AI 任务的相关需求信息。**

#### 4.4.1 原项目的画像机制评估

原项目在 `contracts/scheduling/v1/` 中已有 `TaskTemplate`、`TaskContext`、`ExecutionProfile` 等概念，以及 `TaskProfileResolver` 的设计（文档 14 中提及）。这个方向是正确的。

**现有机制的问题：**
1. `TaskTemplate` 是在应用代码中手动填写的（如 `ShoppingTaskService` 中的 `private readonly template`），不是通过系统化的画像生成流程产生的
2. 画像中混入了执行决策（`inferenceLocation: REMOTE_CLOUD`），模糊了「需求声明」和「调度决策」的边界
3. 不同 App 接入时没有统一的接入规范和校验

#### 4.4.2 改造方案：标准化接入 SDK

新增 `SchedulerSDK.register()` 接口，App 接入时调用一次：

```typescript
// App 接入时（任何 App，不只是购物）
const sdk = new SchedulerSDK(runtime);

// 1. 注册该 App 需要用到的 AI 能力（每种能力一次，不是每次任务都填）
sdk.registerCapability({
  capabilityId: 'text.semantic_search',    // 能力ID，与执行器实现对应
  version: 'v1',
  inputType: 'text',
  qualityFloor: 0.75,
  privacyPolicy: PrivacyPolicy.REMOTE_ALLOWED,
  maxLatencyMs: 5000,
  // 不包含执行位置、线程数等调度决策
});

sdk.registerCapability({
  capabilityId: 'image.object_detect',
  version: 'v1',
  inputType: 'image',
  qualityFloor: 0.85,
  privacyPolicy: PrivacyPolicy.LOCAL_ONLY,  // 图片识别要求本地执行
  maxLatencyMs: 3000,
});

// 2. 提交任务时只传入「这次任务的具体输入」，不重复声明质量等约束
const handle = sdk.submit({
  capabilityId: 'text.semantic_search',
  input: { text: userQuery },
  userVisible: true,
  priority: TaskPriority.HIGH,
});
```

这套机制保证：
- 任何 App 都通过相同的 `registerCapability` + `submit` 接口接入
- 调度件从不感知 App 是购物 App、地图 App 还是其他 App
- `privacyPolicy` 等约束在能力注册时声明一次，不需要每次任务都传

### 4.5 调度算法应该宏微观分开还是汇总？

这是你第四个问题中最需要仔细考量的部分。

#### 4.5.1 结论：**必须分开，且原项目的「两级调度」设计本身是正确的**

原因分析：

**汇总所有信息在一起调度的问题：**
- 信息量爆炸：N 个设备 × M 种硬件配置 × K 个 App 任务 = 指数级搜索空间
- 时延不可接受：收集所有终端的实时状态需要网络往返，无法满足本地决策的毫秒级响应要求
- 单点故障：云端宕机时，所有本地决策都无法进行
- 隐私风险：把所有本地任务信息汇总到云端才能调度，违背了 `LOCAL_ONLY` 隐私约束

**两级分开调度的优势（原项目 doc 14 的核心设计正确）：**

| | 外层（宏观，云端）| 内层（微观，本地）|
|---|---|---|
| 决策频率 | 低频（任务开始时、阶段边界、设备掉线时）| 高频（每个任务入队、资源变化时）|
| 响应时间要求 | 100ms 级可接受 | 1ms~5ms（P95 目标）|
| 信息来源 | 各设备上报的画像摘要（不是原始数据）| 本机实时硬件状态 |
| 决策内容 | 这个任务去哪台设备？| 这个任务用几个线程、哪个后端、分几块？|
| 云端故障影响 | 无法做跨设备分配，但本地任务继续正常执行 | 完全不受影响 |

**但原项目目前两级之间的信息交互还不完整：**

当前云端 `WorkflowPlacementPlanner` 做决策时，缺少：
1. 实时的多设备画像数据（因为设备注册是静态配置的，见 4.2.3）
2. 各设备的内层调度状态（当前排队长度、最近任务耗时）

这些需要通过 4.2 节的设备画像注册机制补全。

#### 4.5.2 调度算法的具体分工建议

**外层宏观调度（在 `WorkflowPlacementPlanner` 中，已有基础，需要补全数据来源）：**

算法已完整实现有界束搜索（beam search），核心代价函数：

```
端到端成本 = 传输时间 + 目标排队时间 + 冷启动时间 + 计算时间 + 结果回传时间
```

当前缺口：传输时间 / 排队时间的数据来源不足（因为设备画像是静态的）。
改造后可以用动态设备画像中的 `estimatedAvailableMs` + `queuedAiTasks` 来估算排队时间。

**内层微观调度（在各终端的 LocalScheduler 中）：**

原项目 `ConstrainedPolicy` + `AdaptiveCostModel` + `TaskQueue` 已有良好基础。

当前缺口主要是：
1. `LocalHardwareProfile` 不完整（GPU/NPU 信息缺失）
2. 本机硬件画像没有周期性上报给外层（缺少画像回传机制）

## 六、关于调度算法的附加说明

### 6.1 原文档 14 的算法是否合理？

**结论：方向完全正确，核心公式合理，执行阶段可以直接使用。**

文档 14 提出的三个核心公式：

1. **单任务耗时**：`固定开销 + 输入规模相关开销 + 加载开销 + 档位切换开销`  
   ✅ 合理。EWMA 校准 + 保守先验是经典在线学习做法（参见 Clockwork OSDI 2020）

2. **并发干扰**：`预计并发耗时 = 预计独占耗时 × (1 + 干扰系数)`  
   ✅ 合理。但需要真机配对测量建立干扰系数表，不能估算

3. **边际收益**：`(预计关键路径缩短时间 − 切换成本) / 新增资源配额`  
   ✅ 合理。这是典型的资源效用函数

**当前未实现的关键部分（需要补充）：**

- 工作流关键路径计算（DAG 中从当前节点到终点的最长路径）还没有完整实现。`WorkflowPlanner.ets` 中只有基础框架。
- 干扰系数表没有真机数据，目前默认值是推测值，需要手机验收实验来校准。

### 6.2 宏观与微观算法是否需要分别实现？

**是的，需要分别实现，它们解决的是不同问题：**

- **宏观（外层）用 Beam Search 比较多设备方案**：当前 `WorkflowPlacementPlanner` 已实现（束宽 8，最多评估 16 个节点）。主要缺口是数据来源（设备画像动态化）。

- **微观（内层）用 ConstrainedPolicy + 优先队列**：当前 `ConstrainedPolicy` + `TaskQueue` 已有，主要缺口是硬件画像完整性和两槽并发的正确实现。

这两个算法 **不能合并成一个**，理由：
- 宏观算法需要考虑网络传输成本，微观算法不关心网络
- 微观算法需要毫秒级响应，宏观算法可以接受 100ms 级延迟
- 本地执行时（云端故障），内层仍需正常工作

## 七、执行顺序建议

建议执行 Agent 按以下顺序处理：

```
P0-1 → P0-2 → P0-3（解耦业务，让系统能接受任意 App）
  ↓
P1-1 → P1-4（建设备画像注册服务的基础设施）
  ↓
P2-1（完善本机硬件画像采集）
  ↓
P1-2 → P1-3（Worker 接入动态注册）
  ↓
P2-2（手机画像上报）
  ↓
P3-1 → P3-3（标准化接入 SDK）
  ↓
P4-1 → P4-2（双层反馈闭环）
```

P0 是必须首先完成的，因为其他所有工作都依赖业务解耦。P1/P2 可以并行进行（分别由手机端和服务端开发者各自推进）。P3 在 P0 完成后即可开始。P4 最后。
