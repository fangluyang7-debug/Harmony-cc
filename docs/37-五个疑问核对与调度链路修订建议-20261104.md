## 2. 疑问一：能力包（评测包）

### 2.1 代码事实

能力包的协议形态是 `CapabilityPackV2`（`resources-v2.ts:43`）：契约、执行器标识列表、模型清单、评测套件 ID、质量阈值、资源上限。运行时形态是 `ReferencePack`（`reference-capabilities/src/index.ts:8`）：在此之上加 `cases[]`（输入字节、参数、配置、输出上限）和一个 `evaluate(test, output) → 0..1`。

三个现有包的实际体量：

| 包 | 代码量 | 内容 |
| --- | --- | --- |
| `text.count.v1` | 1 行（`index.ts:23`） | 一个输入、一个期望输出、规范化相等比较 |
| `vector.normalize.v1` | 1 行（`index.ts:22`） | 同上 |
| `image.crop.v1` | 约 20 行（`crop.ts:5–20`） | 合成 64×32 红蓝图、两个裁剪用例、检查 32×32 JPEG 的像素颜色占比 |

协调者对包的消费是通用的：`QualificationService.advance()`（`qualification.ts:208–286`）下发用例 → 执行方在受限许可下跑 → `pack.evaluate()` 打分 → 与 `qualityThreshold` 比较 → 状态机 `DISCOVERED → VALIDATING → CALIBRATING → CANARY → ACTIVE`。包的大小有硬上限：用例 ≤ 128、单输入 ≤ 8 MiB、策略有 `maxRuns/maxDurationMs/maxBytes` 预算（`qualification.ts:159`）。

### 2.2 判断

**"每个新接入的 App 要提供测评包"——这个前提不对。** 规格 D1（§4.4）和 §7.6 第 2 条写的是"能力归提供方"：包跟着**能力**走，不跟 App 走。SoleAI 和 indexer 两个 App 共用 `image.crop.v1` 一个包；SoleAI 的 v2 路径（§11.2）用到的是 crop、image-encode（C4b）和一个固定服务节点，总共两三个包。一个"功能类型很多"的 App，它的功能是由少数能力**组合**成的工作流（`SdkWorkflow`），绝大多数能力是复用的；只有发明了新能力的提供方才写新包。

**包的复杂度是单元测试级别，而且这个负担是解耦的代价而不是解耦的障碍。** 协调器不知道"裁图该怎么测"，正是因为它不知道，所以它才不依赖裁图。操作系统里对应的机制是设备驱动的 `probe()`/自检：内核不知道怎么验证一块网卡，驱动知道；驱动必须先证明自己能驱动硬件，内核才把设备绑定给它。没有这一步，要么内核内置每种硬件的知识（耦合），要么盲目信任驱动（不安全）。能力包就是这个 probe。

**但你的担忧有一半是成立的，只是位置不对。** 真正的耦合在执行器这一侧：

- `cpu-engine.ts:9`：`['image.crop.v1','vector.normalize.v1','text.count.v1']` 写死；
- `cpu-child.ts:12/22/30`：按能力名 `if/else`；
- `host.ts:64`：`this.packs=[...builtinCpuPacks(),...]`，包清单编译进代理；
- 鸿蒙 `NativeAgent.ets:194`：同样遍历编译进的 `packs`。

所以今天"接入一个新能力"= 改 PC 代理和鸿蒙代理的源码。这不违反规格（D1 要求"执行代码随安装包发布"，不动态加载任意代码，这是对的），但它意味着代理没有**注册点**，只有**名单**。AC1 检查的是核心零修改，没有检查代理零修改。

第二个缺口：`TaskContractV2` 没有成本参数声明。v1 曾有 `costModel`（文档 34），v2 协议里去掉了。后果是规划器只能按输入字节数区分工作量——对 crop 可以，对"10 个 token 和 10000 个 token 的文本"不行。这也是疑问二、四里估计不准的根源之一，而补它不增加 App 负担，只增加能力提供方一行声明。

### 2.3 建议（A 组）

| 编号 | 类型 | 内容 | 验收 |
| --- | --- | --- | --- |
| A1 | 接线 | 代理侧增加执行器注册表：`registerExecutor(capability, executorId, run)`。`cpu-engine.ts`/`cpu-child.ts` 改为查表分发；鸿蒙 `NativeAgent` 同样。保留"代码随安装包发布"，注册在编译期完成 | 架构检查扩展到 `services/pc-agent/src/cpu-*.ts` 和 HAR `host/`：不得出现能力名字面值（R4 的代理版）。接入第四个能力时 `cpu-engine.ts` 源码摘要不变 |
| A2 | 协议可选字段 | `CapabilityPackV2.contract` 增加可选 `workModel`（沿用 v1 `costModel` 结构：参数名 + 分档宽度），由 `costConfiguration()`（`capability-cost-model.ts`，已在核心）解释。成本样本按 `(target, workModel 配置)` 分桶 | 同一能力不同工作量参数产生并复用不同成本桶；未声明时退回字节分档（R5：不编造） |
| A3 | 文档 | `capabilities/README.md`：三个包作模板；提供 `equalityPack()` 助手使最小包为 3 行；写明"包按能力计，App 只引用" | — |

A1 不改规格（属于 AC1 的本意）。A2 是 T2 冻结层的可选字段，按 D10 允许增加。

## 3. 疑问二：是否吸收了传统 OS 调度、信息是否上提到协调者

### 3.1 概念映射（核对）

| 传统 OS | 本项目对象 | 位置 |
| --- | --- | --- |
| 运行队列 + 优先级类别 | `MicroQueue`，三类 `ORIGIN_INTERACTIVE / REMOTE_INTERACTIVE / REMOTE_BATCH` | `micro-queue.ts:252` |
| CFS 的 vruntime / 份额公平 | `score()` 中 `debt = Σservice × share[c] − service[c]`，按池容量归一 | `micro-queue.ts:276–292` |
| 老化、有界连续服务（防饥饿） | `aged`、`streaks/maxConsecutive` | `micro-queue.ts:277,289` |
| `nice`/cgroup 对交互进程的保护 | 所有者保护：`ownerActivity=ACTIVE` → `admissionLimit→0` + `YieldNotice` | `device-scheduler.ts:35–40`、§7.2.3 |
| cgroup 资源上限 + 原子准入 | `admitV2()`：资源向量对账本和额度原子检查 | `ledger-v2.ts:191–216` |
| 租约 / fencing token | `FenceV2{holder, ledgerEpoch, counter}` | `protocol-v2.ts:268` |
| 多处理器的资源预约表 + 最早完成时间 | `earliest(occupancy, demands)`：按 `device:pool` 键的区间占用表 | `planner.ts:180–194` |
| 关键路径 / 列表调度 | `extend()`：`ready = max(依赖完成)`，`cost = max(state.cost, end)` | `planner.ts:199,218` |
| 页缓存 / 数据局部性 | 副本位置 `replicas[].readMs` + 有向链路计价 | `planner.ts:151–167` |
| 零拷贝 / DMA 旁路 | B→C 直传不经协调者 | STATUS §25、§44 |

这个映射不是事后贴标签——协议字段（§7.3 心跳附加字段：`admissionLimit/occupied/draining/drainMs/ownerActivity/credits`）就是按"把设备内调度器的状态上报给宏观层"设计的。你的核心思想在架构里是落实的。

### 3.2 实际流入协调者的信息（核对）

| 字段 | PC 代理上报 | 鸿蒙代理上报 | 协调者是否消费 |
| --- | --- | --- | --- |
| `pools[].occupied / admissionLimit / draining` | **实测**（来自账本，`host.ts:218`） | 实测（`NativeAgent.ets:200`） | 是：`directory.ts:106` 算 `available`；`:121` 排除排空池 |
| `pools[].drainMs` | UNKNOWN | UNKNOWN | 否 |
| `ownerActivity` | 实测（Windows 空闲时长）或 PRIOR | PRIOR | 是：`directory.ts:72` 硬过滤 |
| `executors[].compute` | 校准时的一次耗时（`host.ts:94`），**业务执行不回填** | 校准 + **业务执行回填**（`NativeAgent.ets:286`） | 是：候选排序与 makespan |
| `executors[].queue / cold / publish / uncertainty` | **PRIOR 0**（`host.ts:188`） | PRIOR 0（`NativeAgent.ets:194`） | 是，但值恒为 0 |
| `credits[]` | **写死 `owner==='IDLE'?1:0`**（`host.ts:221`） | `MicroQueue.credits()` 真实计算（`NativeAgent.ets:193`） | 是：`directory.ts:127` 取策略优先级那一类作 `availableSlots` |
| `links[]` | 中继链路实测拟合 | 同 | 是 |
| 运行中任务的剩余时间 | 无此字段 | 无 | — |

两个代理在 `credits` 和 `compute` 回填上行为不同，这是 R22（终端等价）的缺口；一致性测试只检查协议和准入语义，不检查上报数值的来源。

### 3.3 判断

**协调者现在拿到的是"静态容量视图"，没有"时间视图"。** 它知道一台设备当前有几个槽位空着、内存剩多少、是不是排空中、所有者是否在用；它不知道正在跑的任务还有多久结束、队里排了几个、下一个槽位什么时候空出来。于是：

- 一台正在跑一个 200 ms 任务的 PC，对规划器来说和一台关机的 PC 没有区别（`availableSlots=0` → `CAPACITY_UNAVAILABLE`，`planner.ts:118`），哪怕它 200 ms 后就是全组最快的目标；
- `queueMs` 恒为 0，所以候选排序（`planner.ts:84`）实际上就是 `computeMs + 传输`；
- `earliest()` 的占用表只装了**本次计划内部**的节点，初始 `occupancy=[]`（`planner.ts:80`），没有装设备上**已经在跑**的任务。

你怀疑"简单按预跑速度调度"，就当前填入的数据而言，是对的。但要分清：这不是算法设计的问题，`earliest()` 就是为了装在途任务而写的资源预约表，只是没人往里装。STATUS §50.2 把这项列为 D2 的"在途剩余时间估计"，尚未实施。

**关于"性能不只是速度"。** 规格 §7.1.1 的目标是分层的："先满足能力、权限、质量、资源、期限约束，再最小化端到端完成时间；在策略允许的时延范围内，再兼顾终端能耗、网络计费和交互负载"。代码里前两层是真的（约束过滤 + makespan），第三层以**约束**而非**目标**出现：电量、温度、省电模式、计费网络是 `directory.reason()` 的硬过滤（`directory.ts:71–79`），不进入代价。这在首版是可辩护的——OS 调度器也只优化一个主目标，其他作为约束——但要在文档和答辩里说清楚：当前"性能"= 可行解集合内的完工时间；所有者不受干扰由微观层份额保证，不由宏观目标函数保证。

### 3.4 建议（B 组）

| 编号 | 类型 | 内容 |
| --- | --- | --- |
| B1 | **新契约（D2/D4 的估计契约正文，需写入规格 WP-D4）** | 心跳增加**设备时间视图**，按持有者、按资源池：`running[]{attemptId, priority, resources, startedMono, predictedRemainingMs:{value,source,ttlMs}, interruptibility, maxNonPreemptibleMs}`、`waiting[]{priority, count, demandSum, oldestWaitMs}`、`releaseProfile[]{atMs, amount}`（按剩余时间排序的释放曲线）。`drainMs` 由此派生。来源优先级按 §7.1.3：同条件实测 → 校准 → 先验 → UNKNOWN，不编造 |
| B2 | 接线（核心零改动或极小改动） | `plan()` 用快照中的时间视图**种初始占用表**：每个 `running` 项变成 `occupancy{key:'device:pool', start:now, end:now+predictedRemaining, amount}` 和 `{key:'target:…', amount:1}`。然后 `earliest()` 自然给出"何时能开始"。**同时删除候选级 `queueMs`**，等待只在占用表里算一次（满足 D4"同一段等待不重复计费"）。`source=UNKNOWN` 的在途项按 R5 处理：该池视为不可用，不猜 |
| B3 | 对齐（R22） | PC `host.ts:221` 改用 `DeviceScheduler.credits()`（已存在，`device-scheduler.ts:71`），与鸿蒙一致；PC 业务执行回填 `compute` 样本（对齐 `NativeAgent.ets:286`），样本按 A2 的工作量桶和 §5.4 维度分开。一致性测试增加"上报的 credits 等于 `MicroQueue.credits()` 的输出"检查 |
| B4 | 目标函数（需用户确认，S6/D5） | 把第三层从硬过滤改为字典序次级目标：可行性 → 期限 → makespan → `(所有者干扰, 电池设备能耗代理, 计费字节)`。前三者 makespan 差距在 `switchCostMs+hysteresisMs` 内（`planner.ts:104` 已有迟滞）时，用第四项决胜。能耗代理只用相对量（电池设备上的计算毫秒 × 1，交流设备 × 0），不报焦耳（§7.5 第 2 条） |

B1+B2 是 S5 出口（D2/D4）已经要求的内容，本文只是把"契约正文"具体化，建议直接作为 WP-D4 第 2 条的正文。B3 是缺陷修复。B4 改目标函数，需确认。

## 4. 疑问三：选定设备后，部分步骤能否转移

### 4.1 代码事实

- 工作流提交时整图规划一次（`workflow-jobs.ts:46`），结果存入 `data.plan`；
- 每个节点在依赖全部提交后，经 `CpuJobs.submit()` **重新规划**（`workflow-jobs.ts:64`）。STATUS §44："图初次规划得到的目标不再被无条件固化为子任务约束；调用方明确指定的 `targetId` 仍保留"。四进程 C→D 改派用例已通过；
- 但这次重规划是**单节点请求**：`nodes:[{id:'compute',…}]`，`committedNodeIds:[]`，`committedArtifacts:[]`（`cpu-jobs.ts:57–63`）。它看见"输入在哪、谁现在最快"，看不见"后面还有哪些节点、它们的输入会落在哪"；
- 规划器本身支持子图重规划：`PlacementRequest.committedNodeIds / committedArtifacts`（`planner.ts:49`），`plan()` 只规划 `pending` 节点并以已提交节点的产物为起点（`planner.ts:77–80`）。**数据结构存在，调用方没用。**
- 执行中迁移：`CHECKPOINT` 可中断性在协议里有，但 `ownerYield()` 只发 `RESTART/DRAINING`，注释明说"直到适配器产生真实检查点为止"（`micro-queue.ts:317`）；`YieldNotice` 触发重规划属 S6，未实现（STATUS §1 S6 行）。
- 节点内切分：无。DAG 限制 ≤16 节点、单汇点、每节点**单输入** `inputFrom`（`workflow-jobs.ts:20,24–30`）。没有汇合边，就不能表达"切成几块分别处理再合并"。

### 4.2 判断

你担心的"选定后固化"不存在；每个节点都在派发时刻用最新快照重选。但有三处真实限制：

1. **短视**：单节点重规划会做出"对本节点最优、对后续节点不优"的选择——例如把 B 放到手机因为手机空闲，而 C 的大输入在 PC，结果 B 的输出还要搬回去。初次整图规划避免了这一点，派发时却丢掉了。
2. **执行中不可迁移**：只能等它结束或取消重做（PURE）。对当前亚秒级任务这无所谓；对 S7 的 GPU 编码或批量索引会成为问题。
3. **粒度由 App 决定**：这是对的（D8：等价路径由 App 声明，调度器不删不拆业务阶段），对应 OS 不会替你拆线程。但 SDK 必须能表达 fan-in，否则 App 想拆也拆不了。

### 4.3 建议（C 组）

| 编号 | 类型 | 内容 |
| --- | --- | --- |
| C1 | 接线（S5，不改规格） | `WorkflowJobs.progress()` 对每个可派发节点改调 `graphPlan()`，传入**整图 + `committedNodeIds` + 已提交产物的真实副本位置**，取结果中该节点的分配作为本次派发的目标约束（仍经 `CpuJobs.submit → PlanningService → preflight`，R21 不变）。前瞻深度受 `limits.lookahead` 约束，超出退回基线（`planner.ts:93` 已有） |
| C2 | SDK/协议（S5 或 S7，需确认） | `SdkNode.inputFrom` 允许数组；`PlacementNode.inputs[]` 已支持多输入（`planner.ts:201–206` 对每个输入分别选路并累加）。协调者侧 `graphInput()` 对多父逐一准备。验收：三路裁剪 → 合并的四节点图 |
| C3 | 新机制（S6-R，规格 §6.5.2 已有设计） | 在线变慢触发：B1 的 `predictedRemainingMs` 超出"备选的传输+排队+执行"且契约为 `PURE + CANCEL_RESTART` 时，经同一 `PlanningService` 创建新 attempt，旧 attempt 按 §6.5.4 唯一提交。本文不新增设计，只指出 B1 是它的前置 |

## 5. 疑问四：并行性，以及"只按速度选设备"

### 5.1 代码事实

做到的：

- 分支按关键路径估计、同池串行：`planner.test.ts:199`（"estimates independent branches by critical path rather than their sum"）、`:203`（"serializes branches when their shared device pool has one slot"）；
- 就绪节点一次全部派发：`progress()` 遍历所有依赖已提交的节点（`workflow-jobs.ts:56–78`），独立分支并发；
- 传输占用中继并发槽位并进入占用表（`planner.ts:215–216`）。

没做到的（全部是数据或接线问题）：

| 项 | 现状 | 后果 |
| --- | --- | --- |
| 每设备槽位 | PC `credits.slots=1`（`host.ts:221`）；示例 `device.json` 的 cpu 容量 1 | 16 核 PC 对规划器是 1 个槽位；两个分支在同一 PC 必串行（`demands()` 的 `target:` 键容量 = `availableSlots`，`planner.ts:170`） |
| 冷启动 | `coldMs` PRIOR 0；实际每任务 `fork` 新 Node 进程（`cpu-engine.ts:13`） | 对毫秒级任务，进程启动是主要开销且规划器看不见 |
| 配置选择（§7.2.1 M5） | 包只给一个配置 `threads:1`；代理 `select:o=>o.allowedConfigs[0]`（`host.ts:112`） | 任务内并行（`sharp.concurrency(threads)`，`cpu-child.ts:16`）从未被使用；宏观"给集合、微观选"的分工没有发生 |
| 优先级类别 | 协调者所有业务任务写死 `REMOTE_INTERACTIVE`（`cpu-jobs.ts:78`） | 三类公平份额（`micro-queue.ts:252`）只有一类有流量；`ORIGIN_INTERACTIVE` 的所有者优先从未生效 |
| 负载均衡 | `QUEUE_STARVED` 只在设备端超时抛出（`device-scheduler.ts:52`），协调者未据此改派 | 没有"从忙设备把排队任务拉到闲设备"的路径（OS 的 `load_balance()`/工作窃取） |

### 5.2 判断

**"太低级"这个评价，对算法不成立，对当前数据成立。** 快照 → 约束过滤 → 带资源预约表的关键路径列表调度 → 束搜索 + 迟滞 → 派发前复核 → 设备端原子准入 → 实测结算，这是教科书结构（HEFT 一族 + 两级调度），不是贪心。但因为槽位=1、队列=0、冷启动=0、单一优先级，它在运行时退化成"合格且空闲的目标里，选 `compute + 传输` 最小的"。换句话说，算法已经为"整个体系所有终端资源整合调度"准备好了，输入还停留在"每台设备一个开关"。

### 5.3 建议（D 组）

| 编号 | 类型 | 内容 |
| --- | --- | --- |
| D1 | 缺陷修复（S5） | = B3。槽位来自 `MicroQueue.credits()`；示例 `device.json`/`contribution.json` 给出多核容量。验收：同一 PC 两个独立分支并行执行，追踪中两个 `EXECUTE` 跨度重叠 |
| D2 | 补数据（S5/D2） | 暖进程池：代理预 fork `maxCpuThreads` 个 `cpu-child`，任务复用；`coldMs` 改为**实测**（有暖进程 → 实测接近 0；无 → 实测 fork+就绪耗时）。鸿蒙侧对应引擎初始化耗时。不允许把"假设为 0"标成实测（R5/R16） |
| D3 | 接线（S6/D7） | 能力包声明配置集合 `{threads:1,2,4}`；宏观 `allowedConfigs` 下发集合；微观按当前空闲核数在集合内选（M5），回执带实际配置（已有字段 `actualConfiguration`）。成本桶按配置分开（§5.4） |
| D4 | 协议使用（S5/S6） | 优先级由 SDK `SubmitOptions` 声明（`interactive: boolean`）并受组策略上限约束（§5.3 第 3 条已有规则）；来源本地执行的节点标 `ORIGIN_INTERACTIVE`（`MicroQueue.enqueue` 已校验 `originDeviceId`，`micro-queue.ts:267`），远端批量标 `REMOTE_BATCH`。这样三类份额才有意义 |
| D5 | 新机制（S6/D3，规格 §7.2.2 第 6 条、§5.5 第 8 条已有） | 协调者消费 `QUEUE_STARVED`：先撤销未启动 attempt、取得取消结算回执，再经规划器改派。配合 B1 的 `waiting[]`，可在超时前主动均衡 |

## 6. 疑问五：资源与数据流通是否应脱离任务、时刻发生

### 6.1 现状（核对）

数据平面严格**按需、绑定 attempt**：传输授权绑定 workflow/attempt/App/制品哈希/字节上限/收发端点/代次/有效期（§5.6 第 5 条）；副本只在核验回执后登记；保留关系由图/attempt 的引用计数决定（`retention.ts:14–41`）；中继缓存 128 MiB（`resource-transport/src/index.ts:31`）。规划器在已有副本中按链路成本选源（`planner.ts:151–167`）。

已经做到的"流水线"：节点 C 的输入在 C **准入之前**就由 B 推送（`progress()` 先 `graphInput` 再 `start`，`workflow-jobs.ts:66–70`），不是"准入后再搬"。根输入先提交元数据再决定是否上传（§6.2 第 1–2 条），这是故意的——否则无法选择本地执行。

没有的：任何预取、预置、投机复制（全库 grep `prefetch/preposition/预取` 仅命中规格 §7.4 第 6 条一处，且含义不同）。

### 6.2 用操作系统的标准权衡

OS 里对应的是 **readahead + 页缓存**：预读在访问模式可预测时收益巨大，代价是带宽、存储和（这里特有的）安全。逐条对照：

| 维度 | OS 经验 | 本项目 |
| --- | --- | --- |
| 正确性/陈旧 | 页缓存必须处理写回与失效 | 制品不可变、内容寻址（`contentHash`）。副本**不会陈旧，只会无用**。这使预置比 OS 页缓存**更安全**——你的直觉在这里站得住 |
| 安全 | 不会把一个进程的页"顺便"映射进另一个进程 | R12/D6：每个离开设备的字节都要有绑定用途的授权。**无主的、不绑定任何计划的数据复制违反底线**。预置可以做，但授权必须绑定"某个计划或某个能力准入"，而不是绑定具体 attempt |
| 能耗/计费 | Android Doze 把后台网络批到充电+Wi-Fi 窗口 | §7.5 的约束同样适用于传输：只在空闲、不计费、不低电时做投机传输 |
| 存储压力 | 干净的缓存页随时可丢，脏页/锁定页不行 | 需要**保留等级**：被在途 attempt 引用的不可驱逐；图需要的保留到依赖结束；投机的最先驱逐。当前 `retention.ts` 只有"需要/不需要"两态 |
| 与放置的耦合 | 数据在哪，计算就倾向去哪（HDFS/Spark "move compute to data"） | **预置改变放置成本**。如果一个独立守护进程决定把数据推到 X，它就替规划器做了一半放置决定——两个调度器会打架。所以预置必须是 `PlanningService` 的输出（R21 的精神），不是独立的数据流通服务 |

### 6.3 判断

"时刻发生、不绑定任务"——方向对一半：

- **对的一半**：传输延迟应当被隐藏在计算后面；制品不可变让这件事比 OS 更容易；有一类数据本来就不属于任何任务——**模型权重、参考资源、能力包的静态数据**。S7 的图像编码模型几十 MB，必须在能力准入阶段预置到执行器（§7.6 的 `WAITING_MODEL` 状态、D3 的"模型缓存用容量配额加引用计数"已经为此留位），而不是每次任务搬一遍。这就是"数据流通不绑定任务"的正确实例。
- **错的一半**："无主的、时刻的"复制违反安全底线，会和规划器争夺放置决定权，并且在没有访问模式证据时只是在烧电和带宽。

正确形态：**由规划器输出的、绑定计划（而非 attempt）的、带驱逐等级的预置提案；传输本身成为一等任务，分优先级进入 `TRANSFER_SLOTS` 池**（`PoolV2.kind` 已有此类型，`resources-v2.ts:72`）。"时刻在流通"于是变成：传输调度器在空闲时总有低优先级的事可做——这和 OS 的 I/O 调度器带后台预读是同一结构。

### 6.4 建议（E 组）

| 编号 | 类型 | 内容 |
| --- | --- | --- |
| E1 | 新机制（需确认，建议 S5 收尾或 S7 前） | **制品保留等级**：`PINNED`（在途 attempt 的输入/输出）> `REFERENCED`（图中未完成下游需要）> `CAPABILITY`（模型/参考资源，按能力准入引用计数）> `SPECULATIVE`（预置提案）。`retention.plan()` 在 `availableCacheBytes` 低于阈值时按等级逆序驱逐；`ARTIFACT_CACHE_FULL` 之前先驱逐 `SPECULATIVE`。所有者在贡献设置里给**缓存配额**（与 `maxCpuThreads/maxMemoryBytes` 并列） |
| E2 | 接线（S7/C4b 必做） | 模型预置进入能力准入：`DISCOVERED → WAITING_MODEL` 时由协调者签发**绑定能力包版本**的传输授权，执行器下载并校验哈希后登记 `CAPABILITY` 级副本，再进入 `VALIDATING`。`coldMs` 区分"模型未驻留/已驻留"两桶 |
| E3 | 新机制（需确认） | 规划器输出 `prepositions[]{artifactId, toDeviceId, reason}`：首版只两种来源——(a) 已选计划中下游节点的输入（把现有的"B 推 C"提前到 B 提交回执的瞬间，已基本如此）；(b) SDK 显式提示 `likelyNext(inputs, workflowTemplate)`（例如拍照后极可能裁剪+编码）。授权类型 `SPECULATIVE`，绑定 `(App 安装实例, 模板, 目标设备, 有效期)`，不绑定 attempt。只在目标设备 `ownerActivity=IDLE`、非计费、非低电、缓存配额有余时签发；传输在 `TRANSFER_SLOTS` 池以最低优先级执行，真实传输随时抢占 |

### 6.5 存储压力的边界

有了 E1，压力是可配置的上界而不是不可控的增长：`SPECULATIVE` 总量 ≤ 所有者缓存配额 − 更高等级占用；`CAPABILITY` 按能力数 × 模型大小，准入时就知道；`PINNED/REFERENCED` 受图上限（16 节点 × 8 MiB）约束；硬期限清扫兜底（已有）。关键不变量：**任何等级的驱逐都不得删除仍有读写进行中的文件**（`retention.ts` 已对 `PINNED/REFERENCED` 保证，扩展到新等级即可）。
