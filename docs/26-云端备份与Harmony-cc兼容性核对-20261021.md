核对日期：2026-10-21。对象：新建的 Harmony-cc 仓库与当天从 Zeabur 下载的持久卷备份。

## 1. 结论

**当前 Harmony-cc 的后端代码能够接续这份云端数据库，未发现会阻止初始化、读取商品或使用现有向量的结构冲突。** 已在隔离副本上运行两次正式数据库初始化命令，36 张表的记录数及逐行数据哈希均保持不变；应用初始化、历史数据读取和两种向量检索也已验证。

迁移仍需处理三类问题：

1. **部署时使用已核对的实际配置。** 后续收到的 Zeabur 实际变量已经包含 COS 桶名及正确的向量模型信息，与当前代码和备份匹配。本地 `.env` 的桶名、通用模板的模型名仍有空值，不能用这些空值覆盖实际配置。第 10 节记录了补充核对结果。

3. **已有数据和运行状态有边界。** 3 个历史会话缺少候选结果快照，其中 2 个还没有用户归属；近期调度运行记录、性能采样等保存在内存中，卷备份不会保存它们。

因此，本次判断是“代码、持久化数据及用户提供的 Zeabur 配置兼容，可以进入恢复验收”，尚不能宣称 Railway 上的完整业务链路已经通过验收。本次没有连接 COS 或模型服务，也没有更改线上服务。

## 7. 数据与部署中需要处理的问题

### 7.1 COS 图片不在这份备份里

1,975 个商品均指向 `demo-assets` 逻辑桶组，且均具有 `imageObjectKey`；36 个已上传图片资产使用 `compressed-recognition` 桶组。数据库保存的是资源引用，图片内容仍在腾讯 COS。

本地配置存在明确差异：

| 配置文件 | COS 凭据有值 | 三个 COS 桶名 |
| --- | --- | --- |
| `.env` | 是 | 全为空 |
| `.env.zeabur.local` | 是 | 均已配置 |
| `.env.zeabur.example` | 模板空值 | 全为空 |
| 用户提供的 Zeabur 实际变量 | 是 | 三个逻辑组均映射到同一个已有桶 |

这意味着不能把根目录 `.env` 原样视为可用的 Railway 生产配置。后续用户提供的实际变量已补齐桶名，地域为 `ap-singapore`。三个逻辑组使用同一个 COS 桶是当前适配器支持的配置；对象键以日期、前缀、资产组 ID 和资产 ID 组织，不需要为了迁移服务器另建三个桶。此次只检查配置是否有值及映射是否匹配，没有输出密钥，也没有验证这些密钥目前是否仍有效。

### 7.2 三条历史会话数据不完整

备份已有的异常组合：

| 会话情况 | 数量 |
| --- | ---: |
| 有归属用户且有候选快照 | 73 |
| 有归属用户、缺候选快照 | 1 |

这 3 条记录状态均为 `ready`，但 `shopping.read` 需要读取候选快照，因此不能完整返回这些历史结果。另有 2 条缺归属用户的记录会受到当前资源归属检查限制。它们不是本次复制或初始化造成的。

建议保留原记录，在明确业务用途后再决定标记为历史不完整、提供可解释的空结果，或依据可信来源补齐归属。不能通过给全部记录随意分配用户来绕过归属检查。本次没有修复或删除这些记录。

另有 51 个 `text-query` 资产没有 `ownerUserId`，对应文本查询占位资产，不能将它们误判为 51 张上传图片丢失。67 个用户均为游客，`UserCredential=0` 与游客认证实现一致；新建游客会产生新用户，不能自动获得另一游客的旧会话。

### 7.3 手机端地址与游客令牌

`CloudApiConfig.ets` 的默认地址仍为 `https://cixin.zeabur.app`，支持通过设置保存新的 HTTPS 服务地址，变更地址时会清除当前内存令牌。

切换 Railway 后，需要在手机端设置新地址，或修改默认值后重新构建安装包；已安装 App 保存过的地址也应核查。Web 的 `PUBLIC_API_BASE_URL`、`VITE_API_BASE_URL`、浏览器缓存地址和服务端 `CORS_ORIGINS` 需同步检查。

如果保留 JWT 签名密钥，尚未过期的旧令牌在新后端仍可能有效；如果轮换签名密钥，客户端需要重新认证。游客令牌和旧会话归属的衔接要单独验证，不能把“数据库仍有记录”理解为“新游客能看见旧游客记录”。

数据库所有 TEXT 列的扫描未发现 `zeabur.app` 字符串，当前未发现需要批量替换的数据库内旧域名引用；这个结果不覆盖 COS 对象内容和未导出的环境变量。

## 8. 接续部署的约束

1. 保持 Prisma 的 SQLite 数据源；初次迁移继续使用 `file:/data/harmony-agent.db`。直接换成 PostgreSQL 的 URL 无法使用这份 SQLite 文件。
2. Railway 创建一个持久卷并挂到 `/data`，使用一个 API 实例。不要让无持久卷的空数据库启动后被误认为恢复成功。
3. 数据库恢复必须在目标应用未读写数据库时完成，并映射到配置指定的文件路径。保留原压缩包，避免把卷归档再包一层放进容器而应用仍读不到数据库。
4. 使用仓库根目录构建。现有构建命令为 `npm ci --include=dev` 后运行 `npm run api:build`；启动链路可继续使用 `npm run api:zeabur:start`。该名称虽然带有 Zeabur，但内部校验、初始化及 Node 启动不依赖 Zeabur SDK。
5. 保留 `PRODUCT_POOL_RESUME_IMPORT_ON_START=false`，初次恢复时关闭自动导入恢复和 Artifact GC，先确认数据和协议状态。其他协议开关以原生产值为准，不在迁移时一并启用实验功能。
6. 数据库初始化应在有卷的运行阶段执行。Railway 的构建和 pre-deploy 阶段不提供持久卷，不能把本项目 SQLite 初始化移到这些阶段。[Railway 卷文档](https://docs.railway.com/volumes)、[pre-deploy 文档](https://docs.railway.com/deployments/pre-deploy-command)。
7. 新服务验收后，安排短暂写入冻结，取得最终快照再切换客户端。当前这份 17:03:42 的快照不包含该时刻之后旧服务产生的新写入。

### 10.2 补充本地验证

使用上述非敏感配置、随机生成的测试凭据和另一份数据库副本，重新创建真实 Nest 应用上下文；本轮设置为 `CLOUD_MODEL_MODE=required`，阻止全部外部 HTTP 请求。

以下 11 项检查均通过：应用初始化、真实服务模式、监听配置、向量配置、视觉场景覆盖、聊天配置、COS 三组映射、图片及导入参数、手机设备读取、购物手机演示开关、无外部网络请求。数据库中 8 个手机设备记录里有 7 个 active，启用手机调度开关后能按归属读取这 7 个设备。

这验证了配置解析、模块初始化和手机设备数据读取；它没有验证真实 API 密钥是否有效、远程模型名是否可用或 COS 是否可达。手机购物裁剪还要求同一用户的工作手机持续轮询、最近心跳不超过 10 秒，因此切换后需要让手机重新连接新地址。

验证脚本与结果位于 `compatibility-audit/zeabur-env-audit.cjs` 和 `zeabur-env-report.json`。脚本只使用随机测试凭据，不含用户提供的真实密钥。

### 10.3 Railway 变量模板

已生成 [railway-variables.example](migration/railway-variables.example)。它保留本次实际使用的非敏感参数，将 7 个敏感变量和三个桶名留空，需在 Railway 控制台填写。该文件不应直接作为已填好的生产配置使用。

首次迁移继续使用已有 COS 桶，不必把图片转移到 Railway。待新服务通过数据库、COS、模型和手机真实请求验收后，再进行最终切换。填写 Web 的实际来源地址到 `CORS_ORIGINS`；不要复制旧平台分配的 `PORT` 去覆盖新平台监听设置。

用户本次粘贴的模型、COS、JWT 和维护接口凭据已出现在聊天中，后续应按实际迁移窗口轮换。JWT 轮换会使旧令牌失效；游客身份与旧会话的访问衔接需单独安排，不能自动将旧游客会话移交给新游客。
