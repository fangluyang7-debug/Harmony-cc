# 实时调度仪表盘与提问诊断

日期：2026-09-22。分支：harmony/mobile-scheduler。范围：harmony-agent/apps/harmony。

## 电脑端实时监控

用户明确调度仪表盘应放在电脑运行，不需要手机内同页仪表盘。原同页方案已从 App 移除；手机只保留电脑接收地址、配对码与推送开关。

原设计原型为 `调度盘/code.html`，包含开发板 NPU/功率等模拟数据，不能直接接手机实时状态。电脑网页现沿用该原型的六联仪表、机架面板、琥珀色刻度与三栏工作台视觉；数据改接 SchedulerService 的真实遥测，未采集的 SoC 温度、风扇、NPU 利用率、云 RTT 与开发板外设不会显示为实测值。

### 数据链路

```text
设备适配器 -> SchedulerService 的设备状态、任务队列、执行计划与执行器遥测
          -> getDeviceState / getMetricsSnapshot / getActiveTasks / getRecentLogs
          -> SchedulerMonitorPublisher（同意后每 750 ms 推送快照）
          -> 电脑 Node 接收服务 :8765（配对码校验、字段白名单、仅内存保留）
          -> 浏览器只读页面（750 ms 拉取，3 秒无数据标记断连）
```

在仓库根目录运行 `npm run monitor:dev`，电脑服务监听 `0.0.0.0:8765` 并输出随机配对码。电脑与手机连同一个可信局域网；电脑浏览器打开 `http://localhost:8765` 并输入配对码。查电脑局域网 IPv4 地址，在 App“我的 -> 电脑实时监控”填写 `http://电脑IPv4:8765` 和同一配对码，然后开启推送。Windows 防火墙若弹窗，仅允许专用网络访问。不要在公共 Wi-Fi 或互联网暴露此调试端口；完成演示后关闭服务并关闭推送。

服务只接受 `POST /api/snapshot`，浏览器通过带配对码的 `GET /api/snapshot` 查看最新快照。它只保留一份最近快照和最多 24 条设备事件在进程内存，退出服务即清除；带认证失败拒绝读取或写入。默认不写文件、不接收搜索词/图片/商品输出、不连接旧 Cixin 后端。传输使用本地 HTTP，配对码会在可信局域网中发送，不能视为加密链路。

手机 publisher 读取现有只读快照，不接管 scheduler、executor 或策略控制。活动任务快照不含输入；桌面接收端再次裁剪白名单字段。每次只允许一个 HTTP 请求在途，失败指数退避；App 进入后台暂停推送，回前台后自动重连；用户关闭开关立即停发。连接电脑失败不会阻塞调度决策。

| 展示 | 真实来源和限制 |
|---|---|
| 电量、CPU、可用内存、热状态 | 当前设备状态；未知显示 `--`/UNKNOWN，保留 REAL/INJECTED/MIXED 来源；热级别不冒充摄氏温度 |
| 运行、排队、暂停、窗口 P95 | SchedulerService 当前队列及终态窗口统计；无完成样本不显示虚构 P95 |
| 活动任务、目标/截止时间、高质量要求 | 新增 ActiveTaskSnapshot，来自实际已提交任务；无业务原文、图片或输出 |
| 计划配置、实际配置、原因、耗时 | 调度日志与执行器 actual 遥测分列；未确认不冒充实际执行，保留策略模式和保护原因 |
| 反馈与参数回执 | 同任务 telemetry.feedbackReceipt；是否校准由 SDK 回执判定 |
| NPU/GPU 利用率、功率、云 RTT | 本手机路径尚无采集数据，明确不展示原型模拟数字 |

网页每 750 ms 检查一次，手机每 750 ms 推送一次；传感器采样频率仍由数据源 TTL 决定。短任务从近期终态事件查看，不保证每个任务都能单独显示 RUNNING。

## 结果后的低频体验题

此前的“速度/质量平衡、300/500/800 ms”首次参数题已撤销。它把内部调度概念交给普通用户判断，体验不合理；当前搜索直接采用 App 的保守默认约束，用户不需要理解目标时延、模型档位或执行配置。`SearchPreferences` 仍保留为内部兼容的 TaskContext 构造能力，但没有对应的普通用户弹窗。

用户进一步明确：温度、内存占用和卡顿属于应自动观测的客观信息，不应询问用户。最终方案撤掉发热/卡顿题；指标缺失时保持未知并遵守既有保守调度，不用问卷代替采集。内存占用不能直接等同于卡顿，精确卡顿仍需要帧耗时/掉帧遥测；当前未接入完整帧卡顿采集，不宣称已实现。

提问门槛是“这一步能否调整调度参数”（前台、非后台/预览任务、已授权、有受控执行配置），**不再要求任务成功**。超时、取消、失败，以及用户等太久离开，都是可感知的等待体验：仍生成等待容忍度问题，选项包含“一直没出来”。成功且结果已展示时才询问质量疑点。非成功/离页的问题标记 `NEXT_IDLE`，邀请保留 30 分钟，在用户回到前台或下一次空闲时才展示，避免在已经离开的页面上强弹。调度器先读取终态、结果展示/消费、任务耗时与可选应用观测，再按下表选择；没有必要就不提问：

| 优先级 | 条件 | 用户看到的问题 | 选项 |
|---|---|---|---|
| 90 | 任务以超时 / 取消 / 失败结束，或用户等太久离开，没有可用的成功结果 | 刚才等待结果的时间可以接受吗？ | 很快 / 能接受 / 有点慢 / 一直没出来 |
| 80 | 任务成功，但调度耗时或 App 测得的结果准备耗时超过任务软截止 | 刚才等待结果的时间可以接受吗？ | 很快 / 能接受 / 有点慢 / 一直没出来 |
| 40 | 任务成功且 App 明确报告结果质量不确定，且未报告有用性、用户尚未消费结果 | 这次结果符合你的需求吗？ | 有用 / 不够准确 / 无关 |
| 不出题 | 正常完成且无明确疑点、应用已提供所需判断，或该步没有受控执行配置 | 无 | 无 |

一次只问一个问题；“稍后回答”收起，不会当作满意或不满意。进入商品详情时隐藏题目。等待容忍度和结果需求符合度独立校准，不把实际耗时直接当作用户不满意，也不把一次点击直接当成正面训练标签。客观设备保护无需等用户作答。等待答案在超时/取消场景下也允许参与速度维度校准（等待感受不依赖执行配置是否被确认），结果质量答案仍要求真实执行已确认。

通用 `TaskSignal.experience: AppExperienceObservation` 是可选字段，不依赖购物页面或商品类型：

- `responseReadyMs`：App 从提交到结果交给页面的实测耗时，与 SDK 执行耗时分开保存，不冒充屏幕实际出帧时间。
- `resultQualityUncertain`：应用确有质量疑点时主动上报；不能拿资源预测置信度或随机分数冒充结果置信度。
- `resultUseful`：应用已有明确判断时上报；未提供不填 false。已有判断或 RESULT_CONSUMED 可抑制不必要的质量题，但不会替用户填写问卷。

只有成功任务的 RESULT_DISPLAYED / RESULT_CONSUMED 信号接收这些字段（非成功终态没有结果展示信号，直接按终态询问等待感受，不依赖 `responseReadyMs` 或质量疑点）；数值经过有限性和范围校验，布尔值校验类型，只复制白名单，不记录业务原文。当前购物 App 只上报真实 `responseReadyMs`，**未伪造质量置信度或强制置为不确定，因此常规路径仅在等待超出预期时询问容忍度**。质量题接口已由合成用例验证，后续接入真实质量判断后才会按条件启用。新增字段不改既有硬约束或直接下发执行参数。

```text
成功结果 -> RESULT_DISPLAYED -> getFeedbackAvailability(workflowId)
  -> getFeedbackRequest -> 页面单题 -> submitFeedback
  -> 校验工作流/同意/有效期/选项/重复 -> 有界校准或积累 -> 回执

非成功终态（超时/取消/失败）或等太久离页
  -> 邀请标记 NEXT_IDLE，保留 30 分钟
  -> 回到前台/空闲 -> getFeedbackAvailability -> getFeedbackRequest
  -> 等待容忍度单题 -> 同上校准链路
```

新增只读 FeedbackAvailability。SDK 按工作流所有权映射到输出节点，返回 READY 或明确原因。反复读取状态不生成邀请、不消耗提问次数。设备事件显示未授权、等待完成、未成功、未展示、无需提问、已回答、邀请过期、同类今日已询问、日总上限或间隔不足等原因，并在事件中展示 selectionReason 和提问优先级。结果出来之后再授权，可以尝试获取符合条件的邀请，并非必定弹题。

保持既有频控：UTC 日最多 2 次，同能力/任务类型每天最多 1 次，两次至少间隔 30 分钟；成功结果题的邀请 2 分钟过期，非成功/离页的延后题保留 30 分钟并在下次前台空闲时展示。因此，同一购物检索当天连续测试通常只有一次结果体验题，这是原保护规则，不是弹窗故障。系统不会为了轮询更多维度而突破频控。

回答仍走文档 12 的 FeedbackReceipt 和受约束校准。时延、结果质量各自达到默认最少 10 条才可能校准，同配置/版本/状态桶隔离，样本仅进程内；普通短会话多为 COLLECTING，**没有完成持续跨启动学习或神经调度模型训练**。一次回答只产生有界样本，不直接改线程数、模型档位、质量底线或硬截止。手机页面回执只告诉用户“已记录/积累后再调整/继续经过安全边界”，不展示内部权重。体验题与电脑端监控页面分离；历史 DEVICE_COMFORT 枚举为接口兼容保留，当前自动邀请不会产生此类问题。

## 验证与复测步骤

自动化覆盖简单提问文本与选项、等待容忍度优先于质量疑点、客观指标异常或缺失不产生客观问卷、App 观测校验和拷贝、无必要不消耗配额、不把消费当正面反馈、任务所有权、限频和过期、实际活动任务快照及防修改、监听销毁、延迟初始化、未知数据和读取失败。最新执行结果见阶段记录中的阶段九及 testing 下的原始测试报告。

电脑监控链路加入前，主机回归曾通过：scheduler 160、entry 26、Python 9 项，无失败或忽略；这些测试和构建结果是此前版本的基线。本轮电脑监控改动的 HAP/HAR 构建已成功，但未运行测试套件，也尚未完成真机网络配对和界面复测。旧初始题截图已删除，其余截图明确标记为历史；本轮产物哈希与设备复测见[验收记录](testing/08-live-dashboard-and-questions.md)。

建议在目标手机和电脑逐项复测：

1. 直接输入商品并发送，不应出现内部时延参数题；搜索仍采用保守默认约束。
2. 启动电脑端服务，打开浏览器监控页并完成配对；手机填写电脑 IPv4/端口及配对码后开启遥测推送，再进行搜索，确认电脑页面显示活动任务及真实终态事件。
3. 开启本地体验反馈，符合频控且等待超过预期的成功搜索出现等待容忍度问题；正常快速搜索不出题。回答回执与相同输出 taskRunId 对应，后续同类邀请仍受日限额限制。
4. 高温/低内存仍自动走设备保护，不问温度、内存或卡顿；质量不确定通过测试信号验证，且低于等待容忍度问题优先级。选项不出现目标时延、模型档位等术语。
5. 停止电脑服务或断开网络时，页面显示遥测中断；恢复后自动收到新快照。切换 App 到后台暂停推送，回前台后恢复。反馈邀请仍遵守过期、撤销授权和任务关联规则。
6. 模拟器的硬件状态可用性和性能不代表真机。真实手机还需验证传感器、MindSpore 推理、热保护、质量和收益，不以逻辑测试或构建成功替代。
