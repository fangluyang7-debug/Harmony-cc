## 找到的调度偏差

1. 三机轮次 GPU 首批约 1.55～1.65 秒，随后多数分块约 0.064～0.183 秒。原成本反馈对最近 32 项同尺度样本等权计算 P90，早期慢样本持续使不确定余量维持约 1.466～1.478 秒。某块 GPU 纯执行估价约 0.173 秒，最终含传输、发布、余量的估价却约 2.16 秒；叠加排队后可到 3.86 秒。普通 Windows 的约 2.23 秒估价因而胜出，尽管 GPU 已经热起来。
2. 手机三块预计 EXECUTE 约 1.182 秒，实际 3.390、3.348、2.980 秒；普通 Windows 两块预计约 1.448 秒，实际均约 1.382 秒。不是所有 CPU 都被低估，不能统一修改倍率或绑定设备 B。
3. 同一待执行任务尚未出现在 heartbeat 时，中心使用“服务时间＋不确定余量”预占时间；heartbeat 报告排队后，又只算服务时间。对冷启动余量很大的 GPU，每个未确认前驱额外叠加约 1.5 秒，导致计划随 ACK 到达而跳变。
4. 双机的一块手机增强是 GPU 返回 RESOURCE_UNAVAILABLE 后的未执行改派，不是重复执行。保留该恢复路径；估价不能代替真实资源准入。

## 已修改

- `services/coordinator/src/performance-feedback.ts`：声明像素尺度的工作按同一执行身份、校准代次、workKey、config、startup 和计时口径归组，用最近至多八个已提交执行样本计算指数加权 P50/P90（相邻权重 0.65）。冷热转换后不再长期背负旧冷启动尾部；新慢样本立即提高 P90，连续变慢提高 P50。不是选择最快记录，不改变非尺度工作统计，也不删除原始审计证据或持续退化检测。
- `services/coordinator/src/directory.ts`：未确认派发与已报告排队统一使用预计服务时长，剔除历史 policyQueue 和重复的不确定余量。候选自身仍保留不确定性；运行中未知剩余时间的保守预测、实际 CPU/RAM/VRAM 账本、派发上限均保留。
- 使用现有端到端最早完成规划：包含排队、计算、传输、发布成本。不存在每台设备必须分到增强块的要求；GPU 预计更早完成时允许 CPU 空闲，GPU 长队列或不可用时保留 CPU 备用路径。

## 仍有优化空间

双机首批只提交三张照片，下一张在已有图片完整交付后才提交（照片 3 约 8.187 秒提交）。GPU 计算已结束但等待下一批输入、上传、手机处理结果，形成 3.617 秒空档。后续可将手机的“提交下一张”和“下载/展示上一张”解耦，并用有界字节预算控制在途数据；这需要修改图片 App，不能仅增加 GPU 槽位解决。本轮不调整 App 或 B 安装包。

双机仍有资源重试和一次 GPU 准入拒绝。先由用户以同序六图验证 R9 的分配变化、首张和整批耗时，再依据新 traces 判断是否需要调整在途窗口；不保证加入任意慢设备都严格更快，也不承诺尚未测量的提速。
