# 真实购物候选集的设备协同计算

本页说明当前实现与后续演示步骤；持续进度以 STATUS §100–101 为准。软件链路和手机 + Windows 双设备购物协同已验证，三设备验收待鸿蒙电脑接回。

2026-11-09 接续更新：用户接回手机后已完成手机 + Windows 真机调试及追踪持久化修复，详见 STATUS §101 和[双设备实测记录](../../artifacts/acceptance/2026-11-09/shopping-phone-windows/README.md)。第三台鸿蒙电脑仍待接回。03 调度件应使用 `dist/调度系统补丁-20261109-trace`，替代初始 shopping-final 的 HAP；01/02/04 沿用原包。

## 入口和职责

在 Windows 的 Harmony 协作空间应用中打开空间调度盘，选择「购物协同」。页面为 `shopping.html?space=<当前空间 ID>`，默认需求「500元以内的运动鞋」，预算 500 元。

1. 页面向现有独立 Railway 购物服务申请访客身份，通过 `/api/v1/sessions/text` 获取真实候选商品与业务 `runtimeRunId`。
2. 页面仅把候选 ID、原始价格、币种和原排序传给计算设备。候选不重复扩增；每件候选只属于一个分片。
3. 各分片使用既有 `SchedulerSdk → 空间 SDK 接口 → PlanningService → 设备 CPU 执行器`，执行 `catalog.filter.v1`。每片预算 30000 ms。
4. 执行器以整数「分」校验价格，过滤非人民币及超预算商品，并按价格、原排序排序。Windows 与鸿蒙共用同一份纯计算逻辑。
5. 来源页面校验结果数量、商品 ID、价格和结果哈希，合并排序，恢复完整商品展示。图片、店铺、链接来自原始业务候选集，不由计算设备生成。

业务地址为 `https://api-server-production-0135.up.railway.app`。没有变更云端部署；不向调度内核添加购物接口或新的派发入口。该结果是服务目录商品，不保证交易平台实时库存、售价，不执行下单。

## 两种调度模式

- **协调者自动分配**：默认。规划器选择合法目标；不承诺每台设备都有任务。
- **覆盖在线设备验收**：每台已就绪设备约束一个候选分片，最多四台；目标约束通过 SDK 进入规划器，仍经过准入、资源预算和结算。候选数少于设备数时只创建必要分片，不能宣称所有设备参与。

第二种模式用于核对三台设备均可计算，不代表规划器自动最优选机或加速。30 件候选的筛选通常计算量很小，不应通过重复候选制造「算力加速」。性能结论需要独立、同输入、同预算对照。

## 展示与恢复

购物页显示业务 runId、分片输入数量和字节数、jobId、实际设备、实际任务状态、分片结果及耗时。调度追踪链接定位对应任务，既有调度盘保留资源和时间线。

本地保存运行记录并支持导出。失败或刷新后「恢复结果查询」复用原 jobId，不自动重新提交或重新搜索。完成结果已接收后中继数据会释放，页面保留已校验的结果，不将再次下载已释放结果作为恢复策略。取消仅表示发起取消请求，最终以任务结算状态为准。

当前这条购物编排入口位于协作空间页面；**尚未将相同文字购物后处理嵌入 SoleAI 手机聊天界面**。SoleAI 原生图片协同链路保持原样。手机打开独立业务 App 时调度件可能停止前台贡献，因此三执行端演示从 Windows 发起。

### 2026-11-09 性能实测后的默认策略

固定 30 件真实候选的 5 轮真机对照未证明双设备加速。默认自动模式现在整批提交小候选集（执行器每批最多 10000 件，超过才拆），继续使用 SDK 与统一规划器；覆盖模式仍用于各设备执行验证。自动整批中位 3.665 秒，双机拆分 6.282 秒，最快 Windows 整批 2.783 秒，均不含云端检索。自动整批的收益来自避免过度拆分，不能标为并行加速。已修复原生消息乱序/重连堵塞及校准与业务资源竞争。详细方法、失败记录与范围见[性能验收报告](../../artifacts/acceptance/2026-11-09/shopping-performance/README.md)及 STATUS §102。
