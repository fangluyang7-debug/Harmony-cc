### 接口速查

| 接口 | 用途 |
| --- | --- |
| `POST /v2/apps/registrations` | 设备所有者凭据确认 App 策略并签发邀请 |

## 5. 已知边界与修复经验

- 当前支持同一输入、同一能力的单节点等价方案，可约束不同目标；输出契约或质量目标不同会拒绝。多节点 DAG、跨能力等价路径及通用副本/直连属于 S5。
- 当前数据经过协调者中继，结果目的地只接通 `ORIGIN`。来源 App 尚未作为本地执行候选；`SOURCE_PULL_NOT_ESTIMATED` 仍在，不能报告完整端到端预测收益。
- 离线基础额度已经预留，但离线执行、SDK 宿主与 agent 同机预算整合及在线/离线联合对账尚未完成。基础预留不能直接当成已经可用的离线运行能力。
- `cancel()` 当前仅能在派发前证明未开始；已派发未结算会返回 `CANCEL_REQUIRES_HOST`。等待结果超时不取消、不重提、不释放。结果成功但资源未结算，或者记录缺失，仍需保留相应占用。
- SDK 默认最多等待容量 15 秒；兼容服务端网关使用 `capacityWaitMs:0`，由客户端负责等待。上轮曾因内外两层等待撞上 HTTP 超时，修复后 Harmony 10/10 通过，不要重新引入嵌套等待。
- Node `Buffer.slice()` 会共享输入内存；SDK 已改为复制后哈希，注册后调用方修改原输入不会改变已登记内容。TS 与 ArkTS 提交代码必须同步修改并通过一致性测试。
- 运行中仍观察到 `CONTROL_INTERNAL_ERROR` 日志，协议测试通过不代表异常分类问题已解决。后续定位时保留原始证据，不把重试成功解释为没有异常。
- App 名称是用户确认标签，不是发行者签名证明；X5 仍待完成。当前不提供策略修改管理界面，策略冲突返回 `APP_POLICY_CONFLICT`。

## 6. 下一位协作者的开发顺序

以下是基于本快照的接手建议；实际执行时先核对最新 STATUS。先完成 S3，不扩展空间产品界面、不部署 Railway、不开始 S4。

| 顺序 | 工作 | 可交付的验收效果 |
| --- | --- | --- |
| 1 | SDK 宿主整合持久化账本、微观队列、资格评测、App 沙箱制品与物理预算；让来源 holder 进入同一个规划器 | 本地更快时选来源 App 本地执行，输入不上传；远端更快时选 PC；两条路径通过同一 plan/preflight 和准入结算链路 |
| 2 | 接通离线基础额度、本地路径，以及恢复连接后的资源/配额联合对账 | 失联时仅使用自己的基础额度，旧任务占用仍计入；超额被拒绝或等待；重连不产生重复执行 |
| 3 | 为两个代理实现持久化执行中取消及真实引擎停止/结算 | SDK 发起取消后能观察到最终结算；未得到停止/结算证明前不回收资源；PC 与 Harmony 共同测试 |
| 4 | 补齐固定服务节点、结果目的地、SDK 根追踪和来源取回区间 | 能观察任务从 SDK 提交到结果可用的完整过程，按实际支持范围验证输出去向 |
| 5 | 复核 S3 软件/模拟器验收，并更新 STATUS | 同一 App 的本地/PC 选择、离线回退、配额、取消和结果均有正反例，再判断是否达到 S3 完成条件 |

**真机 C3、X5、GPU、多物理终端与长时间后台验收继续暂缓。** 本交接不把这些设备条件当成继续软件实现的前置阻塞。
