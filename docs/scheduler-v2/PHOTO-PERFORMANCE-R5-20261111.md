# 照片流水、成本预测与模型复用优化 r5

分支：`imageprocessing`。在 `df79a6b` 后的本机真机修改上继续开发，保留此前未提交内容。本轮用户要求更新应用后自行按同一顺序复测六张照片；未自动运行新的真机照片批次。

## 依据与改动

r4 用户批次 `c9e1252e-1fbf-4d68-b227-d894b0da90aa` 为 45.583 秒，比前次 43.251 秒慢。详情见 `PHOTO-PERFORMANCE-R4-AUDIT-20261111.md`。这些是旧版本成绩，不能算作 r5 提速证据。

1. **每图独立推进**：`services/coordinator/src/workflow-jobs.ts` 去掉整组工作流的执行屏障。数据库扫描只负责唤醒；每个工作流有独立 runner、最新持久化游标和通知合并。同图保持单写者，不同图不再互等一个完整推进周期。每图仍最多 4 个就绪节点，源端仍为 2～4 图窗口，实际并行由设备总账准入控制。
2. **修复工作量与剩余时间预测**：`photo.enhance.v1` 契约 v2 声明像素工作模型，使用实际输入图块（包含 16 像素边界）的面积，忽略压缩大小。校准加入 112×112 输入、96×96 核心区域，作为 12544 像素参考；先验按像素比例缩放。泛型 workModel 的可选 `inputBytes` / `scale` 同步到 TS、ArkTS 和 JSON Schema。普通能力原有分桶不变。
3. **尽早利用真实执行证据**：显式比例工作模型可使用首个同工作量/配置/启动状态的已提交样本，但标注 LOW，少于 3 条时增加至少 100% 的计算不确定量；普通能力仍至少 3 条。执行身份、校准代次、10 分钟 TTL、32 条窗口和成功提交门槛保留。手机与 Windows 未拆分初始化的照片执行按完整 EXECUTE 使用，不重复叠加冷启动。
4. **电脑忙碌不等于永远不可选**：同几何工作量的设备剩余时间历史不再被照片哈希分裂。仍无历史时，仅对 PURE 且身份/目标/截止时间匹配的在途任务，以新鲜 elapsed 加已准入决策成本推导短 TTL 的 PRIOR 释放预测；超过估计时保留递增余量。预测只用于规划等待，绝不据此释放真实总账、伪造完成或触发重复计算。
5. **轻量步骤合并**：Web 和手机 SDK DAG 同步为分析 → 各图块的准备+增强 → 合成+成品。用户的 192×128 图片仍分为 4 个相同核心区域，节点由每图 11 个减少到 6 个，六图 66 → 36；不改变模型、分片边界或质量。原 prepare/assemble 能力保留给旧客户端。新的增强/成品输入支持多 schema，工作流派发明确继承实际输入 schema，避免将图块集合误标为 image.raster。
6. **减少重复加载与编码**：Windows 照片调用留在长期运行的宿主，重计算由最多 4 个原生进程承载，实际准入仍在原调度路径上；一个进程保留一个模型，空闲 60 秒退出，取消等待该进程退出后结算。模型文件按大小/时间指纹合并验证，文件变化更换 worker；鸿蒙原生线程各保留一个模型并为每次输入新建 extractor。仅复用模型，不缓存业务输入或成品。合成后的 PNG 直接生成产品包，避免再编码完整图片；非 PNG 仍正确转 PNG。

核心位置：`packages/scheduler-core/src/{protocol-v2,capability-cost-model,planning-api,ledger-v2}.ts`；`services/coordinator/src/{workflow-jobs,cpu-jobs,directory,performance-feedback}.ts`；`services/pc-agent/src/{cpu-engine,execution-runtime,host,photo-accelerator}.ts` 与 `executors/{photo,photo-workers}.ts`；`apps/harmony/scheduler/src/main/cpp/photo-core.h`；原生 `host/executors/Photo.ets`；`packages/reference-capabilities/src/photo.ts`；两端 `PhotoWorkflow`。

## 真实性与兼容边界

- 安装参考是确定性合成像素，使用真实模型推理，仅用于能力校验/计时，不含用户六张原图和结果。大面积参考采用易压缩图案以遵守 64 KiB 校验传输上限；没有扩大协议限制。既有真实颜色/图像质量参考仍保留。
- 首次安装更新触发能力校验，图片 App 继续使用现有可取消就绪等待。它不是用户任务预计算，仍计入提交时剩余批次预算。
- 手机单机也使用同一个模型复用实现，不能故意保留慢基线。模型、4 倍增强、总预算 180 秒和原图均不变。
- Windows GPU 适配了合并输入；当前没有 NVIDIA 真机，不声称 GPU 模型常驻或 GPU 性能通过。Vulkan 外部推理仍是原单次进程路径。
- 模型缓存是每进程/线程的，不跨 App 共享；任务输入在提交之后才经既有 SDK 和传输路径送往执行设备。
- 合并后增强节点接收源图并在执行端切块，少量源图传输可能较原图块输入更大；减少控制往返的收益需由真实六图 trace 验证。
