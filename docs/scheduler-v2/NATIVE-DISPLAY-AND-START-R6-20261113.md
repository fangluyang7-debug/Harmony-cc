# 鸿蒙调度盘与图片轮次展示修复 R6

本轮接续 R5 GPU 连续供给修改。范围是鸿蒙电脑协调中心、共用评委展示页与手机图片 App；不修改 B 的执行器协议、模型和输出质量。

## 问题与处理

| 问题 | 原因 | 修改后的行为 |
| --- | --- | --- |
| 总览在线数量与拓扑数量不一致 | 总览统计在线设备，拓扑遍历全部已配对设备；另有“宿主”数量，容易与物理设备混淆 | 两处共用 `onlineDevices()`；拓扑标题明确“台在线设备”，离线设备继续保留在设备资源页，宿主与物理设备分别标注 |
| 出现未执行的手机本机轮次 | 原生展示服务将 PICKING、SELECTED 也持久化为执行轮次；一次选图、选完、开始前重新生成预览可产生多个 ID | 草稿只用于实时预览；START 后才进入执行历史。读取历史时兼容过滤旧草稿，保留真实成功和失败记录，不需要清空历史 |
| 每轮看不出参与设备 | 接口已包含实际分工，历史卡片只渲染模式与时间 | 每轮显示“参与设备：…”，从实际派发及执行状态取得，展示端与未执行的在线节点不计入 |
| 蓝色进度条开始阶段慢 | 手机先编码全部输入，再等待整批上传，最后才提交首张任务；此前编码与上传不计入步骤进度 | 所有原图上传持续推进，某张上传完成即可提交该张任务，不等最后一张；进度加入真实完成的编码、上传，断线恢复不重置到 0% |

进度表示完成的步骤比例，不表示剩余时间。没有增加假动画、修改实测耗时，或通过预计算用户图片提高成绩。原图仍按每张上传完成实时出现在左侧。

最新 11.961 秒只有一张图片，不能称为六图提速成绩。中心建批发生在手机编码之后，因此表中 1 秒左右的等待不包含全部编码时间，也不能与手机总时长相减充当精确分解。

最新单图的两个 Windows 增强分块 EXECUTE 为 3.241、3.128 秒，两个 B 分块为 0.370、0.903 秒。最终组装需要等待全部分块，所以还有 CPU 尾部影响；本轮没有把它解释成进度显示问题，也没有宣称上传优化能消除全部差距。整体首张交付的收益需用户复测。
