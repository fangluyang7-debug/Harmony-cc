## 时间分布与主要等待路径

以下为各节点局部时段的累计，**不是互斥墙钟分解，不能相加得到 15.504 秒**：

| 项目 | 累计 | 解释 |
| --- | ---: | --- |
| PLAN | 5.5 毫秒 | 22 次记录中的规划算法时段；不含所有构建画像/数据库/资格工作 |
| OFFER | 2.021 秒 | 准备并持久化派发等；不同节点可重叠 |
| QUEUE | 1.252 秒 | 执行端排队累计 |
| ADMIT | 2.436 秒 | 准入及授权等累计 |
| LOAD | 0.827 秒 | 包含部分输入接收，不能与接收再累加 |
| EXECUTE | 28.604 秒 | 并行计算累计，其中 Windows 两个增强分片占 13.481 秒 |
| PUBLISH | 2.995 秒 | 发布回执/结果等；可能包含传输，不能当作纯网络耗时 |
| TRANSFER_RECV / SEND | 0.611 / 0.892 秒 | 已记录的传输局部区间，不代表所有网络与等待 |

`DELIVER` 两个约 14.625 / 15.130 秒的时段，其原因码是 `SOURCE_SDK_SUBMIT_TO_VERIFIED_RESULT`，表示各图 SDK 提交至结果校验的根时段，**不是最后传图用了 15 秒**。

以协调者第一个 PLAN 为相对零点：分析在 0～0.156 秒规划，切块在 0.671～1.191 秒规划，增强在 2.179～6.001 秒规划；Windows 两片都在约 4.08 秒规划，随后各执行约 6.7 秒。两图直到 11.505 / 11.957 秒才规划合成，12.906 / 13.437 秒规划成品生成。Windows 慢分片位于主要等待路径；准备后到增强派发、合成到最终交付也仍有优化空间。不同设备单调时钟不得直接相减，这里只比较同一协调者时钟的 PLAN。

本轮 Windows 增强预计 EXECUTE 约 1.021 秒而实际约 6.7 秒，说明小参考样本/历史成本不能充分描述这次图块负载；这部分属于后续成本估计优化，未通过指定设备、虚报成本或清空历史来绕过。

## 已实施修改

1. `scripts/prepare-photo-runtime.cjs` 和 `services/pc-agent/native/photo-runner.cpp`：Windows ncnn 开启 OpenMP、runner 同步链接 OpenMP。构建验证实际 CMake 标志，并通过 `--runtime-info 8` 实际建立线程组；不满足便构建失败。运行库说明去掉“每图块单线程”的旧限制。
2. `services/pc-agent/src/executors/photo.ts`：CPU 推理输出先在原始 RGB 像素上裁掉 halo，再编码最终 PNG，去掉整块 PNG 编码、解码、再次编码。模型、尺度、halo、图块核心和最终像素保持；Vulkan 分支保持输出几何校验。
3. `services/coordinator/src/workflow-jobs.ts`：未成功的节点不反复查 committed 输出；成功但输出尚不可见时仍继续等待并复查。SDK 状态轮询一次批量查已建立 Attempt 的节点，只给尚未准入的节点检查输入传输，不反复对正在执行的节点重建输入票据。取消、备份胜者、唯一派发、结果提交语义保留。

没有加入任务结果缓存、提前传用户照片、降低手机单机资源或改变模型质量。没有移除原始照片/成品供评委页面实时展示所必需的传输。
