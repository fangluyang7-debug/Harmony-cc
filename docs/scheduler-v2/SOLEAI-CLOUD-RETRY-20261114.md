# SoleAI 云端连接与执行条件检查修复

## 问题与证据

2026-11-14 真机排查发现，部分 SoleAI 查询在任务派发前因云端模型健康检查失败而被拒绝。同一句查询稍后重试可以成功，不能把这种情况解释为设备 CPU 配额不足。

- 历史 embedding 检查在约 300 ms 后返回 `MODEL_PROBE_TIMEOUT`。旧服务端把所有 fetch 异常都归类为超时，无法区分连接失败与真正超时。
- 手机收到一次依赖不可用后直接结束，没有针对短暂故障复查。
- 文字查询也等待完整健康检查，包括不依赖的视觉模型、COS 和视觉商品索引。
- 手机健康请求的等待上限为 20 秒，服务端模型探测允许 30 秒；先测网络再测模型还可能让刚测得的 RTT 过期。

## 本轮修改

### 手机 SoleAI

`apps/harmony/scheduler/src/main/ets/network/HttpRouteProbe.ets`：

- 连接超时、发送/接收网络错误、网关 502/503/504，客户端最多尝试两次，每次创建并释放独立 HTTP 请求。
- 健康接口报告暂时性模型网络故障时，依据负缓存剩余有效期复查一次，连续两次不可用则结束。不会无限重试；取消和任务截止时间优先。
- 401/403、模型配置缺失、429 限流、商品索引缺失保留具体原因，不用重试掩盖问题。
- 按当前购物能力请求健康检查，先检查依赖，再测 RTT/吞吐；健康 HTTP 上限改为 35 秒，仍受本轮总截止时间约束。
- 此处只重试探测，不重发 `/shopping/tasks`，不制造重复业务任务。

`apps/harmony/entry/src/main/ets/services/CommercePresentation.ets`：显示模型授权、限流、商品索引、连接失败等可区分的原因。

### 云端保持原版本

本轮曾尝试将按能力探测和模型请求重试发布到云端，但部署包携带的 API 基线依赖云端旧库尚无的 `RuntimeCostObservation` 表，导致启动失败和 502。用户指出两轮查询已成功，不应扩大修改范围，因此停止云端改造，回退原部署；本地三份云端源码/测试改动也已撤销。

手机继续兼容原健康接口：旧接口忽略 capability 参数时仍读取完整响应中的对应能力；暂时不可用时按原负缓存有效期等待并复查。客户端依赖状态复查与 HTTP 传输重试分别有界，不代表整个业务流程总共只发送两条 HTTP 请求。购物业务 POST 本轮没有增加重发。
