# 鸿蒙协调中心：GPU 连续供给修复 R5

基线：`52aedf1a6bdbf88dfa48883b95ac0e23ef2291c9`。本轮针对鸿蒙电脑承担协调中心的真实记录，修复原生中心与 Windows 中心之间的派发差异。没有降低照片质量、缩小本轮输入或预计算成品。

## 1. 两轮真实记录

两轮均为六张 192×128 照片，原图哈希及顺序完全一致，全部交付。详细依据见 [脱敏时间摘要](native-photo-gpu-feed-r5-evidence-20261113.json)。

| --- | ---: | --- | ---: |
| `073d8c7a-aafd-44f7-a6ce-a74a5cdc1db5` | 36.576 秒 | Windows 14 块、手机 10 块 | 16.033 秒 |
| `b5546128-fd8f-4e8d-b75c-b8b1af9abb93` | 36.707 秒 | B GPU 11 块、Windows 8 块、手机 5 块 | 18.752 秒 |

第二轮实际有三台执行设备，不能称为“手机＋B”双机对照。分析、成品组装均在手机执行。首张交付使用中心时钟，整批计时使用手机时钟，不能直接相减构造精准的阶段耗时。

## 2. GPU 确实计算了，但供给不连续

B 的真实目标为 `ncnn.photo.vulkan.v1`，后端 VULKAN；不能因为目标 ID 带有 cuda 前缀就称为 CUDA 执行。

- 11 个 GPU EXECUTE 区间累计 6.537 秒；因并发，区间并集只有 3.303 秒，峰值同时执行区间为 4。
- 从第一次执行开始到最后一次执行结束跨越 25.787 秒；中间存在约 5.032 秒及 15.921 秒无 EXECUTE 区间的空档。
- 第四张照片的两个分块，派发至准入分别用了 15.429 秒、14.857 秒，对应计算仅约 0.323 秒、0.285 秒。
- B 的 PUBLISH 区间累计约 5.584 秒，LOAD 累计约 2.717 秒，TRANSFER_RECV 累计约 2.648 秒。上述区间可能重叠或包含彼此，不能相加当作整批墙钟耗时。

这说明主要问题不是“完全没用 GPU”，也不是只允许单线程计算，而是计算与准入、传输、后续工作供给没有充分重叠。EXECUTE 区间覆盖率不是显卡硬件利用率，本轮未取得 B 上逐任务 `PHOTO_GPU_TIMING` 日志，不能确认每次是否发生模型加载，也不能把所有空档直接归因于网络。

## 3. 已落实的修改

### 控制链路不再反复投递同一消息

`CoordinatorChannel.ets` 原先每次 pump 都重发尚未收到 ACK 的 Outbox 消息。节点忙于准入或发布时，这会制造重复消息和账本处理开销。现在同一有效连接只发送一次；重连后仍按原 messageId 恢复未确认消息，保留幂等及持久化恢复。

ACK 改为按 Outbox 主键查询，不再扫描解析该设备全部历史消息；入站消息处理与 ACK 序号分配共用同一数据库事务。正在 pump 时出现的新工作会触发紧接着的补发，不额外等 500 ms 定时轮询。

回归证明重复 pump 100 次只发送一次，重连后恢复同一消息，ACK 后不再发送。这证明修复了重复投递路径，但历史记录不足以精确量化本轮 15 秒中有多少由它造成。

### 接通胜出 GPU 的等待队列

原生规划器能够选择预计更早完成的忙 GPU，但 `CoordinatorJobs.choose` 随后只接受“立即有空闲额度”，把规划结果再次挡回等待。新增 `CoordinatorDispatchCapacity.ets`，在 GPU 仍为预计最佳方案、任务可重启且剩余预算足够时，允许有界预派发。

当前四槽 GPU 最多四项运行、三项等待，共七项；小容量设备按实际资源缩减。仍由节点对 CPU、RAM、显存和 GPU 执行名额作原子准入，不把排队等同于实际占用，也不把资源伪报为空闲。没有按 B 的设备 ID 固定派发，也没有强制各设备均分。

完整规划集成测试验证：连续七次提交成功，第八次等待；CPU 的原有额度约束保持。该测试使用合成规划夹具，不代表真实 GPU 性能成绩。

### 照片流水窗口按已就绪 GPU 容量扩大

`/v2/apps/me/capabilities` 增加 `acceleratorSlots`：只计入在线、通过能力评测、容量采样有效的 GPU，同一物理设备的多个执行目标不重复计算。

手机 `PhotoSession.batchConcurrency()` 使用这个容量。四槽 GPU 时允许六张照片工作流并行推进，前面照片交付期间可继续供应后面照片的增强步骤；总上限八张。没有 GPU 或旧中心不返回字段时保留原策略。输入仍在用户点击后由手机提供，通过现有 SDK 和同一调度器提交。

六张并发、取消、提交断线、结果超时、展示回报超时测试均覆盖；不通过重复提交或延长原始预算“补成功”。

## 5. 后续复测

1. 协调中心保持运行，设备重连同一空间，等能力就绪。
2. 先暂停 Windows 节点贡献，确认只有手机与 B 提供增强能力，再以原顺序处理同一组六图。
3. 恢复 Windows 贡献，再处理同一组六图；保持模型、预算、图片顺序一致。
4. 比较整批耗时、首张交付、GPU 实际分块数、执行空档、offer→admission 等待；不只看任务管理器默认的 3D 曲线。
5. 若仍有长空档，取 B 本地的 GPU 时序、控制通道和模型加载记录，与中心 attemptId 对齐，区分计算、传输、热状态与调度等待。小块任务不应以人为增加计算量换取漂亮的利用率。

## 6. 合并必须保留

本轮代码、端到端规划回归、容量接口与手机端消费代码须一起保留。不能只把并发数字调大而恢复重复派发、立即额度门槛，或把未知容量当成已就绪。R4 的 Pong 独立处理、未准入原 offer 恢复、既有任务查询/取消/结果通路也必须继续保留。
