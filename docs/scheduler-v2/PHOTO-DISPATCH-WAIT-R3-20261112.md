## 2. 二十多秒等待与本轮修复

最长节点 `image 0 / enhance-2` 从 readyAt 到最后一次推进为 20355 ms，累计 37 次 ALLOTMENT_UNAVAILABLE。该区间包含输入准备及反复推进，不能全部算作纯网络耗时或算法计算耗时。其他分块出现 APP_QUOTA_EXCEEDED，最高累计 19 次。历史记录不能精确还原每次等待区间，但代码存在以下可复现放大机制。

### 输入等待任务提前消耗整份算力额度

旧 submit 为 WAITING_INPUT 草稿就按暂定执行目标预留 CPU/GPU/RAM，实际派发时又重新规划、检查同一 App 全局额度。大量草稿争取同一个 GPU 时，即使尚未产生 offer，也会先占满逻辑额度，阻挡输入已经准备好的工作。

现在 pending 预留只占有界的 maxConcurrent 提交名额，仍验证单任务能否放入 App 配额；资源向量暂为空。真正派发在既有 persistOffer 原子事务中升级同一条预留，失败回滚；设备实际准入与物理额度检查保持有效。已有预留不能通过 pending 请求降级，已派发但未结算的工作仍占用额度。此改动没有简单放大 GPU/内存总额度。

### 资源等待占住同一工作流的推进游标

旧 start 可在内部睡眠重试、等待额度 ACK 和目标资源。虽然分块并行推进，整张图的游标仍要等当次所有分块返回，其他分块的新回执及下一步可能因此延后。

工作流现调用 `start(peer, id, false)`：遇到资源/ACK 暂不可用立即归还推进机会；快照改变最多进行一次即时重规划，之后交回事件循环。真实回执、画像事件继续唤醒；每张图最多一个 150 ms 兜底计时器，保证没有 UI 轮询时也能继续。此 150 ms 是重试唤醒间隔，不是保证 150 ms 内一定派发。关闭时清理计时器；已准入任务不重复 start，原尝试 ID、预算和回执保持。

上一轮 R2 把“已持久化但未出现在心跳中的 offer”纳入规划队列的修复继续保留，两项配合使排队预测与实际准入更一致。

## 3. GPU 调度原则

继续通过既有 SDK → PlanningService → 原子派发入口，比较输入传输、队列/资源等待、计算、输出发布和不确定性后的预计完成时间。GPU 较快且短暂排队后仍能更早完成时应选择 GPU；GPU 长队、成本失效或传输更慢时允许 CPU 执行。

本轮没有新增强制 GPU 或固定设备 ID 分流。新增回归用 GPU 292 ms、CPU 1993 ms 的模拟成本验证：空闲 GPU 胜出；GPU 等待 500 ms 仍胜出；GPU 等待 5000 ms 时 CPU 胜出；不匹配配置的 GPU 样本不可冒充有效实测。这些是本地算法回归输入，不能作为新的真机结果。
