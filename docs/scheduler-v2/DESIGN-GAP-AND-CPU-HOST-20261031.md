# 设计落地核对与可运行 CPU 链路

日期：2026-10-31。基于 GitHub 提交 `29fa2e435474104be62b32f6d591128f298fb69c`，包含上一轮远程校准以及本轮尚未提交的工作区修改。

## 结论

项目已经具备独立协调者、资源账本、CPU 执行、设备队列、制品传输、自动校准与恢复基础。本轮将这些模块装配为可独立启动的 PC 代理，并接入任务提交、结果读取和命令行入口。现在可以从空库、新配对设备开始，自动校准后执行文本统计或向量归一化，通过网络取回实际结果。

这仍是跨设备协同运行时的一个可运行子集。鸿蒙 SDK、两个独立鸿蒙 App、多阶段工作流入口、完整的链路/数据位置决策、会话展示与团队操作界面尚未齐全。不能把本轮单节点 CPU 链路写成整个 B/C/D 阶段完成。

核对依据是用户提供的《36-跨设备资源协同架构核对与最终修改方案-20261029.md》，正文实际为 2026-10-30 修订 5。已核对它与仓库 `specification-r5.md` 的 SHA-256 相同：`95294c6d2e006e49f39c5c08438d0ed564b69f2b9603f2d69b8f3362e1a31560`。该文档中“v2 均未实施”描述的是旧基线，不代表当前代码状态。

推进遵循用户最新要求：功能落地优先，先提供可以启动、提交、运行、看结果的入口；不以生产级加固或真机条件作为所有软件工作的前置。账本、结果身份和基本访问隔离继续服务于运行正确性。真机验收暂不执行。

## 本轮实现与设计取舍

1. 新增 `services/pc-agent/src/host.ts`、`host-main.ts`：加载配对配置和贡献策略；自动额度续期、周期画像、事件校准、真实 CPU 执行及关闭等待结算。
2. 协调者启用 `COORDINATOR_CPU_HOST=1` 后安装内置参考包、启动自动校准、为新组建立 CPU 基线策略。已有其他版本的组策略保持原配置，不能被自动覆盖。
3. 新增 `services/coordinator/src/cpu-jobs.ts` 与 `CpuJob` 迁移：元数据提交 → 返回目标和上传票据 → 上传后显式启动 → WS 派发 → 执行者获得读写票据 → 来源端读取结果。
4. 新增 `submit-main.ts`：用户可以提交 JSON 输入并保存输出。客户端查询结果的短周期等待不是执行端领取任务；执行端业务和校准均由事件唤醒。
5. 新增工作区包 `@harmony/reference-capabilities`：协调者与 PC 共用可信参考样例、契约、摘要和 schema，避免两个服务各自复制清单。没有新增外部运行时依赖或升级第三方版本。加入了架构依赖扫描。
6. 新增文本统计实际执行，支持 Unicode 字符数、空白分隔词数与行数；向量归一化也通过相同公共接口执行。
7. 原校准每 500 ms 领取改为长连接通知后领取、重连后对账、失败投递定时重试；空闲 worker 不定时领取。校准中的取消状态检查只在有在途执行时进行。

为尽快形成完整功能，本轮有以下明确简化：

- 任务入口只支持一个 CPU 节点和内置文本/向量能力。默认按合格候选的参考计算时间加队列估计排序，也可指定目标；没有把这个简化入口称为完整 DAG 规划。
- 数据经协调者的独立制品端点中转。先提交元数据再上传已实现，但来源本地执行、自动直连和传输成本选择仍未实现。
- 控制台使用设备配对凭证，App 身份由服务端固定派生；未冒充完整 C2 App 注册。
- CPU/RAM 来自 OS；电池、温度、充电状态保持 UNKNOWN。`dedicated` 模式的空闲、贡献前台和电源策略按用户配置标作 PRIOR，不冒充 OS 实测。CPU 参考耗时包含一次校准执行流程，只作为 PRIOR 估计；队列/冷启动/发布初始值同样是 PRIOR，不是实测收益。
- 新宿主快照版本尚未贯通执行追踪，返回 null，不用计划修订号冒充快照版本。现有 trace 模块保留，但本轮端到端 CLI 不宣称完整追踪。
- 暂不提供任务取消和自动改派入口、页面权限配置、长期日志压缩。未知历史执行仍需对账，不删除账本恢复容量。

## 如何运行软件链路

下面在仓库根目录执行；示例为单机软件演示，域为 SIMULATED，CPU 运算是真实子进程。跨 PC 使用时需要按实际地址配置证书主机名、邀请地址和网络连通性，本轮没有进行真实多机验收。

先安装并构建：

```powershell
npm ci
npm --workspace @harmony/coordinator run build
npm --workspace @harmony/pc-agent run build
New-Item -ItemType Directory -Force C:/HarmonyRuntime
$env:COORDINATOR_DATA_DIR='C:/HarmonyRuntime/coordinator'
$env:COORDINATOR_DOMAIN='SIMULATED'
npm --workspace @harmony/coordinator run db:init
node services/coordinator/dist/provision-main.js examples/cpu-host/device.json C:/HarmonyRuntime/invitation.json
```

示例邀请文件和安装目录要求首次创建；重复运行时复用已有安装，不覆盖它们。下列 Node 命令均以仓库根目录为工作目录。

保持相同环境变量，终端 1 启动协调者：

```powershell
$env:COORDINATOR_CPU_HOST='1'
node services/coordinator/dist/main.js
```

终端 2 配对并启动代理：

```powershell
node services/pc-agent/dist/pairing-main.js C:/HarmonyRuntime/invitation.json C:/HarmonyRuntime/pc
node services/pc-agent/dist/host-main.js C:/HarmonyRuntime/pc/agent.json examples/cpu-host/contribution.json
```

`contribution.json` 示例明确选择 `dedicated`，表示用户主动将配置内资源用于贡献；不是“检测到用户没有使用电脑”。也可改为 `windows-idle`（默认 60 秒当前会话输入空闲）或 `paused`。CPU/RAM 上限不能超过 provision 中已确认的预算。安装目录已存在时复用其 `agent.json`，不要重复配对或清空账本。

待自动校准完成，终端 3 提交任务：

```powershell
node services/pc-agent/dist/submit-main.js C:/HarmonyRuntime/pc/agent.json text.count.v1 examples/cpu-host/text.json C:/HarmonyRuntime/counts.json
node services/pc-agent/dist/submit-main.js C:/HarmonyRuntime/pc/agent.json vector.normalize.v1 examples/cpu-host/vector.json C:/HarmonyRuntime/normalized.json
```

期望输出：文本样例为 `{"characters":18,"words":3,"lines":2}`；向量首行为 `[0.6,0.8]`。已有输出文件不会覆盖；再次演示时指定新文件名。`NO_AVAILABLE_TARGET` 表示尚无具备资格和可用额度的目标，通常先等待初始校准和画像发布；它不是已进入运行状态的任务。

示例本机同时是来源和执行设备。独立进程测试另使用不同的来源与贡献设备身份，验证凭证/票据通过网络流转，但这不等于两台物理机器的验收。
