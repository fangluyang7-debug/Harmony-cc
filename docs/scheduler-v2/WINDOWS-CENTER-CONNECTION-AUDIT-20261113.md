# Windows 答辩协调中心：接入稳定性检查与修复

日期：2026-11-13。工作基线：`codex/local-snapshot-20261113-r8` / `f77dabf`，叠加本地鸿蒙 R9 与本文修改。本文不是新的 GitHub 发布声明。

## 1. 范围与结论

答辩使用 Windows 本机作为协调中心，鸿蒙手机、鸿蒙电脑、设备 B 作为计算节点。按用户要求，**保留每次启动中心后重新配对的流程**，不恢复旧中心身份，也不复用已失效中心的配对码。

已修复 Windows 服务中的历史无接单任务阻塞及配对码成功读取错误占用限额问题，并更新本机实际安装目录。手机、鸿蒙电脑已通过 Wi-Fi 发现并接入本机中心，完成退出后使用原有效配对码重新加入，以及真实文本任务交付。设备 B 本轮不可用，不将本机多进程测试算作 B 真机验收，也不报告 GPU 性能结论。

## 2. 发现与处理

| 问题 | 影响 | 本轮处理 |
| --- | --- | --- |
| Windows 实际安装包中 `auth.js`、`discovery.js` 落后于源码 | 短码第一次读取后失效；发现服务 socket 出错后不能恢复；同 IP 不同来源端口相互限流 | 将本机安装包同步至已验证实现，保留证书固定和设备身份绑定 |
| 旧 epoch 的 PURE 任务无接单记录，执行端明确返回记录缺失 | 即使没有实际在跑的任务，也可能永久 `SPACE_SWITCH_BUSY` | 增加 `unadmitted-closure.ts`；恢复和状态核对时取消此类旧任务、作废旧消息、保留审计标记；退出及配对统一识别 |
| 合法短码读取累计占用全局错误尝试额度 | 多次正常配对可能最终 `PAIRING_RATE_LIMITED` | 成功读取扣回本次计数；错误猜测、并发在途及过期限制继续保留 |
| 已安装图片展示脚本版本较旧 | 历史轮次设备名等改进未生效 | 同步当前 `photo-display.js` 与样式 |
| 部分历史测试与当前接口不一致 | 全量回归出现失败，不能直接宣称全绿 | 修正测试环境与预期：可重试短码、服务目标设备数、协调中心管理 App 配额、OFFERED 状态夹具、购物任务自主选址；编码器故障注入不再破坏同时运行的可信校准输入 |

旧任务收尾必须同时满足：执行端明确无记录、协调中心无 admission/receipt、属于旧 epoch、PURE。真实未结算执行不会因超时或 UI 退出被假装完成；不删除任务历史、不伪造成功回执、不放开一机多空间。

## 5. 更新范围与现场操作

已更新 `C:/Users/17321/AppData/Local/Programs/ZhiDiao/01-Coordinator-Windows-x64` 中协调服务及展示资产。旧文件备份、部署 SHA-256 清单位于本轮证据目录 `installed-backup/`、`deployed-files.json`。这是当前安装目录的更新，不代表旧下载 ZIP 自动更新。

最终 TypeScript 构建通过；已逐个比对安装目录的 auth、device-membership、store、unadmitted-closure、discovery 与最终源码构建产物，SHA-256 全部一致。中心保持运行，避免在交接时再次改变配对身份。

本轮服务修复不要求更换设备 B、手机或鸿蒙电脑的节点包。不能用鸿蒙电脑上的“协调中心”替代“调度连接”：本场只开启 Windows 协调中心，其他三台开启节点 App。

1. 四台设备连接同一可互访 Wi-Fi。中心选择实际 WLAN 地址并点击启动。
2. 每个节点分别生成设备邀请，再扫码或填写该节点的配对码。短码五分钟有效；同一有效邀请可供原设备退出后重连，不用于给另一台设备冒用。
3. 确认调度盘各设备在线、照片能力就绪，再在手机图片 App 重新授权当前空间。
4. 演示期间保持中心运行、鸿蒙节点前台。中心重启后重新配对，并重新授权业务 App。
5. 如果热点拦截广播但设备互访正常，可直接填写中心显示的 HTTPS 地址和新配对码。不要关闭整个防火墙；当前安装的中心 `runtime/node.exe` 已有公用网络 TCP/UDP 放行规则。
