# 照片协作性能优化 r2：实现、安装与真机记录

日期：2026-11-11。分支：`imageprocessing`；起始基线：`df79a6b8a5213eb6c545f8cb68004b7ad17dc5c3`。本文记录该基线之后的工作区修改，尚不能把基线提交视作包含本轮实现。

## 实现与合并要求

1. 自动专用贡献采用实测全部逻辑 CPU（最多 64），内存仍按实际可用量准入，系统余量限定 256 MiB～1 GiB。用户固定配置仍有效，资源额度不是强制预分配内存。
2. 鸿蒙原生运行库通过 `sysconf` 读取 CPU 数，照片增强实际接收线程参数。手机本机和协作宿主均根据可用 CPU 的一半选择 1/2/4/8 线程，允许多个分片并行。PC CPU 执行器采用相同策略；GPU 探测和显存自动额度保持已有实现。
3. 照片参考包覆盖每个线程配置的成功/边界校验；宿主只认证自己实际广告的配置，预留 CPU 与传入引擎线程一致。旧包必须更新，不能只更新中心后继续混用旧参考包。
4. 图片 App 激活时调用 `POST /v2/apps/me/performance`，在线份额跟随同设备共享容量，避免业务 App 仍固定 2 CPU / 1 GiB。合同和离线额度不扩大，真实准入仍通过设备总账；旧声明可重新授权到已扩大配额的 App。
5. 工作流同组最多并发推进 2 张图，每图最多 4 个就绪节点；图内元数据串行写入，节点唯一尝试、已派发不重复 start、剩余预算与结果确认保留。合并同时发生的资源快照刷新，不做 TTL 缓存。
6. 原生照片的分析、切块、合成、成品生成保留在源端，增强由原有规划器选目标；同设备线性阶段使用已有留存产物。多输入合成仍由中心物化 bundle，此处尚未实现零中转。
7. 快照中的目标和设备投影改为同事务分批参数化 UPSERT（每批最多 100 行），减少逐目标数据库往返；容量预算、安装记录、排队任务改为批量读取。保留旧版本投影，失败时整笔事务回滚。
8. Windows 配对成功即清除旧 `coordinatorGone` 标记，修复重配成功后界面仍误报未配对的问题。

具体文件及不可覆盖语义见 `MERGE-PROTECTION.md` M01、M15～M20；未改变独立图片 App、仅展示连接、手动保存图库及单设备单空间的行为。

## 已完成验证和安装

- 中心/PC/共享包构建通过；HAR 和两个 API 24 签名 HAP 构建通过。
- App 配额、能力认证、自动贡献、真实 CPU 图片 DAG 与就绪节点并发定向回归通过；最后一轮图片 DAG 7/7，资源快照/目录/规划回归 30/30，桌面接入回归 6/6。
- 本地真实 CPU 参考图在 1/2/4/8 线程下质量校验全部通过。小参考图耗时不是业务提速证据。
- 手机和鸿蒙电脑已覆盖安装新版 `org.harmonycc.agent` 与 `org.harmonycc.photo`，Windows 已安装中心和执行器代码已更新。未重装 SoleAI。
- 三台照片增强能力均观察到 ACTIVE / EVALUATION_PASSED：Windows 22 CPU / 每片 8 线程，鸿蒙电脑 20 CPU / 每片 8 线程，手机 12 CPU / 每片 4 线程。逻辑 CPU 数不等于物理大核数量，额度也不等于利用率。
- Windows 更新期间已按原产品规则重新配对到同一空间，旧账本保留；后续中心重启前先暂停 Windows 执行器可保留其配对。

首次 NO_LEGAL_PLAN 发生在手机从本机模式恢复协作之后；后来使用当前快照只读重放可找到合法计划，下一轮成功。目前不足以认定唯一原因，不能把该失败删除或写成已彻底修复。

### 最新状态：用户接手真机复测

快照批量读写版本已构建、通过上述 30 项目录/规划测试和 7 项真实 CPU DAG 测试，并更新本机安装目录与 01 分发 ZIP。更新后尝试提交返回“手机正在连接或校准”，未开始计算；因此**没有最新版本的有效真机耗时**。此前 30.380 秒不能作为批量读写优化后的成绩。

检查时 Windows 中心本机 HTTPS 访问返回 200、监听 7443；两台鸿蒙设备连接失败。Windows 仍为 172.20.10.6，手机 172.20.10.3、鸿蒙电脑 172.20.10.2；系统将 `iPhone 2` 识别为公用网络，存在针对已安装 01/02 包 `runtime/node.exe` 的公用网络入站阻止规则。未关闭防火墙或绕过规则。用户要求停止复测并亲自验收，已停止派发测试任务。

手动复测顺序：

1. 先解决当前测试网络对已安装协调中心和 Windows 执行器的访问许可；仅针对这两个程序放行，不需关闭整个防火墙。
2. 打开协调中心与各执行器；确认手机图片 App 的授权已完成，调度盘的照片增强能力就绪。仅有“已连接”的旧页面文案不足以证明控制通道已恢复；当前手机可能仍停在重新授权页，网络恢复后再完成授权并返回。
3. 保持同两张原图、同模型、180 秒预算；本机轮次点“改用本机处理”，电脑只接收展示。完成后切回“连接协作空间”，待就绪后再开始，不重新选择不同图片。
4. 用完整两图批次耗时对照；检查每个增强节点的设备、线程配置、执行回执及所有成品。设备在线不代表实际入选，不为展示三设备而强制派发低效节点。
5. 手机保持前台，测试期间不要构建、压缩安装包或运行其他性能测试；记录充电/温控状态。失败轮次单独保留，不按成功轮次计算加速比。

目前仍未证明协作快于优化后的手机本机；多输入合成仍有中心中转，初次恢复后的规划失败与连接状态反馈亦属于后续观察项。
