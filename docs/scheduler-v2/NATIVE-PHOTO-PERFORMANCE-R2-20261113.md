# 原生中心第二轮性能诊断：17.687 秒与 30.950 秒

日期：2026-11-13。实现版本 `native-photo-perf-v3`。当前工作树为 `codex/main-gpu-integration-20261112`；本轮没有合并、提交或推送远端分支。

## 结论

存在可以确定的代码、调度算法和链路差异，不能将性能回退笼统归因于 Wi-Fi 或鸿蒙硬件。19 个相同图片、相同分块参数、均在 B 上执行的 GPU 样本，平均 EXECUTE 从 351.069 ms 变为 360.097 ms，仅约增加 2.6%；而整批从 17.687 秒变为 30.950 秒，增加 13.263 秒。

本轮已修复 GPU 等待队列、未确认派发与陈旧画像占用的处理，增加 HTTPS 连接复用，移除重复能力状态写入，并接上手机源端输入读取。实际连接微基准已确认固定开销下降；没有在修改后重新运行六张照片，不能宣称已恢复 17 秒。

## 1. 比较范围

两轮六张原图哈希、顺序、尺寸、模型权重和 180 秒预算一致。历史记录来自 `.test/gpu-r9-audit.json` 的 `19176e53…`；本轮来自鸿蒙中心 `85c38d92…`，其决策版本确为上一轮安装的 `native-photo-perf-v2`。

| 轮次 | 实际执行组合 | 总耗时 | 增强块分工 |
| --- | --- | ---: | --- |
| Windows 中心历史 `19176e53…` | 手机 + B | 17.687 s | GPU 23、手机 CPU 1 |
| 鸿蒙中心 `85c38d92…` | 手机 + B | 30.950 s | GPU 20、手机 CPU 4 |
| 鸿蒙中心 `fe26754c…` | 手机 + 普通 Windows + B | 33.025 s | GPU 6，其余 CPU |
| 鸿蒙中心 `69402a05…` | 手机 + 普通 Windows，未见 GPU 执行 | 38.638 s | 全部 CPU |
| 手机本机 `local:3402a2eb…` | 手机本机 | 55.550 s | 无远端执行 |

后三个协作记录均 6/6 交付，但实际计算组合不同。本报告主要比较前两行。33 秒和 38 秒轮次不能作为相同设备、同样 GPU 可用性的重复实验；历史记录不足以还原每次未进入候选集的全部原因，不猜测 B 当时是断线、额度未就绪还是被用户退出。

## 2. 算法差异：本该比较等待 GPU，却提前回退 CPU

30.950 秒轮次中四个落到手机的块，与历史同块对比如下：

| 图片 / 块 | 历史 B GPU 的 EXECUTE | 本轮手机 CPU 的 EXECUTE |
| --- | ---: | ---: |
| 照片 2 / enhance-0 | 280 ms | 4304 ms |
| 照片 2 / enhance-1 | 338 ms | 4938 ms |
| 照片 6 / enhance-0 | 176 ms | 5165 ms |
| 照片 6 / enhance-1 | 235 ms | 5127 ms |

最后两块的决策明确将 GPU 排除，原因为 `POLICY_WAIT_UNKNOWN`。前两块的决策没有该拒绝条目，不能伪称四块都有同样拒绝证据。

代码原因：上一轮只覆盖了部分正在执行任务的完成预测，却要求等待队列为空才进行资源投影，且没有把实际 queued 任务和未确认 offer 的服务时长送入共享规划器。GPU 有工作等待时，其队列成本变成未知，导致 CPU 成为唯一候选或过早被选中。这是上一轮修复不完整，而不是要求用户增加配额就能解决的问题。

照片 6 的两个 CPU 块从派发到结算分别约 7.139 和 7.387 秒；后者结算后仍需等待合成、上传与接收，是最后交付的关键尾部。不能将并行块时间相加当作整批损失。

本轮修复：

- 以已派发任务的实际规划记录建立 queued 服务时长，未确认 offer 只计一次，不同时算进占用和排队。
- 对新鲜 elapsed、已准入的纯计算任务补充剩余时间预测，未知或无依据的工作仍不假定立即完成。
- 资源可用性与共享规划器使用同一组在途、排队预测；保留真正的派发额度和设备端原子准入。
- 经验证、资源已结算的回执可以修正仍列着同一 attempt 的旧画像，避免等待下一次心跳才承认资源释放；不释放其他任务或仅预测完成的任务。

## 3. 连接与实现差异：不是简单的 Wi-Fi RTT 变慢

全 GPU 样本的阶段均值如下；两轮 GPU 分块数量不同，精确计算比较应参考前述 19 对匹配样本。

| 阶段 | Windows 历史 | 鸿蒙 30.950 s 轮次 |
| --- | ---: | ---: |
| GPU EXECUTE | 335 ms | 345 ms |
| GPU LOAD | 53 ms | 279 ms |
| GPU ADMIT | 96 ms | 239 ms |
| GPU PUBLISH | 212 ms | 563 ms |
| 手机分析 LOAD | 8 ms | 278 ms |
| 手机成品合成 LOAD | 260 ms | 566 ms |

LOAD 包含输入接收，PUBLISH 包含输出发送；不同任务也有重叠，不能把这些均值或总和相加推算整批时间。LOAD 不等于模型加载时间；本次没有底层模型加载次数或硬件 GPU 利用率采样。

在修改前，Windows 对同一鸿蒙中心的只读 HTTPS 健康请求测得：Wi-Fi TCP 建连中位约 9.5 ms，HTTPS 完整请求约 86.2 ms；USB 只读转发约 84.4 ms。消除 Wi-Fi 后固定开销依旧存在，提示 TLS 握手和服务实现是明确因素。该实验不能排除历史 Wi-Fi 吞吐、拥塞、温度的变化，尤其不能用小请求推断大图带宽。

确定的代码原因：原生服务对所有 HTTP 响应都强制 `Connection: close`，即使客户端允许复用也每次重建 TLS。执行、授权、图片传输、状态读取均承担这一成本。此外，ACTIVE 能力每次查询仍写回数据库，串行事务中的磁盘工作并不必要。

修复后同一 USB 通道、相同健康请求的复用微基准：

| 条件 | 16 次请求建连数 | 去掉首个请求后的中位数 | P90 |
| --- | ---: | ---: | ---: |
| 修改前，请求允许复用但服务强制关闭 | 16 | 80.6 ms | 116.0 ms |
| 修改后，服务支持顺序复用 | 1 | 10.8 ms | 11.4 ms |
| 修改后，故意每次新建连接的对照 | 16 | 77.3 ms | 87.9 ms |

这隔离验证了连接复用收益，**不是六张照片的加速结果**。测试没有通过 USB 执行照片。修复包括有界 HTTP keep-alive、每请求独立鉴权、空闲关闭、TCP_NODELAY，以及去除 ACTIVE 能力无变化写入、复用已读取的画像。

## 4. 链路差异：手机原图不应再绕回手机

历史 Windows 工作流使用 SDK 的 ORIGIN 输入登记和本地宿主读取。此前原生图入口一律返回 RELAY，手机即使已登记原图，也要上传给中心，再由源端分析任务下载回去。

本轮接入现有 LOCAL 协议：仅当请求指定 ORIGIN、根节点指定 ORIGIN_DEVICE 时，根节点在同一来源 App 宿主读取本轮 SDK 暂存的原图。规划器限制为相同 holder；该节点 transferPlan 为空。后续派生输入仍须经验证的产物传输，远端不预放测试图片或成品。

展示所需的输入上传仍保留；本次减少的是重复的计算输入上传及下载。完整的执行端产物保留、跨设备直传尚未全部移植，不能把本轮称为已与 Windows 数据链路完全等价。

两轮都是三个照片工作流的窗口。历史后半批在约 8.2～9.3 秒已提交；本轮后半批的分析任务约 12.8～17.5 秒才建立。前半批慢及结果接收会使后半批晚开始。本轮先修复确定的分配与连接开销，没有以无条件放大整批并发掩盖原因。
