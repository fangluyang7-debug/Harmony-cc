## 2. 为什么加 GPU 仍慢

### 2.1 没有持续给 GPU 和 CPU 供给任务

B 的每片执行约 0.97～1.08 秒，但片间空档为 1.426～6.192 秒。鸿蒙电脑最长执行空档 28.457 秒。首批四张 analyze 的最终规划在 0～0.240 秒内发生，部分 enhance 的最终规划却在 23.990～32.854 秒才出现。第五、第六张的 analyze 到 34.155、38.840 秒才开始规划：当前四图并发窗口受首批完成速度拖累。

成功 PLAN 的算法本体累计仅约 7.9 毫秒；这不含失败重规划、快照构建、SQL、准入和输入准备。将这 50 秒理解为“规划算法算得慢”不准确。

代码找到可复现的放大器：choose 会刷新整组快照，preflight 原先遇到任何 snapshotVersion 变化就返回 false。并发就绪节点和设备心跳互相使对方的计划过期，触发重试/重规划，即使最终设备、路径和资源仍可用。该轮成功快照从 49120 增到 49432，但未保留每次拒绝的历史；不能把所有 30 秒空档精确归因于这一项。新增的持久化诊断用于下轮区分这些等待。

### 2.2 GPU 每片重启、重载模型

旧 r2 GPU 分片每次 spawn 一个引擎，进程内读权重、创建 Vulkan 管线后退出。CPU 已有常驻模型，GPU 没有。业务中 5376 像素的小片仍约 971 毫秒，与 12544 像素的大块接近，固定启动成本明显；原像素线性成本曾将小片估成约 452 毫秒。

本轮本机 Intel Arc / Windows 隔离 8×6 原生测试：首调模型加载 936.767 毫秒，后续同模型新输入复用检查 0.0368 毫秒；再次运行约 1036.24 / 0.0511 毫秒。推理本身仍实际执行，不能据此声称 B 一定快同样倍数，更不能换算为整批加速比。

### 2.3 传输和控制有开销，但不是 50 秒都在传照片

| 记录阶段 | 跨任务累计 | 最大单次 |
| --- | ---: | ---: |
| OFFER | 6.407 秒 | 351 毫秒 |
| ADMIT | 6.208 秒 | 361 毫秒 |
| LOAD | 1.509 秒 | 163 毫秒 |
| PUBLISH | 9.640 秒 | 808 毫秒 |
| TRANSFER_RECV | 1.347 秒 | 158 毫秒 |
| TRANSFER_SEND | 2.900 秒 | 355 毫秒 |

这些阶段会并行、嵌套；TRANSFER 不应与 LOAD/PUBLISH 重复相加，发送/接收也可能是同一次传输的两端。LOAD/PUBLISH 包含控制及编码，不只网络。增强输入约 52～68 KB，片结果约 52～458 KB；最终聚合包约 0.9～1.39 MB，成品约 0.53～0.94 MB。记录不支持“图片太大或带宽不足是唯一主因”。

Trace 中 DELIVER 累计 175.747 秒是六个来源端任务从提交到收到结果的重叠区间，**不是纯下载耗时**。本轮不再使用 DELIVER 总和当网络耗时。

目前仍有必要的片结果中继聚合、成品回传和展示留存；来源端及同设备线性中间结果的复用保留。先解除调度重试及模型加载，避免在没有证据时改写传输协议或盲目扩大并发。

### 2.4 配额

实际回执电脑增强采用 8 线程配置，手机增强采用 4 线程，GPU 用 1 个 GPU 槽和 1 个 CPU 辅助线程；GPU 的 CPU=1 不等于只使用一个 GPU 核。这里不能再归因于“电脑只开单线程”。设备已存在长空档，提高上限本身不能消除这些空档。本轮未压低手机基线、未改变图像尺寸/模型/质量、未延长预算，也没有提前给电脑放用户照片。

## 3. 实现

- `services/coordinator/src/planning.ts`：最新快照重新规划，只在策略、合法性或实际选择/路径改变时拒绝；不因观测版本递增机械拒绝。仍是唯一 PlanningService → preflight → 原子准入路径。
- `cpu-jobs.ts` / `directory.ts`：把通过复核的快照与成本证据在 offer 事务内持久化；事务检查执行器完整 identity、当前额度和 grant ACK，避免同名目标换运行库时使用旧配置。增加 dispatchPreparationMs / dispatchReplans。
- `workflow-jobs.ts`：保存节点首次就绪时间、最近推进时间和阻塞原因计数；按已有串行游标合并写入，相同元数据不重复保存。既有跨工作流独立推进与去重保留。
- `services/pc-agent/src/executors/photo-workers.ts` / `photo.ts`：原生 Vulkan 使用有界常驻 worker，按模型版本、线程、后端和 GPU 编号隔离；只复用模型，输入/输出临时文件每任务独立。空闲最多 60 秒，取消杀掉对应 worker，等进程结算后再释放。
- `photo-core.h` / `photo-runner.cpp`：常驻 GPU Net；每次输入创建新 extractor；显式先清模型管线、再销毁 Vulkan，正常 EOF 和异常保持生命周期顺序。输出 modelLoaded / modelLoadMs / inferenceMs 用于原生检查。
- `host.ts`：GPU executorVersion 升为 2，引擎 identity 改变并重新资格/成本校准，隔离旧逐片冷启动历史。模型、任务契约和 executorId 不变，旧手机与鸿蒙电脑仍兼容。
