## 0. 更新规则

1. 本文件是项目进度的唯一记录（规格 R24）。每次提交后更新；用户明确要求时可另写 `HANDOFF-*` 交接快照，快照不作为第二份持续进度文件。
2. 只记录事实与证据，“来源”写明：`核对`（阅读代码确认）、`测试`（附命令与结果）、`记录`（来自历史交接文档，尚未复跑）。
3. 状态取值：`未开始`、`部分`、`已有实现（待复核）`、`完成-替身`、`待真机`、`完成-真实`、`冻结`；运行环境不可用时允许明确标注 `阻塞：模拟器不可用`。
4. 切片完成条件见规格 §10.0；工作包完成级别见规格 §0.2 第 6 条。

### 本轮修复的实际缺陷

1. 同一 attempt 换 messageId 重投时，按不可变 offer 比较并返回已有准入/回执；变更输入返回 ATTEMPT_CONFLICT，不重复启动引擎。YieldNotice 和 ProtocolError 持久化进 outbox，协调者记录让出信息；S6 重规划尚未实现。
2. 续期可能改变已选 offer 的额度版本。现在派发前的 grant/ACK 版本复核与 offer 持久化位于同一事务，等待准入的 OFFERED 期间不换新额度版本；暂不可用返回有界可重试原因，预算不延长。
3. 暂停贡献时原 PC 画像的 draining 与非零准入额度矛盾，导致校验拒绝。现在准入额度归零，已占用量保留到实际结算，不放宽 schema。
4. 已结算的失败回执此前只被保存为待对账证据，任务状态要等重连才变化。现在同一有效 fence 下的失败立即更新镜像，业务结果仍不提交；冲突终态被拒绝。取消/超时本身仍不释放资源。
5. 总入口首次在 CPU 宿主用例失败：任务 PUBLISH 阶段撞上 CANARY 继续参考评测时退回 CALIBRATING。已改为新鲜 CANARY 证据在追加评测期间保持有效；真实质量失败仍撤销资格，并补充正反例。首次失败的总入口日志不计为通过，以修复后最终组件结果为准。

## 25. 用户决定：设备间直连与签名传输授权纳入 S5（2026-11-02）

来源：用户确认。本节解除 §24 的暂停，并作为 S5 后续工作的执行依据；规格 §5.6、§6.1、§7.1.5 的对应细则在下一修订写入，写入前以本节为准。

### 1. 决定

1. 按规格 D6“控制与数据分离”执行：**协调者只下发计划、签名传输授权并接收核验回执；业务数据在设备之间直接传输；直连不可达时经已认证中继兜底。** 当前“全部经协调者中继”是阶段性实现，不是目标形态。
2. 撤回“暂缓独立 PC 数据端点、S5 只以中继完成”的方案。设备间直连与签名传输授权是 S5 的必做项。
3. 传输耗时必须进入同一 `PlanningService` 的成本比较（规格 §7.1.2、§7.1.5）：规划器在“本机执行 / 直连到执行设备 / 经中继到执行设备”之间按总耗时与期限选择。直连只是新的传输路径，**不新增派发路径**（R21）。

### 2. 实现内容（WP-D1 扩展）

1. **端点注册**：每台 PC 在本机生成并保存数据端点私钥；通过已认证控制通道注册地址、证书指纹、端点实例代次与能力，并用该私钥签名协调者下发的挑战值，证明持有私钥。禁止复用或转发协调者的私钥。
2. **签名传输授权，代替内存票据**：协调者为每次传输签发短期、一次性授权，至少绑定：任务与 attempt、制品 ID 与内容哈希、字节上限、操作（上传或下载）、发送方、接收端点及其代次、过期时间，并用协调者身份私钥签名。接收端点用配对时取得的协调者公钥验签，不依赖协调者内存。直连请求**不得携带长期设备或 App 凭证**（现有 `X-Device-Credential` 只用于与协调者的通信）。
3. **在线核验与撤销**：v2 要求在线，首版由端点在使用授权前向协调者在线核验“有效且未使用”；协调者或端点重启后代次变化，旧授权全部失效；与协调者失联时不签发、不接受新的传输授权。
4. **接收端身份**：协调者把接收端点的证书指纹写入传输计划，计划由协调者签名；发送方按该指纹固定校验。
5. **方向限制**：手机只主动连接。手机 ↔ PC 走直连（手机上传给 PC、手机从 PC 下载）；手机 ↔ 手机经中继，不在本轮实现手机监听。
6. **成对链路**：链路记录按设备对与方向保存（A→B 与 B→A 分开），来源为小探测传输与真实传输观测，带网络代次与有效期。端点验证通过且链路证据新鲜，才成为直连候选；否则只保留中继候选，中继的传输资源与成本照常计入。
7. **数据目录**：直连传输完成后，接收方核验哈希并向协调者发送回执，协调者更新副本位置；下游节点按副本位置规划。

- 【替身】两个**独立进程**，各自持有自己的端点密钥，禁止复用协调者证书或同进程鉴权闭包。
- 【替身】拒绝用例：假证书、指纹不符、错误接收端、跨 App、授权过期、重复使用、撤销后使用、端点或协调者重启后使用旧授权、携带长期凭证的请求。

- 【替身】改变成对链路的观测值时，规划器在直连、中继、本机执行之间的选择随之变化。

### 5. 网络环境自动降级与 AP 隔离（X9）

用户确认：自带路由器、PC 有线接入等**不保证有条件**。系统必须在任何网络环境下自动选出可用的最好方案；需要人工操作的改善措施只作为提示，不作为运行前提。

**5.1 自动降级等级（软件自动完成）**

| 等级 | 网络情况 | 系统行为 |
| --- | --- | --- |
| L0 全直连 | 所有设备对都可达 | 按成对链路成本在直连、本机执行之间规划 |
| L1 部分直连 | 部分设备对不可达（例如手机之间被隔离，手机与 PC 可达） | 可达的设备对走直连，不可达的设备对走协调者中继；中继成本计入规划 |
| L2 全部中继 | 设备之间都不可达，但都能连上协调者 | 全部数据经协调者中继；规划照常比较“本机执行”与“经中继远端执行” |
| L3 退出协同 | 设备连不上协调者 | 该设备按修订 6.1 退出 v2 协同：新业务回到原有本地调度，旧任务待重连对账 |

要求：

1. **可达性探测**：设备配对、重连、网络变化事件（手机已有网络变化监听）以及规划前链路证据过期时，探测“设备 → 协调者”和“设备 → 各 PC 数据端点”是否可达，结果写入成对链路记录（含不可达原因，如 `PEER_UNREACHABLE`、`TLS_MISMATCH`、`TIMEOUT`），带网络代次与有效期。
2. **等级只由探测事实决定**：不得在没有证据时假设可达；不可达的设备对不进入直连候选。网络恢复后，经新的探测自动回升等级。
3. **降级对用户可见**：局域网控制台显示当前等级、不可达的设备对和原因；追踪中区分直连与中继传输。
4. **降级不改变正确性**：任何等级下仍只经过同一 `PlanningService`、同一授权与账本规则；降级只改变可选路径和成本。

**5.2 人工改善措施（系统给出提示，有条件时由用户执行）**

控制台根据探测结果给出建议，用户执行后系统重新探测并自动升级：

1. 设备之间不可达、但都能连协调者（L1/L2）：建议 PC 改用网线接入路由器（多数 AP 隔离只阻断无线设备之间的通信），或使用可关闭客户端隔离的路由器。
2. 设备连不上协调者（L3）：建议开启 PC 热点，让设备加入。此时 PC 成为网络中心，手机与 PC 之间一定可达。首版只提供操作指引和带热点信息的邀请；是否由软件自动开启 Windows 热点，作为 X9 的调查项。

**5.3 替代链路只做调查，首版不实现**

Wi-Fi P2P（Wi-Fi 直连）、鸿蒙分布式软总线（仅鸿蒙设备之间，受账号与权限限制）、USB 有线网络、蓝牙（带宽低，只适合控制消息或很小的数据）。如果以后采用，只作为新的传输适配器接入，链路类型作为链路记录中的数据，由规划器统一计价，不新增派发路径。

## 32. 用户确认的启动失败修复方案（2026-11-03）

来源：用户审查意见、关键代码只读核对，以及用户对修订方案的确认。**状态：方案已确认，待实施、待验收。** 本次仅登记方案，不代表代码已修改或测试通过；§31 的全量 78/79 和失败证据继续保留。

目标：普通续租期间正常任务能够等待并恢复启动；重复启动或响应丢失时沿用原任务；资源不足、权限失效和版本不匹配仍须正确拒绝。执行顺序为：**诊断 → 恢复守卫 → 确认等待 → 按诊断决定是否换绑版本 → 并发启动与 SDK 恢复、错误分类 → 完整验收**。修复验收后接续原 S5 路线。

### 1. 诊断：分别记录额度变化和快照变化

资源额度（grant）的版本与计划快照的版本是两套独立编号。当前 `choose()` 调用 `profiles.refresh()`，刷新会递增快照版本；`preflight` 要求快照版本严格相等。其他任务提交、启动、画像或网络刷新都可能使计划过期。`replans` 同时被规划失败、预检失败和事务内版本冲突消耗，不能从 §31 的最终版本 33/34 推断“连续 8 次都撞上确认空窗”。

- 每次失败记录任务编号、宿主、阶段、错误码、重试次数、耗时和剩余预算；记录任务单额度版本、最新 grant 版本、设备确认（ACK）版本，以及规划和预检时的快照版本。
- 对快照刷新记录来源与关联任务/事件，区分任务提交、任务启动、设备画像和网络更新；保留有界的刷新关联记录，不能只用最后一次刷新解释多个并发变化。
- 协调者在内存中按宿主和版本关联签发至确认的耗时，清理过期记录，不写入 Reservation 持久化数据；不记录凭据或业务输入。
- 续租由设备发起。PC `AllotmentClient` 已单飞，鸿蒙主循环串行等待续租，不重复实现触发合并。先取得证据，不改快照递增规则，不预设续租是唯一根因。

### 2. 恢复守卫：已有执行安排不能退回重新规划

执行安排记录（attempt）保存选定宿主及任务条件；待发送消息记录（outbox）保存派发或恢复查询消息。存在这些记录不代表已经执行，也不能当成从未安排过。

- 统一带事务检查的重置函数：只有 attempt 和所有类型 outbox 均不存在时，才允许从 DISPATCHING 回退到 WAITING_INPUT。检查与更新在同一事务完成。
- 优先修复 `cpu-jobs.ts` 预检失败直接回退的分支；代次检查、额度校验失败后的回退也统一使用该函数。额度校验失败分支目前有事务回滚保护，不将其误记为同一种已证实缺陷。
- 在 WAITING_INPUT 入口检查既有执行安排，兜住旧缺陷留下的数据。检查 outbox 时包括已作废派发消息和恢复查询消息。
- 已有安排沿用已持久化的任务单，交给现有 outbox、recover/requestStatus 机制查询或恢复，不另建恢复路径；记录不一致时进入恢复检查，不直接宣告成功。
- 完整重启改变协调者代次时，现有代次分支已有守卫；重点验证同代次重入、并发启动及保存成功后状态更新失败，不能把所有崩溃一概归入预检回退缺陷。

### 3. 确认等待：拆开规划和额度读取，超时必须返回错误

将 `choose()` 拆为“生成计划并选择设备”和“读取已确认额度”。确认等待结束后只重读额度，计划是否仍有效继续由 preflight 判断，不因等待结束主动完整重跑规划。

- 只对明确的“当前 grant 尚未确认”等待通知，其他 PLAN_STALE 原因分别处理。
- 等待方先注册监听，再读数据库；`acknowledge()` 在事务提交后通知。唤醒后重新读取任务状态与额度，核验取消、期限和确认状态；通知只是唤醒提示，数据库是依据。
- 一次启动请求的累计等待上限取约 2～3 秒和剩余任务预算扣除余量后的较小值，预留后续数据库操作及返回响应的时间；两端 SDK 请求超时为 10 秒。每轮不能重新获得完整等待额度。
- 不持有数据库事务等待网络确认；处理通知遗漏、设备断线、取消和监听清理。
- **等待超时返回非 200、带明确错误码及 `retryable` 的响应，不能返回表示启动成功的等待状态。** 本轮没有后台推进，若 SDK 转入纯状态轮询，未启动任务将无人继续推进。只有核实尚未创建执行安排时，才能声明“尚未创建”；已有安排须走原恢复路径。

### 4. 可选优化：已确认的普通续租直接换绑版本

由第 1 步数据决定是否实施。若主要成本来自快照刷新，暂缓这条优化；它不替代确认等待或计划有效性检查。

- 仅在尚无执行安排、新 grant 已确认且原计划仍通过 preflight 时考虑换绑。
- 比较 groupId 及 allotmentId、deviceId、holderInstanceId、appInstanceId、ledgerEpoch、coordinatorEpoch、base、extra；身份、代次和额度内容均须保持一致，ACK 版本须等于新 grant 版本。leaseMs、leaseRequestId 可以随正常续租变化，但仍须遵守现有租约有效性规则。
- 额度版本不参与 executionDigest，只说明可以考虑换绑；`persistOffer` 对既有 attempt 比较完整 offer，不能借此修改已有任务单。
- 若在最终事务中换绑，需调整 `persistOffer` 的生成/校验位置，使任务单、消息 payload 和 `cpuJob.metadataJson` 在同一事务内保持一致。不能只修改版本号而遗漏消息内容。
- 等待和换绑后仍须经过最终事务中的 `apps.context`、`reserveJob` 及其他派发检查；权限撤销、额度缩减、目标或计划变化不得绕过。

### 5. 并发启动、SDK 恢复及错误分类

## 39. S5 实施方案：把已提交的中间结果直接交给下游（2026-11-03）

本节落实 §25 的直连要求，细化 §38 的唯一副本故障策略。状态为待实施。B 是生成结果的执行宿主，C 是下一步需要结果的宿主。首版在 PC 上完成正式链路。正常路径只传一份业务数据，从 B 到 C。B 保留原件，C 收到的完整结果可作为第二份副本。只有两者属于不同的已确认物理设备，才能算作可抵抗单台设备离线的两份副本。

### 39.1 先接通串行交付

1. **规划和保存输出。** 在正式工作流中由协调者设置生产端保留策略。将规划器的 `retainAtExecutor` 和选定端点映射到 B 的 `retainOutput`。为 execution/output 增加 RETAINED 交付方式，与 LOCAL、RELAY 并列。RETAINED 返回本次输出的完整描述与保留端点，PC 宿主按完整描述保存并校验字节，调用 `publishOutput` 登记位置，再照常提交执行回执。执行回执提交前，已存字节不能作为下游输入。保留原有来源私有输出与中继输出路径。
2. **判断上游完成。** 将 `graphOutput` 的图推进条件与发起 App 下载最终结果的 `outputTicket` 分开。图推进核对当前 attempt、已提交的成功回执、对应输出 ref，以及至少一份仍有效的位置证据（生产端、已确认的接收端、来源宿主或中继，按各自作用域核验）。副本暂时不可读时记录数据等待，保留已提交的执行事实。不得因缺少中继票据重新执行 B。
3. **准备 C。** 工作流提交时预分配的 jobId 只标识一个待办节点。等 C 的所有直接前置节点都已提交，按现有流程创建 C 的正式任务，把使用哪条数据依赖、生产者的 `sourceAttemptId`、完整输出 ref 和大小写入内部元数据。对这类内部数据边，CpuJobs.submit 直接使用父输出作为 C 的输入描述，保持 artifactId、版本、哈希、schema 和字节数一致，沿用硬期限。仅传哈希再生成 in-<jobId> 会导致目录查找失败。根输入继续按原规则创建。排序依赖不自动产生读权限。用同一规划器选择接收宿主、路径和端点代次。数据授权可以先于 C 的执行 attempt，但必须晚于 C 的正式任务和已保存的目的地选择。
4. **交付后启动。** B 获取一次性授权并推送。C 先完整落盘、校验大小和哈希，再用自己的身份向协调者确认。协调者持久化 C 的副本后，工作流推进 `start`，按实际副本重规划并经过现有额度确认、预检、attempt/outbox 和本地准入。保留输入就绪门槛。首版接受这些步骤串行，性能验收记录实际关键路径。是否值得把准备工作前移，留待测量后决定。

**把保留位置与传输操作分开。** B 的保留端点只说明字节在哪里。当前 planner.ts 为该副本固定设置 READ，首版 PC 推送需让同一规划器比较 B 所测的 WRITE 到 C 与认证中继两跳。直传分配必须保存 WRITE、B 的 holder、C 的 holder 和 C 的端点 ID/代次，用这条有向链路的新鲜观测计价。签发与核销按这份分配核对。只有 C 对 B 的 READ 可达证据时，不能据此选择向 C 推送。以后实现主动拉取时，再按 C 发起、B 监听的 READ 和相应通知机制独立选路。

### 39.2 两类上传共用传输实现，分别核验权限

保留现有来源 App 上传自己任务输入的 WRITE 范围。新增“交付已提交输出”范围，复用签名、在线核销、HTTPS 上传和完整性校验。协调者根据服务端工作流记录签发并在使用时复核以下绑定：

- B 的认证 holder、工作组、App 安装实例和所有者，B 当前已成功提交的 attempt、对应回执、完整输出 ref 与字节数。
- B→C 是该工作流声明的数据边，C 的 jobId 和输入确实引用该输出，C 仍处于允许准备输入的状态。签名授权应能无歧义地绑定生产者和下游，列明新增字段或签名版本并同步协议校验与反例测试。
- 直传的接收者必须是当前计划选中的 C，绑定 holder、设备、端点身份、证书指纹、端点和网络代次、协调者代次、操作及有效期。取消、撤销、换目标或换代次后拒绝旧授权。所有执行仍走现有派发入口。
- 消费者改派为 D 时，记录输出来源的 B attempt 继续用于证明数据血缘；实际读取端点可以是规划器选中的 B 或 C。由目录证明该端点持有同一 App 作用域内同一 ref 的完整、未失效且允许对外服务的副本，再授权给 D。当前 `localOnly` 副本只给本宿主读取。不得仅凭相同哈希或调用方填写的端点将其升级为可对外提供数据的副本。

**B 结算后怎样收到任务。** 首版采用已认证的 PC 宿主轮询。工作流推进在保存 C 的交付计划时持久化待交付项，以工作流、数据边、生产 attempt、输出 ref、目的地和计划版本标识。B 的控制循环调用新增的交付查询接口，只能领取自己当前 holder 和端点代次对应的事项。查询、申请授权和确认结果的路由按方法加入 allotment-client.ts 白名单。持久化事项只存交付意图，短期授权在领取后签发。重复轮询、响应丢失和协调者重启时按同一事项与回执对账。取消、到期、改派或 B 换代时作废旧事项及授权。交付只占用传输资源，已经结算的 B 计算 attempt 保持终态。同步更新 HTTP 契约、PC 轮询消费者及正反例；首版不新增 WS 控制消息。

**提交后的中继授权。** 已提交输出的交付范围包含两种计划目的地。走中继时，由独立交付接口验证同一父回执、数据边、所有者和剩余期限，再为 B 签发仅可将该 ref 写入选定认证中继的授权。中继核验后登记副本，C 按自己的读取权限取得数据。换路时旧目的地授权失效。B 不再调用终态 attempt 的 execution/output，协调者保留其现有终态保护。

### 39.3 副本的确认、保留和释放

区分一次性传输授权的使用期限、目录证据的新鲜度、制品可使用的硬期限，以及工作流的原始截止时间。现有 WRITE 回执登记约 30 秒，生产端登记沿用输入描述的硬期限（约一小时，不能从每次转交重新起算）。首版工作流预算最多 30 秒，WRITE 首次收货发生在工作流创建后。在同一协调者时钟下要求“首次收货时刻 + 30 秒 ≥ 原工作流截止时刻”，并检查制品硬期限覆盖所需使用时间。首版无需为工作流内的正常 WRITE 新增证据刷新接口。换代、撤销或确认缺失仍立即失效。超过工作流期限的最终结果领取使用单独的输出保留与授权路径。

B 在所有直接使用该结果的下游节点成功提交回执之前保留原件。分叉图逐个下游释放。同一份 C 副本若正供 D 使用，也应保留至相应依赖结束。终态失败、取消或工作流到期后清理已结束依赖，避免提前清理仍在使用的数据；进程恢复时按持久化工作流和回执重建待释放项。最终输出另保留至发起端确认完整取走，或到约定领取期限与制品硬期限中较早者。签发下载票据不等于已经取走。

**物理回收。** 为 B、C 和中继的缓存分别登记使用者。最后一项保留关系结束且无进行中的读写后，宿主幂等移除目录描述、内存登记和对应文件，回报释放结果；离线时记录待清理项，重启后补清理。并发分支和最终领取仍引用的文件不得删除。硬期限清扫只承担兜底。端点当前缓存上限为 128 MiB，规划器没有剩余容量观测。接收端应在写入时检查容量并通过认证通道报告 ARTIFACT_CACHE_FULL。B 无法保留时，若字节仍可用，在提交前评估并切到可用中继发布；C 已满时，中继也不能腾出 C 的磁盘，须先回收、改派或确认 C 能通过无需该缓存的路径消费。剩余预算内没有可行路径则明确返回容量不足。

**已有行为。** 在授权仍有效且端点代次匹配时，receipt() 接受 CONSUMED 或 COMPLETED，对同一 WRITE 副本键执行 upsert。重复确认不会产生第二条副本记录。当前实现会更新时间字段；新增交付事项、引用计数与硬期限须另验重复回执不会重复计数或延长硬期限。READ 成功目前只完成传输授权；将来支持手机拉取时，须由接收宿主保存、校验并确认本地可读后，才登记为手机本地副本。手机接收执行与宿主扩展本轮仅保留设计。手机到手机走中继时，也只有中继完整接收并核验后才多出一份完整数据。

### 39.4 断线、超时与早失败

每次失败先查已有完整副本。C 有可读副本即可本地继续。B→C 直连失败而 B 和 C 都能连认证中继时，按计划让 B 上传、中继验收、C 下载核验。两跳的带宽、时间和中继并发占用都计入同一规划与追踪。业务字节可以重复传输，执行 attempt 不随传输重试而增加。

若只剩暂时失联的 B，保留最后已知端点代次，等待期间关注重新登记、其他副本回执、取消与截止时间。用规划器已有的剩余关键路径估计决定最晚等待时刻，包含输入传输、排队、执行、后续依赖耗时和不确定性余量；已含在估计中的分量只计一次。剩余预算不足时立即复查其他合法位置。端点换代、制品到期或认证宿主明确确认本地数据消失时，立即作废对应 ref/端点/代次的位置证据。若再无可行来源，返回可区分的“制品不可用”及原因。失联本身不能证明磁盘数据已经消失。不通过自动重算已提交节点处理此故障。

授权只使用一次。发送结果不明确时先查已确认回执；仍需传输时，在原期限内取得新授权。无论第几次重试都校验完整字节。PC 端点目前把多类异常统一返回拒绝，需增加经认证、限定到本次授权与精确副本身份的缺失报告，才能安全处理 `TRANSFER_CACHE_MISSING`。普通超时、通用 403、未认证客户端的陈述仅影响链路判断，不能删除目录记录。

## 43. §42 循环等待修复与按需中继（2026-11-04）

### 实现

- `graphInput` 的生产端交付事项进入独立输入准备步骤；发生有授权关联的传输失败时，在原截止时间内调用同一 `PlanningService` 重新比较路径。计算 `start` 的输入就绪门槛保留，准备步骤不创建 attempt/outbox；数据库事务同时检查未派发、旧元数据未变化，并更新交付 ID、撤销旧未用授权。
- 宿主报告失败仅引用自己的授权 ID；已确认回执优先。失败不删除 B 原件或端点证据，也不重开已提交计算。当前任务通过规划请求排除失败的直传端点，中继上传及下载成本仍来自有向链路观测。规划保存两跳分项、剩余时间和可用中继槽位；额度与 dispatch/preflight 继续走原链路。

- 签名上传与普通中继上传/下载共用 4 个 HTTP 槽位；中继上传授权另有 4 项未过期保留上限，规划读取可用槽位并对两跳区间占用建模。容量拒绝发生在核销前，不烧掉尚未使用的授权。中继接收记录 TRANSFER_RECV，C 读取继续记录 LOAD，不把不同域区间相加冒充完整端到端。
- HTTP 契约见 `contracts/scheduling/v2/CPU-HOST-API.md`。本轮未增加依赖、修改 SDK/ArkTS 或接入云端；中继签名数据端点仅在主线局域网原生 TLS 启用，代理 TLS 模式保持不启用。手机主动传输/接收宿主扩展仍按 §39 保留待实现/待运行验证。
