# 鸿蒙协调中心照片性能回退：对比、修复与复测交接

日期：2026-11-13。当前源码分支：`codex/main-gpu-integration-20261112`，工作树含本轮与此前原生中心的修改，未在本轮提交或推送。

## 1. 实测结论

六张原图的哈希、尺寸（192×128）、顺序、模型权重和 180 秒预算已与 Windows 历史记录核对。原生中心存在性能回退，但历史轮次的网络、设备温度、冷热状态并非受控，不能把全部差值归因于操作系统或协调中心。

| 轮次 | 协调中心 / 实际计算设备 | 完成耗时 | 交付 | GPU 增强块 |
| --- | --- | ---: | ---: | ---: |
| `19176e53…` | Windows / 手机 + B | 17.687 秒 | 6/6 | 23/24 |
| `96a9586a…` | Windows / 手机 + 普通 Windows + B | 21.437 秒 | 6/6 | 19/24 |
| `fb05ef23…` | 鸿蒙电脑 / 手机 + B | 30.869 秒 | 6/6 | 19/24 |
| `93e84a85…` | 鸿蒙电脑 / 手机 + B | 25.808 秒后失败 | 5/6 | 不作成功耗时比较 |

原生成功轮次较 17.687 秒历史轮次多 13.182 秒，约慢 74.5%；首张交付由历史约 8.021 秒变为 13.129 秒。本次六张交付偏移为 13.129、14.992、15.210、29.703、30.181、30.534 秒，明显分成两批。

鸿蒙电脑本轮承担协调与展示，并未作为第三台计算设备。不能把“电脑作为协调中心”误写成“该电脑参与照片推理”。

## 2. 耗时证据与原因

### GPU 确实执行，但供给不连续

- 19 个 Vulkan 增强块的 EXECUTE 累计约 3.594 秒，单块平均 189 毫秒；从首块到末块的执行时间窗口约 19.570 秒。
- 同一设备、同一单调时钟域内合并重叠执行区间后，覆盖约 2.807 秒，最长无 EXECUTE 区间约 8.324 秒。这是执行器区间证据，**不是任务管理器或硬件 GPU 利用率读数**。
- 手机承担 5 个增强块，单块约 1.157～2.959 秒；分块几何不同，不能将均值比直接宣称为等任务 GPU 加速比。
- App 当前按在线执行设备数限制工作流窗口，这轮为三个照片工作流。首批的接收、合成及交付尚未释放窗口时，后续照片还没有全部提交；中心自身的阶段等待进一步放大空档。

### 传输和控制开销明显增加

| GPU 每块平均耗时 | Windows 历史 `19176e53…` | 鸿蒙本轮 `fb05ef23…` |
| --- | ---: | ---: |
| 接收输入 TRANSFER_RECV | 49.9 ms | 264.1 ms |
| 上传结果 TRANSFER_SEND | 109.7 ms | 319.0 ms |
| LOAD（包含接收输入） | 52.7 ms | 266.6 ms |
| PUBLISH（包含上传结果） | 211.6 ms | 561.9 ms |

LOAD 与 TRANSFER_RECV、PUBLISH 与 TRANSFER_SEND 存在包含关系；不同设备和分块也会重叠，不能相加作为整批墙钟耗时。LOAD 几乎全是接收输入，不应将它当作反复加载模型的证据。本次没有采集底层模型加载次数或显存利用率。

确定的代码差异包括：原生每个内部子任务多次事务、两次规划；工作流空轮询重复写盘；逐节点状态查询占用串行数据库队列；HTTP 分片接收每次重复制已收到的整个请求。原生仍通过中心中继中间数据，Windows 已有的源端保留和直传能力尚未完全移植。

### 规划估价和恢复存在缺口

- 原生按输入字节数 ×64 估算照片输出，曾把每块 PUBLISH **预测值**放大到约 6.6～20.9 秒。这不是实测网络耗时。
- 原生先过滤当前没有空闲资源的设备，没有完整比较“等待忙碌的快速 GPU”与“立即交给慢 CPU”的完成时间；也未接入已完成业务的成本反馈。
- 五图失败记录中，`858e8782…enhance-3` 收到明确的 `RESOURCE_UNAVAILABLE`，且 `record=null`。原生将该未准入拒绝直接作为整张照片失败处理。不是已完成的六张结果中仅漏显示一张。

## 3. 本轮已修复

1. **共用照片输出大小估算**：将 `photoOutputBound` 放入 scheduler-core；Windows 引用的 reference-capabilities 与原生规划器使用同一实现，按几何与编码上界估算，不再统一放大 64 倍。
2. **减少内部派发往返**：已存在中间输入的子任务在一次事务内规划、记录并入派发队列；去掉重复规划、再次绑定同一输入和无用写入票据。外部 SDK 接口仍保留。
3. **即时推进与批量查询**：收到回执或准入状态变化后唤醒工作流；200 ms 轮询仅作兜底。相同照片的节点状态一次事务批量读取，无状态变化不再重写完整图。启动后立即安排首次推进。
4. **线性 HTTP 接收**：头部有界解析，正文只分配一次缓冲区，按片写入；保留大小、二进制完整性及请求边界校验。
5. **忙碌快设备参与比较**：在新鲜在途占用、剩余时间和资源总量完全可核对时，使用共享规划器比较预计完成时间。若应等待 GPU，则等真实资源及派发额度可用后才发，不用预测释放真实配额。未知或不完整占用不假定立即释放。
6. **实测成本反馈**：匹配宿主、执行器身份、合同、配置、启动状态及有效时间，只采用成功且有执行追踪的样本；最近最多 8 个样本按 0.65 递减权重计算分位数，不挑最快记录。完整 EXECUTE 已含初始化时，不再额外叠加冷启动成本。
7. **明确未准入拒绝恢复**：仅对 `RESOURCE_UNAVAILABLE` / `CREDIT_UNAVAILABLE` 且无执行记录的拒绝，使用新尝试号有限重试、短退避；沿用原剩余预算。已接受兄弟节点和已交付结果不重算，其他拒绝仍如实报错。
8. **展示不挤占执行**：历史概要按修订缓存，保留实际设备名单；读取单张成品不再重复加载所有历史批次及全部设备画像。
9. **补充诊断**：本机只读 `/diagnostics` 提供有限数量的业务任务、回执及追踪，用于复测核对。执行记录新增创建、派发、接受、结算时间，以便下一轮准确定位协调中心内等待。

尚未将原生中心改造成 Windows 的全部直传/执行端保留实现，也没有修改手机的照片工作流窗口。若复测后空档仍主要发生于两批之间，应再优化提交与结果接收的流水重叠；不能绕过 SDK 另开计算入口，不能提前把输入或成品放到 B。

## 5. 用户复测

1. 鸿蒙电脑保持协调中心前台、服务开启，点击“图片任务演示”。
2. 手机和 B 保持同一可互访 Wi-Fi，重新连接这个鸿蒙协调中心；不要误连 Windows 中心。保留原配对记录，通常重连即可，若提示配对失效再用新的配对码。
3. 图片 App 恢复协作授权，等就绪后使用原顺序六张图。处理开始后才读取、分发本轮输入。
4. 等 6/6 成品交付后记录整批耗时及首张时间。建议连续两轮并记录是否为重启后的首次运行，不挑选最快一次。
5. 保留记录，不清空展示页；下一轮检查 GPU 分块数、最长供给空档、输入/结果传输及新记录的协调等待。
