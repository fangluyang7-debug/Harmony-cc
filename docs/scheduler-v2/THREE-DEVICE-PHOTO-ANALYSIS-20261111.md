## 已确认的瓶颈

### 1. 工作流推进过慢，计算资源没有尽早启动

以下均相对第一条协调中心 PLAN 的单调时钟，避免跨设备时钟相减：

| 事件 | 相对时间 |
| --- | ---: |
| 首次分析规划 | 0 秒 |
| 第一块准备规划 | 2.092 秒 |
| 首次增强规划（鸿蒙电脑） | 9.380 秒 |
| 手机首次增强规划 | 11.122 秒 |
| Windows 首次增强规划 | 14.287 秒 |
| 最后一块增强规划 | 18.446 秒 |
| 两张图的合成规划 | 22.455 / 23.627 秒 |
| 两张图的成品生成规划 | 25.612 / 26.527 秒 |

切块本身仅 9–117 ms，但增强直到约第 9.4 秒才开始进入分配。22 次 PLAN 区间合计仅 7.06 ms，因此不是规划算法求解花了数秒。源码 `services/coordinator/src/workflow-jobs.ts` 的全局 work Promise、逐工作流 progress、逐节点 await 数据库/状态/提交操作，与这种串行推进现象一致；SDK 还有 250 ms 状态轮询。具体数据库锁等待、状态传播和重试各占多少，需要新增计时，现有日志不能精确拆分这部分空档。

### 2. 配额与执行配置未充分利用设备

Windows 当前贡献上限 16 CPU 槽位，实际每个增强 offer/config 仍是 standard / threads=1。三个增强任务的执行区间有重叠，但没有用满 16 槽位。`services/pc-agent/src/executors/photo.ts` 将 config.threads 原样传入独立推理进程。

鸿蒙电脑当前 CPU 贡献仅 2 槽位，尽管内存贡献约 22.25 GiB。`NativeAgent.ets` 的 measured.cpuThreads 为 null，CPU total 使用 PRIOR 配额值，不能把这里的 2 当成真实硬件只有两个核。手机图片 App 当前执行身份也仅有 2 CPU / 1 GiB 配额。增强任务请求 1 CPU / 512 MiB；两份增强会占满手机当前 1 GiB 声明额度。实际决策中多次出现 RESOURCE_WAIT_UNKNOWN，但现有记录不能把每一次拒绝单独归因于 CPU 或内存。

### 3. 耗时预测明显偏低，且没有本机基线比较

初始每张工作流预测约 1.224 秒，实际每张 SDK 从提交到结果校验为 27.659 / 28.608 秒。初始 baseline=null。

增强执行预估与实测示例：鸿蒙电脑预估 284 ms，实测 1.774–4.028 秒；手机预估 647 ms，实测 3.498–5.936 秒；Windows 预估 1.303 秒，实测 3.631–7.783 秒。不同块面积不同，不能用这些范围直接排名设备速度；它们说明小样本先验没有准确反映业务块尺寸、冷启动与并发条件。单节点决策还标记 SOURCE_PULL_NOT_ESTIMATED，端到端成本缺项。

### 4. 网络有开销，但已有数据不支持把主要问题归咎于 Wi-Fi

已记录的 TRANSFER_RECV 累计 0.788 秒，TRANSFER_SEND 累计 0.793 秒；单个收发区间约 18–191 ms。它们不是完整链路网络总量，且 LOAD/PUBLISH 可能包含收发时间，不可重复累加。

22 个阶段的 OFFER 合计 1.462 秒、ADMIT 合计 4.861 秒、QUEUE 合计 0.789 秒、PUBLISH 合计 2.501 秒，均为跨任务区间之和，不是互斥的墙钟分解。必须另行测量关键路径才能精确报告占比。

当前合成仍由中心收集增强结果并打包，再交给手机合成；两张图合成后又转至 Windows 生成成品，再返回手机。该末端迁移增加了控制与数据搬运。两次合成输入包分别约 969 KB / 843 KB；最终成品容器约 1.12 MB / 0.83 MB。

注意：TraceSpan 中 DELIVER 的 27.659 / 28.608 秒实际 reasonCode=SOURCE_SDK_SUBMIT_TO_VERIFIED_RESULT，是源端完整耗时，不是“下载花了28秒”。

## 建议修复顺序

1. 为工作流就绪、领取、数据库读写/锁等待、输入准备和回执推进补计时；减少整组工作流串行扫描，独立就绪节点有界并发、回执到达立即推进，保持每个节点只提交一次。
2. 校准真实 CPU 核数、配额和 1/2/4 线程配置；联合选择分片并发数与每片线程数，不盲目让全部任务各自占满 CPU。修复手机业务 App 与调度 App 的资源配置不同步。
3. 对照片尺寸、含边缘重叠的实际推理面积、配置、并发度和冷启动建立成本记录；比较本机完成与协作的端到端预计耗时，不能以校准小图时长直接预测业务图。
4. 轻量切块和相邻阶段尽量同设备连续运行，减少小节点反复准入。优化合成汇聚位置，让成品生成尽量跟随合成或源端，避免手机→Windows→手机的末端往返。
5. 再用相同两张输入、相同模型和 180 秒预算做多轮交错对照；记录温控、并发和各设备 CPU 利用率，验证真正的端到端改善。
