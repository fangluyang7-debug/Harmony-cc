# 六张照片协同耗时排查（2026-11-11）

本轮分析实际运行记录和正在运行的安装版本，没有改变设备配额或重新执行用户批次。

## 结论

用户运行 `0db3945b-3e22-4e38-8350-e9a54b676a05`：6 张 192×128 原图，Real-ESRGAN x4plus，180 秒整批预算，成功耗时 **147,232 ms**；折算吞吐为 **24.54 秒/张**。这不是每张任务从提交到完成的独立延迟，因为 App 同时推进最多两张。

**66/66 节点、24/24 增强分片全部由手机执行，Windows 执行 0 个节点。** 这是手机通过协调中心完成的工作流，不能称为双机算力已经共同工作。电脑在线、已加入空间，不等于相关能力可执行。

最近本机轮次 `f0c37489-959d-4062-bb5c-503f043db715` 为 1 张、10,680 ms，输入为六张批次中的第 5 张。可确认协同链路存在显著开销，但 6 张批次平均与 1 张样本不是严格的同批次性能对照。

## Windows 为什么没有执行

实际安装身份对应 `135f0d80-e323-42d2-83cd-e9b9ed9e44ea`，处理器 Intel Core Ultra 7 155H，16 个物理核、22 个逻辑处理器。

| 项目 | 检查结果 |
| --- | --- |
| 所有者模式 | dedicated，自动容量 |
| CPU 贡献上限 / 当前准入 | 11 / 11 个逻辑槽位；不是 2 个 |
| 物理内存 | 约 31.50 GiB |
| 配置的空闲内存保留量 | 8,455,716,864 字节，约 7.88 GiB |
| 检查时系统可用内存 | 约 5.47 GiB，随系统负载变化 |
| 当前可接纳任务内存 | 0 字节 |
| 五项照片能力 | 全部 WAITING_RESOURCE |
| Windows 执行账本 | entries 为空，counter / settlementSeq 均为 0 |

`autoContribution()` 按总内存的四分之一设置保留量；PC 宿主随后用 `已占用协同额度 + max(0, 系统可用内存 - 保留量)` 得出内存准入上限。当前可用内存已低于这条保留线，因此即使 CPU 有额度也无法运行资格测试。采样时该 Windows 身份的 4,111 条评测回报全部 `notRun=true`，没有实际执行；照片运行中也没有该设备的执行回执。

当前资源快照不是历史逐秒内存曲线，不能把 5.47 GiB 写成任务开始时的测量值；但“本轮 Windows 无执行”和“当前内存门限阻止能力就绪”均有直接证据。

代码位置：

- `services/coordinator/src/spaces.ts`：`autoContribution()`。
- `services/pc-agent/src/host.ts`：动态资源上限与设备画像。
- `services/pc-agent/src/system-resources.ts`：系统资源采集与准入公式。

## 手机为何比直接本机模式慢

1. **有效计算设备没有增加。** 手机 App 协作额度仍为 2 CPU 槽位、1 GiB 内存；增强单片资源声明为 1 CPU / 512 MiB，最多并行两个。实际增强区间最大重叠数确为 2。本机 `PhotoLocal.ets` 也最多同时运行两个增强分片，不能把差距解释成“单机无限线程，协作两线程”。
2. **同手机节点间仍绕协调中心。** 照片图包含多输入合成 `inputFroms`，`workflow-jobs.ts` 当前据此对整个图设置 `forceRelay` 并关闭执行端中间结果留存；原生批处理没有声明 `inputLocation: ORIGIN`。本轮 66 个节点每个均记录了数据接收和发送，同手机连续计算未发挥本地数据复用优势。
3. **两张图竞争同一个手机额度。** `PhotoBatch.ets` 同时提交两张，但 Windows 无资格，两个 DAG 共享同一手机的两个增强槽位。直接本机路径在内存内顺序推进每张图片，无 11 个分布式节点逐次准入和往返。
4. **成本估计显著偏低。** 手机增强候选的 PRIOR 执行估计为 371 ms/片；24 个实际增强阶段平均 4,227 ms/片，约为估计的 11.4 倍。初始计划预计整图约 1.29～1.92 秒，实际 SDK 整图区间为 34.45～56.58 秒。需核对输入尺寸、模型冷启动、数据编码和实测成本回写，而非按小评测样本的常量做性能承诺。

## 建议修复顺序

1. **先恢复 Windows 可执行能力。** 将“总内存贡献上限”和“必须保持空闲的内存余量”分开表达；在当前约 5.5 GiB 可用内存环境，预留约 1～2 GiB 是可供复测的候选，仍按实际可用量限制并发。执行状态需显示“已连接 / 能力待就绪 / 可执行 / 实际参与”四种含义，RAM 准入为 0 时直接说明原因。保留人工固定策略，不能悄悄覆盖用户额度。
2. **同设备优先保留中间数据。** 延用现有 SDK 与 PlanningService，接通来源端本地输入；对多输入合成只在需要跨设备的边传输，避免因一个合并节点把整图强制中转。所有数据仍在点击开始后产生与传输，不提前在 Windows 放用户任务材料。
3. **细化阶段间计时并优化控制路径。** 测出输入准备、图推进等待、授权/资格请求、持久化、回执结算和最终捕获，再减少重复握手/写入/轮询；不能直接把不明时间归因网络后盲目改超时。
4. **更新成本估计与批处理并发。** 用尺寸/分片/后端及真实执行样本修正模型；根据当前真正可用的执行槽位决定同时推进几张。不要为了看起来分布式而强行把所有轻阶段拆到不同设备。
5. **最后测 CPU 配额。** Windows 当前 11 槽已经不是首要限制。恢复资格后再比较不同槽位/线程组合、模型加载与实际 CPU 占用，防止简单加线程造成内存和调度竞争。

下一轮应采用同一组 6 张原图、同一顺序、同一模型与质量、同一整批预算，各测手机本机与真正双机至少三轮；记录温控/充电状态、两设备分片回执、Windows 进程 CPU 时间及内存。报告成功和失败轮次，包含输入准备与传输，不复用预计算结果。现有结果不能宣称已经实现双机加速。

本机原始证据在忽略目录 `.test/perf-coop.json`、`.test/perf-local.json`、`.test/photo-performance-state.json`。只读提取了任务回执与资源状态；未修改运行账本、身份、配额和用户任务记录。
