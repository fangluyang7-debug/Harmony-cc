## 本轮修改

### 1. 结算回执立即修正旧画像中的占用

旧准入按最新画像 occupied 减去未上报 offer；即使收到已结算回执，仍可能被旧画像中的 inFlight/occupied 阻塞。新增 dispatch-capacity.settledProfile，为规划读取和原子准入提供一致的派生画像。

仅当画像占用与完整在途清单一致、仍新鲜，且持久化结算记录与该条在途工作匹配 attemptId、设备、holder、ledgerEpoch、target、资源向量和回执 fence 时，移除对应在途项并扣除其已结算占用。保留原始画像、序号、时间戳和原始信用额度，不写假心跳、不延长有效期；重复派生不重复释放。未知、过期、不一致及不同 epoch 的状态保留等待。

准入查询同时收敛到“未结算尝试 + 画像仍引用的尝试”，不再把所有已完成历史拉入每次派发检查。

### 2. 一片执行、一片提前排队

利用现有 Windows DeviceScheduler 微队列，无需 B 换包或新增 SDK 派发入口。仅对输入已经就绪、已通过正常规划/资格检查的 PURE GPU 工作，在预计等待不超过 2000 ms、预算仍足够且节点明确上报队列能力时，允许提前派发一个后继。

原子准入同时统计已报告在途、未上报持久 offer、已报告本地队列，按 attemptId 去重；同一独占 GPU 最多允许一个前驱加一个后继，第三个继续等待。设备端继续在前驱真正释放资源后原子准入后继，不同时占用同一 GPU，不绕过资源额度。App 全局预留及既有权限/租约仍生效。

最终 decisionEvidence 增加 admissionMode=IMMEDIATE 或 GPU_QUEUE，供下一轮确认是否实际使用预排队。CPU 路径和缺少队列能力的节点保持原有准入。等待预测不等于资源释放事实。

### 3. 优先完成较早照片，但不设置全批次屏障

工作流保存 submittedAt，节点只有实际输入准备好后才保存 dispatchReadyAt。相同 App、优先级、GPU target/holder 发生竞争时，如果更早提交的照片有最近 1 秒内确认输入就绪、尚未派发且预算有效的工作，先让该照片推进。

已派发、已取消、输入未就绪或就绪信息过期的工作不会占着该优先机会。其他照片的输入准备、分析和独立 CPU 工作仍可并行；不同 App 不受此顺序影响；REMOTE_BATCH 继续原公平批队列。目标是减少多张照片同时做一部分却没有完整成品的等待，不承诺总耗时必然下降。
