# 六张照片协同优化与复测（2026-11-11）

本轮在 `imageprocessing`、`cee4fa3` 基线上修改并部署到本机协调中心、Windows 执行器和手机图片 App。与只读诊断 [PHOTO-PERFORMANCE-20261111.md](PHOTO-PERFORMANCE-20261111.md) 分开记录；这里确实修改了运行配置并重新执行任务。未删除历史任务、重置账本或预计算成品。

## 保留的实现

1. `services/coordinator/src/spaces.ts`：自动策略的系统空闲内存保留量改为总内存的 1/16，限定 256 MiB～1 GiB。专用模式贡献 3/4 的逻辑 CPU，其他模式仍贡献一半。人工固定策略保留，实际准入继续受当前可用内存约束。本机实际为 16 CPU 槽、1 GiB 系统余量；内存贡献上限不是立即分配的内存，也不是某个批次的预约量。原来的 7.88 GiB 是系统保留线，不是六张图片的真实内存需求。
2. `PhotoSession.ets` / `NativeAgent.ets`：图片 SDK 与原生 App 宿主共用输入存储；`PhotoBatch.ets` 提交 `inputLocation: ORIGIN`。照片仍在点击开始后编码、登记、规划和传输，Windows 没有新增预放原图或结果缓存捷径。
3. `workflow-jobs.ts`：按实际数据边决定中间结果留存，不再因为图里存在一个合并节点就让整图强制中转。来源手机内的线性中间结果可本机读取；Windows 可使用现有执行端留存/直连能力。合并节点的直接输入仍需要中转物化；这部分尚未实现执行端本地多输入合并，不宣称消除了所有往返。
4. 图推进不再同步等待两次全历史缓存清理，已经派发的节点也不再反复调用启动；保留独立清理定时器、交付后的清理通知以及崩溃恢复。
5. `cpu-jobs.ts` 授权响应携带已检查的资格证据，原生执行器免去一次资格请求。旧协调中心仍可回退查询。ADMIT 计时现在包含授权请求，与旧记录的口径不完全相同。
6. `scripts/prepare-photo-runtime.cjs`：Windows ncnn 默认构建启用运行时 CPU 指令检测及 AVX/AVX2/FMA；可用 `--scalar` 构建基线。每片仍为一个 CPU 线程，分片并发由调度额度控制。未更换模型、放大倍数或精度策略。模型参考用例实测质量分数 1，门限 0.99。任务规模相近的 Windows 大分片由旧标量版本约 12～15 秒降到向量化轮次约 6～9 秒，受并发与系统负载影响，不能当作固定承诺。
7. `photo-runs.ts` / `dashboard-history.ts`：展示计时只读取当前批次尝试，避免将全空间历史追踪搬入 JS 后反复扫描。`retention.ts` 只查询与实际缓存对象有关的任务和尝试；未知对象仍保留到到期，不误删未结算依赖。
8. `apps.ts`：修复 App 额度检查的历史 N+1 查询。原先每次准入都读取所有历史预约，再逐条查询 Attempt 和 CpuJob；现在在同一个准入事务内用一次关联查询取得仍占用额度的工作。未结算任务即使过了截止时间也继续占用；已结算历史完整保留。这解决了重复演示后调度成本持续增长的一个确定问题。
9. `apps/runtime-desktop/desktop.js`：Windows 启动页刷新实际贡献配置，不再一直显示首次邀请中的临时“2 CPU / 1 GiB”。额度是上限，不代表所有线程已被任务使用。

## 真机方法与完整试验记录

- 同一组六张手机相册原图、同一顺序，均为 192×128；记录原始 SHA-256。协作时 PNG 重新编码的哈希与原文件不同，必须用 `originalHash` 对齐。
- 两条路径均使用 Real-ESRGAN x4plus、4 倍输出、相同图块划分与 180 秒整批取消预算。本机展示旧协议未上报预算/模型字段；本机预算依据当前 `Index.ets` 的实际取消逻辑，不能把展示中的空字段当作测量值。
- 手机 `wlan0` 与 Windows `WLAN` 同网，已观察到手机 Wi-Fi 地址到协调中心 7443 的实际 TCP 连接。USB 仅用于安装、布局读取和点击；没有使用 USB 端口转发传任务。
- 每轮实际执行新的 66 个阶段、24 个增强分片；没有通过历史成品跳过执行。模型可预装。业务素材随本轮任务传入执行器。历史展示预览不会成为 SDK 的任务输入。
- 手机插线、前台，Windows 同时承担协调与执行。未做恒温控制和随机化轮次，以下是工程复测，不是严格统计基准。

## 开销与 CPU 的实测证据

最终上述轮次的阶段累计：OFFER 3.825 s、ADMIT 13.898 s、PUBLISH 10.311 s；记录的接收 25 条 / 1.158 s、发送 37 条 / 2.420 s。原始轮次接收和发送各 66 条，合计 11.308 s。传输跨度包含请求处理等，不是纯 Wi-Fi RTT，也不能将发送、接收、LOAD、PUBLISH 重复相加。

在历史查询缩小、但额度 N+1 尚未修复的轮次，OFFER 累计为 15.968 s；修复后的 3.825 s 明显降低。不过这些轮次的分配、温控和系统负载不完全相同，不能把整批差值全部归给某一个补丁。跨设备单调时钟不能直接相减，并行执行累计不能当作墙钟时间；原诊断的 68.01 秒非执行余量也不能简单减去这些累计值。

Windows 进程采样实际捕获到首轮 13 个推理进程、向量化轮次 12 个推理进程。按各 PID 已观察到的 CPU 时间最大值求和，下限分别约 124.45 / 42.42 CPU 秒；样本可能漏掉退出前末段，不能当作完整能耗。观测到的最大工作集约 915 / 893 MiB。这既证明 Windows CPU 确实在计算，也说明不能因“图片小”就把单个推理进程的内存声明任意降低；后续需统一额度与进程峰值的统计口径。
