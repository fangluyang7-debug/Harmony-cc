## 3. 已确认的结构性问题

### 3.1 工作流并发仍有整轮等待

`services/coordinator/src/workflow-jobs.ts` 的 `advance` 把整组进度挂在共享 `this.work` 链上，一轮 `await parallelReady(active, progress, 4)` 完成后才进入下一轮。`progress` 内又等待就绪节点的 `start`；`cpu-jobs.ts` 的派发可包含准入确认、资源重试及最长 2.5 秒窗口。

因此，四图并行没有消除慢工作流对其他工作流下一轮推进的阻塞。一次节点状态 SQL 批量读取也只能减少查询开销，不能解除这一结构上的等待。

隔离本地探针 `.test/photo-r4-barrier-probe.cjs` 验证：一个工作流被挂起，另一个已完成本轮的工作流收到新通知，仍只执行 1 次；解除前者后才执行第 2 次。探针没有触及设备或真实业务。此结果证明实现存在等待机制，不等于已测得真机每一段空档都由此造成。

### 3.2 历史预测未进入本轮关键选择

24 个最终增强分配均为 `costSource=PRIOR`。r4 新增的完整 EXECUTE 样本确实写入成本观察，不是代码完全没生效；问题在于关键选择前没有足够可复用的同类样本。

- 照片契约没有专门 workModel，`workKeyV2` 使用压缩输入字节数的 log2 分桶，没有按实际推理像素与 halo 工作量建模。
- 本轮分散到 3 个设备、不同线程配置、多个字节桶；每类需至少 3 个样本。按任务存储的 request.now 检查，本轮选中设备对应的同桶样本只有 0～2 个。request.now 不是全部重规划的精确时刻，但实际决策保留的 PRIOR 证实未用上测量成本。
- 前一轮距本轮约 33 分钟，超过 10 分钟样本 TTL；更新重启后的校准代次也不同，旧窗口不能直接使用。
- 校准参考增强输入为 **8×6**，真实增强参数为 **96×96 / 96×32**，带 halo 后实际输入更大。当前先验没有将这种工作量差异反映到计算成本。

本轮预测对每个设备几乎固定：Windows 0.714 秒，鸿蒙电脑 0.214 秒，手机 0.638 秒。实际单片平均分别约 2.389 / 1.416 / 4.684 秒。

第四图三个分片选手机时，两台电脑都出现 `RESOURCE_WAIT_UNKNOWN`，候选仅剩手机；手机两个大片实际耗时 7.756 / 7.319 秒，小片 4.473 秒。低估计算成本、缺少设备忙碌剩余时间预测，使“短暂等待快电脑”和“立即交给慢手机”无法合理比较。

设备端还存在另一套 RunTimings：`packages/scheduler-core/src/ledger-v2.ts` 与鸿蒙 `core/LedgerV2.ets`。当 startup 为 UNKNOWN 时，历史键保留输入 contentHash；鸿蒙照片以 UNKNOWN 启动，所以不同真实图块难以复用剩余时间经验。它与中心新修的 computeHistories 不是同一链路，上一轮没有解决这部分。本轮增强最终决策中两台电脑共有 8 条 RESOURCE_WAIT_UNKNOWN 排除记录；这不意味着电脑不支持任务，也不能解释为物理上永久占满。

### 3.3 轻量步骤的协议成本远大于计算

每图 11 个独立节点，共 66 次节点派发。24 个准备图块节点：

- EXECUTE 合计 **1.297 秒**，平均约 54 ms；
- QUEUE 合计 **5.989 秒**；
- ADMIT 合计 **6.740 秒**；
- OFFER 合计 **3.111 秒**；
- PUBLISH 合计 **3.464 秒**。

这些切块全部在同一手机上，但仍逐个经完整调度、授权、落盘、回执和阶段推进。保持数据在本设备不等于消除了控制往返。更高批次并发使这些短步骤同时涌入，当前收益不足以覆盖新增竞争。

### 3.4 可避免的重复操作仍存在

- Windows `executors/photo.ts::infer` 每个分片重新读模型文件并算哈希，然后启动新 runner 进程。
- 两端共享的 `photo-core.h::photoInferFiles` 每次构建 `ncnn::Net` 并重新 `load_param/load_model`。鸿蒙虽然缓存模型文件准备承诺，仍没有复用已加载网络实例。
- `PhotoBatch.prepare` 编码 PNG，analyze 又解码/重编码；每个 prepare 解码同一原图；assemble 已生成完整 PNG，deliver 再解码并重编码完整 PNG。
- 增强分片汇聚仍经中心，随后手机合成；成品为展示回到中心。可考虑将已校验的分片直接汇聚到实际合成设备，展示仅取需要的预览/结果副本。
- `CpuJobs.choose` 在规划计时开始前强制刷新整组画像；提交、输入准备、正式派发可能多次调用。PLAN 的 15 ms 不能代表这部分成本已消除。

这些重复行为有源码证据，但现有 EXECUTE 未细分模型加载、纯推理、编码、临时文件 IO，所以不能虚构每项能节约几秒。

## 4. 建议实施顺序

1. **先解除整轮工作流等待。** 每个工作流独立防重入、独立事件唤醒；资源等待注册唤醒后返回，不阻塞其他图的下一阶段。保持元数据串行写入、唯一尝试、总账准入与已提交节点不重跑。增加“一个图等待，另一个图立即继续”的回归。
2. **让计算与剩余时间预测用同一种真实工作量。** 按模型/后端/线程/实际推理宽高和 halo 区分，压缩字节只用于传输估计。分别记录初始化、纯推理、编解码和发布；处理冷启动和有效历史不足。设备剩余时间不再因图片哈希不同而永远无数据。保留估计的不确定度和真正未知，不能凭空写固定快速成本。
3. **合并同设备轻量步骤。** 保留评委看到的逻辑步骤和逐阶段 trace，把分析与切块、合成与成品生成编成较少的执行单元，经原 SDK/规划器派发。四增强分片不变时，可评估每图 11 个派发单元缩至 6 个，六图 66→36；这是设计目标，尚未实现，不是实测节约比例。
4. **复用模型运行环境。** Windows 常驻有界推理 worker，鸿蒙池化模型实例；仅缓存已校验模型与执行器，不缓存真实任务输入或成品。不改变输入来源和任务开始后的传输证据。
5. **随后调线程数和并发窗口。** 根据设备当前负载、每片资源及慢图拖尾动态补充就绪工作，不再把“设备数+1”当成充分性能策略。先修等待和预测，再以同顺序、同图、同预算对比 2/3/4 窗口与不同线程/worker 组合；单机基线同样使用优化后的内核。

持续监控应补充每设备实际 CPU 时间/利用率、内存峰值、热状态与频率（取不到标 UNKNOWN），以及阶段完成到下一阶段调度、等待原因和队列长度。没有这些观测之前，不承诺具体加速倍数。

本轮诊断完成，应用保持用户测试后的状态，未自动启动新任务、未推送 GitHub。
