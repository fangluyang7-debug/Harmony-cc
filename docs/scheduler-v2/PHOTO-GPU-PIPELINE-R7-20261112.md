## 代码修改

1. **候选检查与资源排程采用同一剩余时间预测。** 之前 DeviceDirectory 给 snapshot.inFlight 补了已准入任务的剩余预测，但 availability 仍读取原始 UNKNOWN，规划器把忙碌 GPU 直接排除。现在同一作用域、未过业务截止、具备新鲜 elapsed 的 PURE 工作，可用已准入计划生成 PRIOR，并同时供两处计算使用。不改原始画像、不提前释放实际资源。过期的非空完成预测也重新估计，避免变成无限占用；预测执行时长扣除 policyQueueMs，避免把已等过的队列再加一次。
2. **GPU 待执行队列扩大。** 从最多一个运行加一个等待，改为最多一个运行加三个等待。预测等待仍不超过 2 秒，受原任务预算约束；宿主已知未结算总数达到 7 时不追加，兼容现有 PC agent 的 8 个 pending 上限。只在输入已就绪、GPU 队列可观测、单任务资源可容纳时派发，设备实际执行仍经原子账本，未增加 GPU 同时执行槽或伪造显存。
3. **不混淆空闲执行名额与队列容量。** 立即运行仍需要 category credit；GPU 正在执行导致空闲 credit 为零时，可以依据独立队列检查接收后继任务，避免 GPU 每结束一块都等一个完整往返。
4. **GPU_QUEUE 不再因首张优先退回重规划。** 队列已经获准时直接填充，立即可执行的 IMMEDIATE 分块仍保留首张成品优先。CPU 独立工作不受此规则约束。

改动仅在 `services/coordinator/src/directory.ts`、`services/coordinator/src/cpu-jobs.ts` 及相关回归。仍通过现有 SDK/规划器/工作流链路；不指定 B 的设备 ID、不强制全部任务上 GPU，也不改变模型、照片、画质与预算。等待 GPU 的预计完成时间更短时，它应继续成为合法候选，真正的长队列仍允许 CPU 更早完成。
