# 六图仅交付五张：结果接收超时修复

分支 imageprocessing，基于 r5，2026-11-11。用户批次 `dabdefa2-8957-4143-8639-2048bd8391cf`：39.839 秒后 FAILED，错误 `照片 12：Operation timeout`。原始历史记录未修改、未重跑业务照片；精简证据见同名 JSON。

## 实际发生了什么

六个工作流全为 SUCCEEDED，36 个执行节点全部成功。24 个增强图块由鸿蒙电脑完成 13 个、Windows 完成 11 个；源端手机完成分析和成品合成。

未交付的是 imageIndex=3（本轮第 4 张，名称“照片 12”），不是按照片序号计算到第 5 张后停机。其他五张有 `resultReceivedAt`、展示留存文件和交付记录；该张没有源端确认，也没有展示留存文件。失败时 180 秒预算还未耗尽。

现有错误文本没有请求路径，无法回溯精确区分该张的状态轮询、结果读取、展示留存哪一个 HTTP 请求超时，更不能据此断言纯网络带宽导致。本机 NativeTransport 每请求连接/读取超时为 10 秒。已定位的代码缺口是：SdkTask.result 任一次状态/结果/留存网络错误会抛出，PhotoBatch 立即将该图记失败并取消任务，没有用同一个 task 恢复取结果。已计算成功不代表手机已交付。

## 修复

- `apps/harmony-photo/entry/src/main/ets/PhotoRecovery.ets`：仅对 Operation timeout / timed out / TIMEOUT / HTTP 502/503/504 进行有界恢复；最多两次重试，250/500 毫秒退避，检查取消和原批次剩余预算。
- `PhotoBatch.ets` 在同一个 SdkTask 上恢复 result，重新获取状态与结果票据；不重新 submit，不换 workflow/attempt ID，不重做增强。完整性、授权和实际任务失败仍直接报告。
- 展示记录 POST 超时可能已在服务端完成：再次写入前读最新 revision 和 jobs，合并同一任务关联，避免重复 jobs 或后续全部版本冲突。终止记录允许完成清理请求，不因此延长计算预算。
- `PhotoSession.ets` 增加 `PHOTO_OUTPUT_READ` 与 `PHOTO_DISPLAY_CAPTURE` 错误上下文，便于下次区分结果读取和展示留存。不会吞掉留存错误后谎报交付完成。
