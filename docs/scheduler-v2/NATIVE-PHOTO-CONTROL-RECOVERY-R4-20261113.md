## 3. 确定缺口与修复

### 手机错误地用控制连接状态阻断所有 SDK 请求

旧 PhotoSession 在 WebSocket 短暂断开时，连已有任务的 HTTPS 状态查询、结果确认和取消也一起拒绝；PhotoBatch 将这一提示视作最终错误。这造成手机报失败、后台继续计算的状态分裂。

现在只有新建任务和启动任务检查控制连接；已有任务仍可通过已授权 HTTPS 查询、取消和确认结果。已规划任务的启动在 SDK 内按原 ID 等待短暂重连，最多沿用既有启动等待窗口，不重新规划或上传输入。新建前的明确离线拒绝可在整批剩余预算内重试；不重试未知结果的提交请求。结果传输连接错误也可在原剩余预算内恢复，不重新计算已完成图块。

整批仍为 180 秒并保留用户取消；重试不重新开始手机计时。提交请求的 ID 与请求体保持一致，避免幂等指纹变化。不是通过延长演示时长或隐藏失败解决问题。

### 鸿蒙中心的心跳帧等待数据库业务消息

旧 CoordinatorSocket.receive 在处理每条业务消息时等待数据库事务，再解析后续帧。业务排队会使已经到达的 Pong 也无法及时处理。Windows 中心使用独立 Pong 回调，不存在这条相同的串行等待链。

现在帧解析和 Pong 响应不等待业务处理；业务消息仍严格串行，队列有界，解析或业务错误仍关闭对应连接。未放宽心跳超时来掩盖问题。故障注入已证明：阻塞业务处理时，后续 Pong 能立即被消费，而业务顺序不变。

加入第三台计算设备会增加业务消息和批次并发，可能放大原缺口。但缺少失败时各设备逐帧网络记录，不能断言历史每次掉线均由此引发，也不能宣称排除了 Wi-Fi 的客观影响。

### 未准入任务的恢复缺失

- 重连查询返回空记录时，原尝试仍为 OFFERED、中心也无准入记录、同一 epoch 且未过截止时间，中心重发原始 DispatchOffer，保持相同 attempt ID；由执行端账本去重。
- 已经有准入记录、结果不明的情况仍报告 HOLDER_RECORD_MISSING，不凭空创建新尝试。
- 明确未准入的 COORDINATOR_OFFLINE、AGENT_NOT_READY、CONTROL_UNAVAILABLE 纳入已有有界重试，沿用原工作流截止时间；拒绝策略和用户主动取消不会无限重试。

安装后的启动检查还暴露出历史状态残留：两个失败轮次的交付节点已在 CpuJob 标为 HOLDER_RECORD_MISSING，但 Attempt 表仍为 OFFERED。这会使额度续租一直被 DISPATCH_ADMISSION_PENDING 拒绝。现在恢复处理同时更新两个状态，保留原记录；不通过删除账本或清除配对解决。回归检查这一状态一致性。中心日志增加额度拒绝原因码及未支持路由，避免只留下笼统的 ALLOTMENT_REJECTED/HTTP_503。

- 原生中心、SDK、手机图片与展示相关 156 项回归通过；随后扩充控制拒绝原因的覆盖，照片引擎 9 项再次通过。
- 新增故障注入：数据库业务阻塞期间 Pong 不阻塞；业务顺序、错误关闭、有界队列；手机断线仍能查询/取消/确认已有任务；六图提交前短暂离线后无重复提交；已规划任务重连仅启动一次逻辑任务；未准入重发与已准入缺失的区分。
- 两个已有测试夹具遗漏现行设备资源字段/limits 方法，已补齐夹具以匹配真实接口，没有为通过测试删改业务检查。
