# 设备选择策略分支与真机对比

2026-10-28 更新：本页保留原实验版本的分支和测试说明。`codex/scheduling-data-pipeline` 已修改样本键、持久化统计、校准配额和质量评测；新版本的行为、迁移步骤与校准入口见 [调度数据管道修复与校准接入](33-调度数据管道修复与校准接入.md)。新一轮对比使用同一构建切换 `SCHEDULING_SELECTION_POLICY`，下文“重启清零”“30 秒有效期”等旧边界不适用于全部新路径。

日期：2026-10-24。三条实验分支从同一个提交开始，使用相同的执行、采样和授权代码，区别是默认选择策略。原分支 `codex/complete-scheduling-chain` 保留原实现。

| 分支 | 默认策略 | 什么时候选择其他设备 |
| --- | --- | --- |
| `codex/scheduling-cloud-baseline` | `CLOUD_BASELINE` | 沿用现有规则：以基线为参照，完整估计成本节省超过规划器默认 15 ms 门槛，且通过后续授权 |
| `codex/scheduling-peer-fastest` | `PEER_FASTEST` | 在搜索得到的合法方案中选估计成本最低者，取消 15 ms / 10 ms 收益门槛；即使云端没有合法方案也可以选择其他设备 |
| `codex/scheduling-background-calibration` | `BACKGROUND_CALIBRATION` | 正常请求沿用云端优先；显式后台裁剪测试可以指定设备，不要求它已经比云端快 |

这里的成本包括输入传输、执行、排队、输出回传及现有不确定性项。它是模型估计，不是实测保证；平等竞争仍使用有候选数量、搜索宽度和规划时间限制的搜索，不保证全局最优。原有基线选择在没有云端候选时可能选择其他设备。

## 切换分支

先保存本地修改，再在仓库根目录运行其中一条命令，并重新构建、重启后端：

```powershell
git switch codex/scheduling-cloud-baseline
git switch codex/scheduling-peer-fastest
git switch codex/scheduling-background-calibration
```

分支默认值在 `scheduling-selection-policy.ts`。`SCHEDULING_SELECTION_POLICY` 环境变量可以覆盖默认值；按分支测试前应清除旧覆盖，否则切分支后可能仍运行上一种策略。非法值会报错。

## 后台测试怎么调用

这是服务端测试入口，不是新增的公共 HTTP 接口。真机测试程序在已有 `RuntimeWorkScope` 中调用 `DeviceDispatchService.dispatch()`，沿用已有真实图片 artifact、裁剪参数、云端执行器和手机适配器，在调度上下文中显式传入：

```ts
{
  budgetMs: 60000,
  userWaiting: false,
  importance: 0,
  networkAllowed: true,
  privacyLevel: 'AUTHORIZED_REMOTE',
  calibrationDeviceId: '实际设备ID'
}
```

只允许一个 `image.crop.v1` 任务。手机适配器通过 `PhoneDispatchService.cropAdapters()` 获取，和现有购物裁剪入口一致；不能用伪造候选或虚构带宽代替实际设备。测试应使用可重复的测试图片，不自动重放购物业务流程。

后台测试不要求已有速度样本数达标，也不要求 `nonInferiorityPassed` 已为真，因为这些正是测试要建立的速度证据。仍要求有效的 ACTIVE/CANARY 配置、关闭 kill switch、质量已通过、设备及能力在允许列表中、失败率合规、预算足够和网络传输已授权。每个服务实例中，每个用户与设备组合最多执行 5 次，失败也计数；服务重启重置。这是实验配额，不是跨进程的生产限流。

`qualityPassed` 必须通过独立验证确认，不能仅为了跑通测试而填写。后台测试得到的速度样本不会自动批准生产灰度：普通请求仍使用原有完整灰度门禁。

## 链路与冷启动边界

- 手机候选已有 `coordinator-roundtrip` 成本，包含完整往返，不依赖 Worker 的独立链路样本。
- 普通 Worker 仍需真实上传/下载链路。初次测试可以用现有 `calibrate()` 对同设备、同大小分桶和同参数做三次真实校准，随后立即执行对比；或者由调用方提供有效的实测 `context.links`。没有链路时拒绝派发，不把猜测标记为实测。
- 三个分支都补齐 `executeOnWorker()` 的上传/下载采样，分别在哈希验证通过后记录。完成三次匹配传输后，通用派发可以继续更新链路数据。
- 为了单独比较设备选择策略，本次没有改变 30 秒链路有效期、参数分桶、成本先验或质量评估。后台策略尚不是自动链路探测系统，也不是全自动探索算法。
- 云端不可用且远端授权失败时返回 `NO_AUTHORIZED_PLAN`，不会把未批准的远端当作回退方案执行。

## 真机对比方法

1. 固定图片、裁剪参数、设备、网络和预算，用三条分支轮换测试。各轮使用等价的初始样本库，避免后测分支借用前测分支的数据获得不公平优势。
2. 分别测试：刚启动无成本样本、已有样本、网络变慢、云端无容量、链路闲置超过 30 秒。保持质量准入证据一致。
3. 从调用前到返回/抛错，用 `performance.now()` 记录总耗时；记录图片字节数、设备 ID、成功/失败和错误码。Worker 的 upload/download/compute 样本分开记录，手机当前记录完整往返。
4. 对照 `RuntimeWorkScope` 的 placement 记录：`actualDeviceId`、`reason`、`estimatedMs`。估计值和实测值分列；授权回退时，placement 中的估计可能仍来自原建议，不能当成实际设备的测量值。
5. 比较端到端中位数、P95、失败率、设备选择比例以及启动校准耗时。样本少时保留逐次记录，不根据五次试跑宣称稳定 P95。

关键原因：`PEER_FASTEST_LEGAL_PLAN` 表示平等竞争建议；`BACKGROUND_CALIBRATION` 表示指定设备测试；`PLACEMENT_ROLLOUT_BASELINE` 表示最终授权退回基线。`CALIBRATION_TARGET_NOT_FEASIBLE` 可能来自质量、容量、链路或预算，需结合设备状态及 planner 检查定位。

## 自动验证

在 `services/api-server` 下运行：

```powershell
npm run build
npm run test:unit -- --runInBand scheduling-selection-policy device-dispatch.spec macro-dispatch-workflow workflow-placement-planner
```

覆盖小幅收益时两策略的区别、云端不可用、后台选择较慢设备、前台禁止校准、预算/隐私/质量约束、传输采样、试跑配额和授权失败。单元测试使用模拟设备，不代表已经完成真机传输测试。
