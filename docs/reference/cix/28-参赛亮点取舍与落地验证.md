# 参赛亮点取舍与落地验证建议

日期：2026-09-17。以下是拟议增强项，不是已实现能力；不构成晋级保证。承接通用框架定位，购物仍是验证插件。

V2 阅读说明：本文件保留前期亮点取舍讨论。团队已将“端云技能编译”纳入主创新，本文的证据驱动验证、证据包及实验台改为支撑机制；当前范围与实施优先级以 [作品设计 V2](26-参赛作品设计-通用端云协同Runtime.md) 和 [架构 V2](27-端云模型分工与项目架构图.md) 为准。下文“两个主亮点”等表述为当时方案，不代表最新优先级。

## 1. 判断与推荐

目前方案具备赛道契合度和已有代码资产，但“任务图 + 端云路由 + 故障恢复 + 控制台”作为初选叙述仍较宽泛。建议将核心主张聚焦为：

> 在 CIX P1 上先处理和检查证据，围绕尚未解决的问题选择下一步计算，并只向云端发送完成该步骤所需且被允许的数据。

建议新增或深化 **两个主亮点 + 一个验证展示能力**：

1. 证据不足驱动的端云调度：明确何时上云、为什么上云，以及何时该补充输入而不是继续调用模型。
2. 面向任务的最小证据包：明确上云发送什么，在输入充分、允许出端的条件下减少无关图文。
3. 可重复的端云实验台：通过固定数据、故障注入和策略对照，展示上述设计实际带来的结果。

这里的“最小”表示按规则裁剪到任务所需范围的工程目标，不是数学最小性证明。这些是拟验证的系统设计差异点，不声称是全球首次提出。

## 2. 哪些是基础能力，哪些值得成为主张

| 项目能力 | 定位 | 如何表达 |
|---|---|---|
| Agent 任务图、工具调用 | 基础能力 | 满足任务规划与执行要求 |
| 持久化、检查点、重试 | 基础能力 | 支撑端侧可靠执行，不单独当算法创新 |
| 资源感知与模型路由 | 框架能力 | 结合 P1 本地工具与云模型实际观测 |
| 端侧模型实际推理 | 赛事平台落地能力 | 说明具体模型、工具、运行时及基准 |
| 证据不足触发有针对性的追加任务 | 主亮点一 | 计算围绕未解决的问题分配 |
| 动态构造允许出端的证据包 | 主亮点二 | 调度同时管理执行位置与传输内容 |
| 异常、对照实验与决策原因展示 | 支撑证据 | 使框架收益可检查、可重复 |
| 第二插件 | 通用性证据 | 新业务只新增工具与验证规则 |

已核验的相邻能力：LangGraph 官方文档列出持久执行、流式输出与人工介入等能力；LiteLLM 官方路由文档包括延迟／成本等路由和失败回退。由此只能得出这些基础能力已有成熟实现，不能推断其他项目都不具备本方案的组合能力。

参考：[LangGraph](https://docs.langchain.com/oss/javascript/langgraph/overview)、[LiteLLM Router](https://docs.litellm.ai/docs/routing)。本轮不是完整论文检索或专利新颖性调查。

## 3. 主亮点一：证据不足驱动的端云调度

### 展示行为

用户找同款鞋。本地完成图像检索后，面对不同结果采取不同动作：

- 款号、配色、尺码和报价来源足以满足目标：本地结束相关判断，不追加云视觉复核。
- 款号资料相互冲突，但已有图像和文本可供判断：请求云模型对冲突点进行有针对性的复核。
- 图片模糊且缺少必要细节：请求补图，不反复付费让云模型猜测。
- 候选没有 42 码或报价已过期：查询合法数据源或报告未知；不能靠语言模型补出库存和价格。

### 实现边界

由插件提供业务验证器，输出通用结构：

```text
VerificationResult
  status: sufficient | insufficient | conflict | unavailable
  unmetRequirements[]
  evidenceRefs[]
  suggestedToolIds[]
  allowedDegradation
```

Runtime 负责限制工具集合、预算、重规划次数、数据政策和实际执行。购物插件负责“哪些字段足以确认同款”等领域语义，不将鞋类规则写死到 Scheduler。

首版采用明确规则和固定结构，设置至多 2 次业务重规划作为起始配置。云模型可提出后续步骤建议，但仍须通过本地工具契约和政策检查。

不要把 Top-1 相似度直接当成正确概率，也不要采用未经校准的“置信度低于 0.8 就上云”。有标签集后可以校准阈值，但模型自报 confidence 不构成最终正确性证明。

### 验证方法

比较同一套模型、工具、商品快照下的两种策略：固定执行云复核，以及仅在验证结果要求时复核。固定云复核基线仍必须保留数据政策，不能通过违反政策换取对照结果。

记录：总任务完成率、同款判断错误率、未确认率、平均云调用次数、结果延迟。必须同时报告质量，不能用更多漏判或提前拒答换取“云调用更少”。固定本地和固定云端策略可保留为补充基线；本项消融以固定混合流程为主要对照，减少模型差异干扰。

### 交付与退路

改造点：AgentRuntimeService 的图修订接口、插件验证器、后续节点失效与重用逻辑。难度相对中等，前提是 DAG Runner 已真实驱动工具。

如果自由重规划不稳定，收敛为三条经测试的恢复分支：云复核、补充数据、请求用户输入。明确标记规则路径与模型生成路径，仍展示一次真实模型规划。

## 4. 主亮点二：面向任务的最小证据包

### 展示行为

端侧先从图片中得到商品区域、候选与相关属性，再将当前复核需要的内容整理为云请求：

```text
当前问题：候选 A 与 B 是否为同款同配色？
允许上传的商品区域图
少量候选的款号、配色及来源引用
当前未满足的条件
期望输出的结构
```

用户整段对话、整张场景图、全部商品库和个人偏好不因调用方便而默认上传。云规划阶段与云视觉复核阶段使用不同请求模板。

控制台可并列展示“输入资料、实际发出的证据包、发送原因、请求字节”。这些值由真实请求记录，不用编造节省比例。

### 实现边界

增加 `EvidencePackBuilder`，复用图像裁剪和候选检索。依据当前节点需求、Artifact 出端政策、数量／尺寸上限构建请求；记录变换版本、来源和遗漏字段。

首版只做确定性裁剪、候选条目筛选和字段白名单。无需增加一个专门的压缩大模型。必要细节被裁剪掉时，验证器请求更充分且允许上传的资料；不能用更小数据包牺牲问题可回答性。

裁剪不等于匿名化，向量也不天然不含敏感信息。只可声称“减少无关数据传输”和“执行已配置的出端政策”。对于 local_only 输入，构造器不能通过重命名或压缩绕过限制。

商品相似检索索引继续采用兼容的 embedding 模型及预处理。裁剪图发给云 VLM 复核，并不要求云 VLM 与本地 embedding 共享向量空间。

### 验证方法

在独立、允许出端的测试样例上，用同一云模型比较完整允许输入与证据包输入：请求字节、模型返回的可用 token 统计、复核准确率、信息不足率、端到端延迟。

图像字节减少不等于 token 费用按相同比例减少；需依据服务实际计费与返回用量核算。测得的请求体大小也应说明是否包含 base64、协议开销，不能将文件大小当网络总流量。

### 交付与退路

改造点：EvidencePackBuilder、云调用网关、Artifact 元数据和控制台请求详情。相对难度低到中等，取决于既有裁剪／候选服务可用性。

若自动主体检测尚未适配 P1，可先人工框选；若证据包降低质量，就放宽允许发送的资料范围并标注结果，不宣称必然带来收益。

## 5. 验证亮点：端云实验台

提供三项预设实验：

1. 同一查询分别运行“固定混合流程”和“证据驱动流程”。
2. 注入明确标注的云超时或限流，观察后续路径、未完成步骤和恢复。
3. 修改预算，观察只失效筛选／排序相关节点，图片特征仍被复用。

控制台展示实测值、数据来源、决策原因和任务图修订。节点结果没有实际执行前不得展示成功；未执行候选仅可显示估计，必须标注估计依据。

不得在一条真实运行轨迹旁虚构“假如全走云”的收益。需要另一条实际基线轨迹；离线重放只是回放，不冒充实时运行。

这项能力复用已有 SSE 和调度盘，不增加一套新的业务产品。框架演示最应让人看见：同一任务为什么走了不同路径，以及这种变化的实际结果。

## 6. 建议冻结的首版范围

| 分类 | 范围 |
|---|---|
| 必做基础 | 一个真实 DAG 执行闭环、持久化状态、P1 一个端侧模型、一条真实云模型路径 |
| 主亮点 | 有限证据驱动重规划、规则化证据包 |
| 验证 | 一组受控故障、两类策略对照、最小第二插件 |
| 后续再做 | 本地小语言模型、在线阈值自适应、更多模型后端 |
| 本次不加 | 强化学习调度、任意模型自动迁移、多板集群、多智能体辩论、联邦学习、全品类购物 |

这不是因为后者没有价值，而是现阶段尚未接通实际执行闭环，新增这些模块会增加相互依赖和硬件验证负担。

## 7. 分阶段兑现计划

不依据未知的团队人数或截止时间给出固定工期。以可检验里程碑控制范围：

| 阶段 | 无板能做什么 | 完成证据 | 未完成时如何收敛 |
|---|---|---|---|
| 初选设计 | 两条典型任务图、证据包接口、状态变化、受控演示脚本 | 可读方案与清晰原型，标明未实现项 | 不编造性能与硬件成绩 |
| 桌面可行性 | 真 Runner、一个本地模型、一个云端服务、有限重规划 | 每个计划节点都有真实执行结果 | 优先删增强项，不增加新场景 |
| 获板验证 | 移植 P1 主控和一个官方适配模型，采集基准 | P1 进程、模型、SDK、日志与结果 | 模型受阻时更换官方可运行模型；检测先人工框选 |
| 亮点验证 | 规则分支、证据包和对照实验 | 质量／时延／请求量完整结果 | 无收益则报告适用范围，不宣称普遍更优 |
| 通用性验证 | 最小文件整理插件复用核心 | 无购物条件分支进入 Runtime | 第二插件保持小规模，无需完整 UI |

CPU 回退可帮助开发和验证，不能替代最终对 P1 指定加速路径的真实报告。若始终没有板端运行证据，则不能声称完成了 P1 落地。

## 8. 初选材料应回答的问题

- **谁需要它？** 在边缘设备上接入本地模型和云服务的应用开发者。
- **已有框架能做什么？** 编排、持久化、路由等基础能力已有实现；本项目可借鉴、复用，不以全部重造为创新。
- **本项目聚焦什么？** P1 上的任务证据检查、端云执行选择、受控数据出端及结果反馈的一体化验证。
- **为什么要 P1？** 实际承担主控、模型推理、本地结果与状态保存，并验证 NPU 工具和云模型协同；不宣称同类方案只能运行于 P1。
- **已有基础是什么？** 注册、调度评估、购物代码和控制台；真实执行闭环与板端适配是待完成项。
- **如何证明有效？** 相同任务和质量条件下，与固定混合流程对照；同时报告失败和退化。

没有确认官方初选评分权重，也无法保证评委判断或竞争结果。上述清单是申报建议，不是官方评分表。

## 9. 建议项目摘要

本项目面向 CIX P1 构建通用端云协同 Agent Runtime。系统在端侧完成本地模型推理与证据检查，围绕尚未满足的任务要求决定是否调用云模型，并构造经过数据政策检查的任务证据包；云端分析结果返回后，由端侧校验、调整后续执行并保存状态。项目以购物决策展示图像检索与复杂证据复核，通过受控故障、固定流程对照和第二插件验证调度效果、可靠性及业务解耦能力。项目重点验证在任务质量可接受的前提下，减少无效云调用与无关数据传输，而不预先承诺未经测量的性能收益。
