## 已实现的执行边界

- `ShoppingTaskService` 只注册远程正式搜索；`EntryAbility` 和首页移除了 `DataInitService`、商品 JSON 和索引预热。打包数据和本地引擎保留为 `offline_diagnostic`。正式启动禁用模拟设备状态注入。
- 公开 HTTPS 基址在 App「个人」页设置，保存在应用 Preferences；域名、COS 密钥和模型密钥均未写进业务代码。认证接入可向 `CloudApiConfig.setAccessToken()` 提供当前会话令牌，令牌仅驻留内存。
- `CloudShoppingExecutor` 按远程计划执行 readiness、提交、解析结果及客户端耗时回传。正式任务 `allowLocalFallback=false`。只允许健康探测重试；会产生 Session 的 POST 不自动重放，避免网络超时后的重复业务写入。
- 图片通过受限大小的 API 请求上传，由服务端写入 COS；手机不持有 COS 凭据。当前 App 图片上限 6 MiB，API JSON body limit 至少 10 MiB。
- 通用 `ExecutorRegistryService`、`RuntimeRunnerService` 按计划检查注册执行器、完整 assignment 和依赖顺序，然后执行。运行、成功、失败、超时、取消与未运行的后继节点均有状态；失败不会写成完成。活动运行不会被最近记录上限驱逐。
- 正式文字会话、结果读取、主体调整、画像修改、候选刷新及 debug 图片业务均经注册工作流执行器进入 Runtime。正式图片任务另有 12 个真实阶段：接收 → 资产上传/确认 → 图片尺寸质量检查 → 裁剪标准化/COS 存储 → 类别模型 → 商品画像模型 → 向量生成 → 云索引召回 → 数据库价格库存刷新 → 去重排序 → 回答和结果持久化 → 返回结果。
- 图片质量检查当前验证可解码和最小尺寸，不声称已实现独立的模糊度/遮挡质量模型。主体框支持调用方提供；未提供时标准化整图，不伪称自动主体检测。
- 图片业务复用现有存储、图片内容、模型、向量和候选适配器。候选价格明确来自持久化商品库或候选快照，不声称实时查询外部平台。
- `SessionsService` 的文字/刷新逻辑和 `SearchDebugService` 仍作为原子业务工作流执行器运行，不伪造其内部每一步的独立调度记录。正式图片路径才使用新分阶段图。

## 画像、观测与健康

每次 App 提交包含 taskId、任务模板与约束、设备快照、远程计划、输入引用以及 cloudRoutes。原始业务输入只提供给执行器；Runtime 图中只保存引用和经过白名单过滤的设备/网络字段。图禁止接受 URL 作为图片资产 ID。

未知带宽、费用、存储耗时、排队耗时在 App 中显式为 null，不编造网络测量。服务端图中的 co_located 路线为声明值，只描述服务内工作流传递；它不是一次 COS/模型调用的实测路径。首次执行使用明确的 cold-start 策略，且仍须健康探测成功；冷启动评分不是性能样本。真实性能样本只由 Runner 的真实完成/失败记录产生。提供费用/能源预算但没有可验证测量时，调度会明确阻断。

readiness 检查：真实商品表读取、专用 COS `_runtime/readiness.txt` 对象写入和签名读取、chat/vision 最小请求、实际使用的多模态 embedding 接口。探测有超时、并发合并以及成功 30 秒/失败 5 秒缓存。缺少配置或能力探测失败不能通过。探测会产生少量模型请求与专用 COS 对象写入；不触碰商品资产。

Runner 保存执行耗时、进程 RSS 快照以及分段指标。COS 写、图片存储读、图片模型阶段分别计时。客户端使用 NetworkKit 的发送进度和 `performanceTiming` 采集上传与下载耗时，无法观测时为 null，并通过关联 runId/taskId 回传，且不把客户端报告直接充当服务端性能样本。字段含义见 [OpenHarmony HTTP SDK](https://raw.githubusercontent.com/openharmony/interface_sdk-js/master/api/%40ohos.net.http.d.ts)。

取消为协作式：连接断开与 Runtime 取消会终止后续阶段，模型/COS/图片读取支持 AbortSignal。已经完成的 COS 对象写入或数据库事务不会被伪称为回滚；底层不可中断操作也可能在取消后结束，Runner 会忽略迟到结果。
