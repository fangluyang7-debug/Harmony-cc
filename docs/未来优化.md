# harmony-agent：当前版本暂不做的未来扩展

> 更新：2026-09-28。本文仅记录当前智能识物购物比赛项目可以不做的扩展，不是当前实施清单。
> 当前必须完成的契约、设备接入、数据传输、购物恢复和调度算法改造，全部见 [最终架构修改方案](最终架构修改方案.md)。

## 1. 划分原则

参赛项目是 `harmony-agent`；Cixin 是另一个项目，用户没有 Cixin 开发板。设备按能力解耦、可插拔，不以设备品牌或固定板卡为前提。

**当前要做**：以购物 App 为完整验证场景的 Task + Artifact、两级调度、控制/数据分离、链路测量、可插拔执行适配、容量准入、购物逻辑检查点及恢复选择、算法优化、幂等提交、观测与分阶段上线。不能因为某模块具有通用性，就把它整体推到未来。

**未来再做**：购物场景不需要的特殊恢复方式、其他 App 的业务插件、昂贵的全局求解器和大规模设备群运维。协议可预留版本化扩展点，本轮不要求实现以下能力。

## 2. 文件类任务的检查点

| 未来任务 | 需要扩展的状态 | 恢复与正确性难点 |
|---|---|---|
| 大文件分片上传/下载 | 文件版本、长度、分块大小、分片哈希、已确认区间、multipart upload ID、服务端提交回执 | 字节偏移必须匹配同一文件；不能把发送完毕等同于服务端已提交；授权过期需重新获取 |
| 视频转码、压缩、解压 | 编码器/格式版本、可恢复帧或块边界、字典状态、临时输出位置 | 任意字节偏移通常不足以恢复；编码上下文不兼容时从合法边界重算 |
| 大文档 OCR/解析 | 文档版本、页码/分区、页级结果、解析器和语言模型版本 | 页级提交与游标一致；跨页上下文可能要回读；失败页可独立重做 |
| 目录同步/备份 | manifest、相对路径、文件版本、权限、链接策略、删除记录 | 源文件执行中变化、路径冲突、多文件一致性、半成品清理 |
| 批量文件转换 | 工作清单、逐文件提交结果、错误集合、重试次数 | 一个失败文件不应导致全批重复；保留可追溯的成功和失败记录 |

后续设计应采用临时对象加提交屏障，完成校验后原子发布；校验文件版本、依赖、权限和磁盘预算，再比较传输快照、从输入重做、从已有分块恢复的完成成本。不是只给当前 `TaskCheckpoint.cursor` 换成 `byteOffset`。

当前图片上传的独立数据通道、哈希校验和取消仍属于当前实施范围；上述通用分片协议和任意文件处理引擎可以暂缓。

## 3. 大状态与设备专有检查点

### 3.1 增量和分层存储

未来对大规模向量索引、算法迭代状态、模型 KV cache 研究增量块、内容寻址和分层缓存。需要基准快照 ID、增量序号、依赖链、最大链长、定期合并和垃圾回收策略。目标缺少基准时必须计入补齐成本，不能假设增量一定更省。

### 3.2 GPU/NPU 或模型运行时快照

设备内存布局、runtime handle、驱动状态、KV cache 不能因标记 `portable=true` 就跨设备恢复。未来按模型哈希、量化格式、架构、后端、运行时/驱动版本验证兼容矩阵，失败时改用逻辑检查点或重算。

当前需实现逻辑检查点和恢复合法性框架；L1 大型算法状态、L2 设备专有快照的导出/导入插件暂不实现。不能为了通用化而阻塞购物链路。

## 4. 面向其他 App 的业务插件

| 应用方向 | 可复用当前能力 | 将来新增 |
|---|---|---|
| 音视频/会议助手 | TaskGraph、Artifact、分段遥测、取消、设备放置 | 时间窗、采样率、帧率、说话人、实时流检查点和背压 |
| 文档助理 | 图片/OCR 资源引用、检索、逻辑恢复 | 页码、版面、引用位置、文档权限和版本冲突 |
| 数据处理与批量导入 | 分批执行、索引快照、幂等提交 | 分区、水位、事件时间、schema 演化、跨分区一致性 |
| 端侧生成式模型 | 模型能力声明、资源准入、质量约束 | token 流、上下文预算、KV cache、量化/模型分片与专有恢复 |
| 带外部写入的 Agent | 生命周期、授权、租约、审计 | 工具副作用、人工确认节点、补偿流程、外部系统事务 |

当前 Artifact 基础信封保持通用，但这些字段放在各插件的版本化 payload schema，不堆进购物商品类型或 HAR 核心。

## 5. 算法与设备规模的长期研究

- 大规模多设备 DAG 联合分区、图切割或长时全局优化；当前先做有界 DAG 前瞻和实测成本启发式。
- MAPPO、强化学习、上下文 bandit、模型预测控制等学习策略；先积累数据并证明优于当前规则，保留硬约束和回退。
- 多租户公平性、跨组织配额、跨区域对象复制、联邦设备目录和云费用调度。
- 精确功耗/热动态模型；当前相对能耗评分不能写成实测焦耳或降温保证。
- 整机/跨应用资源治理、内核改造和硬实时系统；当前只做公开能力之上的应用级中间件。

手机、PC、云服务的基础可插拔协议和实际执行闭环属于当前方案；海量设备规模、任意 OS 支持和任意模型迁移才属于未来范围。

## 6. 平台和运维扩展

后续可以按真实需求加入更多系统运行时、真实 GPU/NPU、自托管多区域存储、设备插件签名/更新、跨协调器高可用、长期灾备和多租户管理。Cixin 如未来有设备与需求，也只能作为一个可选适配器，不享有主控或默认目标地位。

当前应做到单协调器的持久化提交记录、重启对账、权限隔离和有限期清理；跨地域灾备和控制器集群共识不列入本轮。

## 7. 项目文档可采用的展望表述

本项目以智能识物购物应用验证统一任务与数据契约、资源感知调度和分层执行机制。在此基础上，后续可通过扩展任务插件、Artifact schema 和恢复适配器，支持文件处理、音视频和生成式模型等工作负载；根据状态体积、依赖、兼容性和恢复成本选择迁移或重算。增量检查点、设备专有状态迁移和大规模联合调度属于后续研究，不作为当前已完成能力或性能承诺。

任何未来方向启动时，都需补充真实工作负载、兼容条件、质量标准、失败样例及独立基准，不能以购物场景成功直接推断任意 App 可用。
