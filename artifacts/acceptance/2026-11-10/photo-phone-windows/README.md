# 手机照片任务与 Windows 协作实测

日期：2026-11-10。分支 `codex/real-device-acceptance`，推送基线 `2b814c23832eaa032241a26f24cce5bc07b08579`，本轮修改尚未提交。证据：[evidence.json](evidence.json)，展示页截图：[judge-complete.png](judge-complete.png)。

## 输入与计时边界

- 用户没有照片，明确授权通过 USB 传文件。使用 Real-ESRGAN 发行包海滩样图的一块区域，显式准备 96×64 PNG，传入手机 Harmony 应用私有目录。准备文件的 Windows 临时副本在测试前删除；不能宣称照片从未经过 Windows。
- Windows 执行器使用隔离账本，任务开始前只有资格验证、端点与账本文件，没有任务照片或结果。模型和通用资格参考样本提前安装，允许；任务图块通过 SDK 在任务开始后传输，没有直接复制给执行器。
- 手机页面“导入 USB 测试照片”仅在私有目录存在固定调试文件时出现，不支持任意路径。它将文件放入正常待处理队列；点击开始前不派发。此入口不替代系统相册导入的验收。
- 两种模式均由手机发起，使用相同文件、Real-ESRGAN x4plus、4 倍放大和 180 秒预算。规范化输入 SHA-256：`6fbe0feb8405a3964ca19248555649386131fb8ad77c9f2bbfd86750e132cf1d`。输出 384×256。
- `LOCAL` 是仅手机执行计算的联网调度基线，不是完全离线的原生单机应用。端到端时间包括提交、规划、传输、计算、回传和来源端校验。
- 业务连接实际观察到手机 WLAN `172.20.10.3` → Windows WLAN `172.20.10.2:7443`，HDC fport 为空。USB 用于安装、操作与输入准备，没有业务端口转发。
- 手机贡献 CPU 2 槽、内存 1 GiB；Windows CPU 4 槽、内存 2 GiB。Windows 无 NVIDIA GPU，本轮未使用鸿蒙电脑。

## 结果

| 顺序 | 模式 | 端到端 | 执行结果 |
|---|---|---:|---|
| 1 | 手机计算 | 26.251 秒 | 7/7 节点提交 |
| 2 | 手机 + Windows | 23.038 秒 | 7/7 节点提交 |
| 3 | 手机计算复测 | 20.587 秒 | 7/7 节点提交 |
| 4 | 手机 + Windows 复测 | 24.880 秒 | 7/7 节点提交 |

第一组协作耗时下降约 12.2%，第二组反而增加约 20.9%。样本很小、系统负载和热状态未严格受控，**尚未证明稳定协作加速**。不挑选较快的一轮作为最终性能结论。

单机两轮的七个节点全部在手机。协作两轮均由手机执行分析，Windows 执行两组准备/增强、合成和交付；不是手机和电脑同时执行增强分片。位置来自规划器真实选择，没有固定设备指派。若验收要求双端增强分片重叠，本轮未满足该项。

四轮每轮恰好七个唯一 attempt、七份已提交回执，无重复节点计算；成品完整交付。Windows 节点有本轮 `TRANSFER_RECV` 和 `EXECUTE` 追踪，不以旧结果代替执行。相同设备重复输出像素完全一致；Windows 与手机结果仅有 30/294912 个颜色通道相差 1（8 位通道），最大差值 1，平均绝对差约 0.000102。输出 PNG 字节哈希不同，不声称跨平台逐字节相同。

首次单机两个增强节点的实际 EXECUTE 为 2385 / 1696 ms；首次协作为 Windows 4414 / 2877 ms。当前 Windows CPU 后端在这个样本上并未比手机推理更快。端到端还包含阶段依赖与控制交付等待，不能把整轮差异全归因于推理速度。

## 本轮修复

1. 鸿蒙照片原生库缺少 OpenMP 依赖：HAR/HAP 构建按 ABI 打包 SDK 的 `libomp.so`；原生模块未加载时不崩溃、不公布不可用能力。
2. 新手机控制台身份复用旧浏览器 App 时发生 `APP_POLICY_CONFLICT`：在确认能力更新的提交路径兼容旧授权，保留 App 与历史身份，不另开派发入口。
3. 旧 SoleAI 宿主画像过期导致同一手机全部共享池过期：已绑定且有持久预留的过期宿主，不参与实时容量采样，整份预留继续扣除；无预留或无确认预算仍按未知处理，不凭过期记录释放资源。
4. 鸿蒙 CPU 总容量错误使用当前 App 配额：改用配对时声明上限，仍明确标记 `PRIOR`，当前 App 贡献和准入配额独立保留，不冒充硬件实测核心数。

构建：协调器 TypeScript 通过；API 24 HAR 和签名 HAP 构建、手机覆盖安装通过。完整 workspace build 曾在运行中 Prisma DLL 被占用而失败，随后只运行 TypeScript 编译；未修改数据库 schema，不把此次完整 build 报为通过。App/照片控制台回归 6 项、directory/profile projection 14 项通过；最终容量保护调整后 directory 6 项再次通过。

失败记录仍保留：`fa91abd8...` 为 APP_POLICY_CONFLICT；`c25de1ab...` 和 `e7073354...` 为 NO_LEGAL_PLAN。均未执行节点，不计入成功性能对照。

## 复现与接续

当前中心从仓库编译产物启动：`node scripts/start-coordinator-lan.cjs 172.20.10.2 7443 .test/real-device-20261109-wifi/coordinator`。手机与 Windows 必须仍在可互访 Wi-Fi，保持手机 Harmony 前台。当前安装包位于 `.test/photo-api24-harmony-agent/entry/build/default/outputs/default/entry-default-signed.hap`，本机签名配置不入库。

手机操作：调度盘 → AI 照片工作台 → 导入 USB 测试照片（一次）→ 只用发起设备计算 → 开始处理；完成后保留同一队列，选择自动规划协作，再开始。不要重复导入而意外增加图片数量。大屏打开同一空间的 `photo.html?space=<空间ID>&view=judge`，可看到原图、逐图交付、实际设备分工及结束后的统计；原调度盘入口保留。

下一步应测试更大且真实有用的照片，按输入尺寸/图块面积和执行目标修正成本估计，并分析逐阶段控制开销。当前参考校准只使用小样本，初始预测明显低于实耗，需校准后再决定分工；不得靠给手机降配、提前缓存任务素材、强制无用分片或选择性展示来制造加速。NVIDIA 设备、鸿蒙电脑、双端增强分片重叠及更大照片的内存/温控表现仍待验收。
