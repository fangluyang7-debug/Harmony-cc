# 三设备无线局域网多类型任务测试

> 后续修复已完成，最终同输入、同 30 秒预算连续两轮 48/48 通过，详见 [修复复测报告](FIX-REPORT.md)。下文保留修复前的原始结果与当时结论。

日期：2026-11-07；分支：`codex/real-device-acceptance`。使用当前已安装的 API 24 真机应用、Windows CPU 代理、REAL 局域网协调者与正式 SchedulerSdk。未更换生产调度规则或放宽任务预算。

结论：两台鸿蒙设备的业务连接经无线局域网到达 Windows 协调者。文本统计、向量归一化、图片裁剪三类任务均取得真实结果；三台同时各处理一类任务通过。**修正测试预期后的复测为 21/24 通过，仍有 3 项 Windows 定向提交被拒绝，因此本轮整体不是全通过。**

## 1. 无线连接证据

| 设备 | 业务 IPv4 | 接口与路由 |
| --- | --- | --- |
| Windows（协调者兼 CPU 代理） | 192.168.71.37 | WLAN；到 .39/.40 的路由为 WLAN、192.168.71.0/24、直连 |
| 鸿蒙电脑 | 192.168.71.39 | wlan0；192.168.71.0/24 路由使用 wlan0 |
| 鸿蒙手机 | 192.168.71.40 | wlan0；192.168.71.0/24 路由使用 wlan0 |

- Windows 物理以太网为 Disconnected。两台鸿蒙读取到的 IPv4 接口只有 lo 和 wlan0。
- Windows 7443 控制连接及 7444 数据连接观察到的远端为 .39/.40；首轮另保存了 103 份连接采样，覆盖其中约 180 秒，不代表覆盖整轮所有时刻。
- HDC 转发列表为空。USB 保留用于安装、状态读取与调试，本轮没有通过 HDC 转发业务端口。
- 证据为 `network-before.json`、`network-after.json`、`network-retest-after.json`、`connections-during.json`。接口累计字节数含其他流量，不能用作任务专属带宽。

这证明已观察到的跨设备业务路径使用 Wi-Fi；**没有进行物理拔掉 USB 后的独立复验**。Windows 上协调者到本机代理的任务属于本机通信。原生设备可经 Windows 中继，不将此结果描述为任意两台均已建立直接数据通道。

## 2. 用例与校验

脚本：`scripts/test-wireless-multitask.cjs`。每轮 24 项：6 个用例各固定到 3 台设备，共 18 项；三种类型各自动选址 1 项；最后三台并发各处理一种类型，共 3 项。

| 类型 | 输入与处理 | 独立校验 |
| --- | --- | --- |
| 文本统计 | 中文、英文、emoji、CRLF；另有 400 行文本 | Unicode 码点字符数、空白分词数、换行数完全相等 |
| 向量归一化 | 4 行含零向量、负数、1e200 数值；另有 4096 行四维向量 | 行数、维度、范数与分量；分量绝对误差 ≤ 1e-10 |
| 图片裁剪 | 合成四色图两个选区，输出 96×96 / 192×192 JPEG | 格式、尺寸与颜色；至少 98% 像素各 RGB 分量误差 ≤ 10 |

正式 SDK 完成输入登记、任务提交、传输和取回输出；SDK 校验输出摘要。任务预算保持 30000 ms。测试端最多等待输出 45 秒，再等待最终状态最多 10 秒；这两个客户端等待期限不会增加执行预算。记录任务、目标、traceId、输入/输出 SHA-256、实际输出与错误，未用模拟结果填充页面。

复现命令（私有会话和证书使用本地文件，不提交账号或 Cookie）：

```powershell
node scripts/test-wireless-multitask.cjs https://192.168.71.37:7443 .test/real-device-20261107/session.json .test/real-device-20261107/coordinator/coordinator-public.crt <新的结果目录>
```

开始前要求当前空间恰有三台在线设备。该脚本本身不证明无线接口，须同时检查路由、业务连接及 HDC 转发状态。

## 3. 两轮结果，失败不抹除

**首轮 14/24 通过。** 原始 `RESULTS.json`、`initial-test-script.cjs` 与 `crop-input.png` 保留：

- Windows 的 4096 行向量提交返回 `NO_LEGAL_PLAN`。
- 8 项图片输出已生成，但颜色断言失败。原因是测试使用 1024×768 长方形图片，却假定只截取矩形选区；产品约定先将选区扩为正方形，独立预期不正确。这些首轮断言失败不改记为通过。
- 鸿蒙电脑的一项小向量已返回输出，但同次响应的状态仍是 `ACCEPTED`，即时断言失败。测试端随后改为等待最终状态；生产 SDK/服务端的状态快照一致性问题未在本轮修改。

**复测 21/24 通过。** `retest/RESULTS.json` 保存全部记录，图片输入改为 1024×1024，使两选区为正方形、颜色预期与产品约定一致。4096 行向量输入保持不变，没有降低规模规避拒绝。

| 模式 / 设备 | 文本两项 | 向量两项 | 图片两项 | 合计 |
| --- | --- | --- | --- | --- |
| 固定 Windows | 2/2 | 1/2 | 0/2 | 3/6 |
| 固定鸿蒙电脑 | 2/2 | 2/2 | 2/2 | 6/6 |
| 固定鸿蒙手机 | 2/2 | 2/2 | 2/2 | 6/6 |
| 自动选址（每类一项） | 1/1 | 1/1 | 1/1 | 3/3 |
| 三设备并发（每类一项） | 1/1 | 1/1 | 1/1 | 3/3 |

复测自动选择：文本 → Windows（4.01 秒），向量 → 手机（3.95 秒），图片 → Windows（3.21 秒）。因此 Windows 图片能力可以执行，定向拒绝存在时变因素，不能解释为 Windows 不支持图片能力。

并发组：Windows 文本 6.75 秒、鸿蒙电脑向量 6.48 秒、手机图片 7.57 秒；整批从开始提交到全部校验结束为 **7.58 秒**。这是一组不同任务的并发提交，不是把单个任务自动拆成三份；也没有对应的同工作量单机对照，不能报告加速比。

所有耗时均为测试客户端从登记输入、提交、处理、下载到观察最终状态的墙钟耗时，**不是 Wi-Fi 纯传输时延或纯计算耗时**。复测成功任务范围约 3.20–24.36 秒，波动仍明显。

## 4. 回执与尚待修复的问题

持久化审计 `RECEIPT-AUDIT.json`：首轮 23 项实际执行、复测 21 项实际执行；共 44 项均为 `SUCCEEDED`，每项一条 committed 回执且 `resourcesSettled=true`。4 次被拒绝的提交没有创建执行记录。这里确认的是协调者账本和回执唯一性，不单凭此宣称已完成设备级重复执行故障验收。首轮执行成功不等同于首轮独立输出断言通过。

复测失败均为 Windows 定向提交：

| 用例 | 请求 ID | 错误 |
| --- | --- | --- |
| vector-1 | 479d4e94-212b-4d50-8696-158b3e5fca6d | NO_LEGAL_PLAN |
| crop-0 | 4d01503f-493d-4cc1-b8d5-f0ed9d7f343c | NO_LEGAL_PLAN |
| crop-1 | be870bc7-eb6e-44e2-9965-bc4c64305352 | NO_LEGAL_PLAN |

只读规划诊断见 `PLANNER-DIAGNOSTIC.json`：读取测试后当前持久化快照，在该快照采集时刻重放规划，不重新执行任务、也不修改生产设置。当前快照中图片被拒绝的细分原因为 `DATA_UNREACHABLE_OR_BUDGET`；在纯诊断中使用假想的大预算后可规划，估计约 59.62 秒，超过正常 30 秒。大向量在更新后的快照中估计约 24.37 秒，已可规划。

当前估算把大向量输出按 3,357,184 字节、裁剪输出按上限 8,388,608 字节定价，并结合波动的链路速率样本。这为“输出大小上界与链路估价使预算判断过于保守”提供线索。**上述秒数都是规划估计，不是测量值；也不是失败当时的原始快照，不能据此断言已唯一定位根因。** 下一步应保留失败现场的候选拒绝细节，检查输出大小估计和链路采样口径，再以同一输入、相同预算回归。

另需使服务端状态、committed 回执与输出可读状态保持一致，避免 SDK 在输出已到时仍返回旧 `ACCEPTED` 状态。当前测试等待最终状态仅处理验收观测，不算产品缺口已经修复。

收尾 `FINAL-DEVICE-STATE.json` 显示三台在线，三种能力均可用。本轮未重启代理、未改动 Railway、未修改生产预算。现有 `NO_SPEEDUP` 性能结论保持不变。
