# Windows 间歇性规划拒绝与状态一致性修复复测

2026-11-07，`codex/real-device-acceptance`。最终版本连续两轮各 **24/24 通过，共 48/48**。此前的 Windows 大向量、图片定向拒绝，以及输出已返回但状态为 ACCEPTED 的情况，在这两轮中均未出现。

## 修复内容

1. **链路估价回退**：当探测耗时被启动开销或抖动主导、线性拟合斜率非正时，旧算法将最慢小探测的整段耗时作为每字节成本，大输入/输出会被过度放大。改为以最大实测载荷的有效速率作为回退依据，再用固定项覆盖所有样本残差。保留真实慢链路的高成本；没有伪造带宽、缩减输出大小上界、放宽预算或跳过规划。Node 调度核心与鸿蒙 `NativeAgent.probeLinks` 同步修改。
2. **状态一致性**：`CpuJobs.status` 用一条带参数的 SELECT 联查任务、执行状态、回执和队列，在数据库同一语句快照中生成响应。避免跨时刻读取造成输出 ticket 与旧状态混合，也避免为高频轮询持有多次异步往返的交互事务。原有身份范围、已收到结果后的 ticket 回收保持生效。
3. **结果确认闭环**：补齐空间 SDK 的 `POST /v2/spaces/:spaceId/sdk/jobs/:jobId/received`，调用已有 `SdkJobs.received`。此前 SDK 的确认请求落入 404、被尽力确认逻辑吞掉，服务端 `resultReceivedAt` 不更新。新接口验证身份和输出后记录确认、沿用制品回收逻辑；回归覆盖重复确认和其他成员访问。
4. **可诊断性**：空间接口遇到未预期数据库异常时仅记录 Prisma 错误码，不输出查询参数或凭据；测试脚本记录失败路由和 HTTP 状态。验收脚本不再等待第二次最终状态来掩盖第一次输出响应的状态滞后。

关键文件：`packages/scheduler-core/src/cost.ts`、`apps/harmony/scheduler/src/main/ets/v2/host/NativeAgent.ets`、`services/coordinator/src/cpu-jobs.ts`、`services/coordinator/src/spaces.ts`。

## 中间失败与边界

初次修复版本 `fixed-round1` 为 **23/24**：所有定向与自动任务成功，但并发 Windows 文本发生 REQUEST_FAILED，尚未建立执行记录。当时通用异常未留下底层错误码，不能断言唯一原因；其余 23 项也因缺少 received 路由而没有服务端接收确认。这一轮保留，不并入最终 48/48 的通过统计。

随后将状态读取从交互事务改为单语句快照、补齐 received 路由和错误码诊断；最终两轮未再出现通用请求失败。期间手机自动锁屏，系统拒绝启动，待用户解锁并恢复三端能力后才开始最终两轮，没有把锁屏期间计入正常协同结果。

本次证明这组设备、无线环境和所列输入上的修复结果，不能承诺任意网络、长期高负载或所有型号均无拒绝。真正链路变慢或预算不足时，规划器仍应拒绝；以后若复发，使用新诊断核对具体错误码和规划成本，不扩大预算掩盖失败。此前首轮与复测的原始失败记录均保留。
