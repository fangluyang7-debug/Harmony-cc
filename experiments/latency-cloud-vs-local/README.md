# 云端与本地协调时延对照实验

本目录只用于实验，分支 `codex/latency-cloud-vs-local`。基于 `2b6159e`，不改变正式协调器、代理、前端、Railway 配置，不向开发分支合并实验代码。

## 复现

需 Node.js 22+、已安装的项目依赖、OpenSSL。先按现有项目步骤构建：

```powershell
npm --workspace @harmony/coordinator run build
npm --workspace @harmony/pc-agent run build
node experiments/latency-cloud-vs-local/run.cjs https://harmony-space-production.up.railway.app
```

脚本启动独立本地 HTTPS 协调器，在本地和指定云端各创建一个私有实验空间、一个 1 CPU 槽位/256 MiB 贡献上限的临时代理。结束后关闭代理、本地协调器，撤销设备凭据并退出会话。云端实验账号和空间记录会保留，不使用已有用户空间。原始数据、数据库与临时凭据仅保存在 Git 忽略的 `.test/latency-*`；请勿整体提交该目录。

正常结束会输出 `results.json`。测试期间勿手动暂停实验代理或关闭进程；异常终止时应撤销对应实验设备凭据。结果中的 `cleanup` 记录是否已正常清理。

## 测量方法

- 两组使用相同代码基线、任务、CPU 设备和贡献限制，域均为 REAL。云端协调服务使用当前线上部署；本地协调服务独立进程运行在同一台电脑。
- 本地 TLS 使用证书信任校验，云端使用公网 TLS 校验，均未禁用验证。
- 先完成配对与自动能力检查，单独记录初始化耗时；每类任务各预热一次，预热结果保存但不纳入正式分位数。
- 三轮分块顺序：本地→云端，云端→本地，本地→云端。单个任务串行执行；不是并发吞吐压测。
- 每组共 15 次新 TLS 连接、60 次 HTTPS 连接复用请求、30 次真实仪表盘查询、60 次实际控制连接上的 WebSocket ping/pong、每类 15 次 CPU 任务、3 次暂停共享。
- 场景：21 字节小文本输入；约 256 KiB 文本输入；4096×8 向量输入约 72 KiB、输出约 704 KiB。所有任务均校验实际结果。
- `ms`：客户端完整读取响应/收到 pong 的往返耗时；ping/pong 是传输基准，不等于执行指令完成时间，也不据此推断单向时延。
- `dispatchMs`：开始提交到同机代理收到实际 DispatchOffer，含输入提交、服务端选择和指令传输。不是纯调度算法耗时。
- `e2eMs`：开始提交到完整读取并解析结果。每次查询完成后等 100 ms 再查询，因此含结果观察延迟；不是当前网页 2.5 秒刷新节奏。
- `readinessWaitMs`：测量前等待仪表盘显示目标能力 ACTIVE 且可用的时间，含至少一次状态读取；另列 `includingReadinessMs`，不隐藏连续提交后的可用状态等待。
- `authorizeMs` / `readMs` / `publishMs`：代理已有端口调用的本地计时，包括内部串行请求与工件传输，不能解释为单次 RTT。
- `engineWallMs` 包含子进程启动、IPC、解析及计算；`algorithmMs` 为既有子进程报告的计算段。计时使用本机单调时钟，不相减云端与设备的墙上时间。
- `appliedMs`：暂停修改开始到代理实际观测为暂停；没有进行正在运行长任务的抢占时延测试。
- 分位数使用 nearest-rank。15 个样本的 P95 就是最大值；暂停仅 3 个样本，只可作探索性观察。

实验通过运行时包装已有代理回调/端口读取时间，不改生产源码。正式测试必须保留失败样本和清理结果，不仅报告成功均值。

## 解释边界

本地回环是当前硬件和实现下的理想传输基准，不能冒充多设备 Wi-Fi/局域网结果。当前环境没有第二台设备，尚不能确定决赛局域网 P95、热点拥塞、调度设备掉线和切换恢复效果。两个代理与基准客户端共享一台电脑；后台系统负载未固定，云端硬件与本地硬件也不同。这是当前方案的实际路径比较，不能把全部差值归因于网络。

新 TLS 连接仍可能使用系统 DNS 缓存；没有测试冷 DNS、冷启动服务器或平台唤醒。任务体积、单设备 CPU 功能、单次网络环境均有限，不能推广为 GPU 推理、视频流、手机、跨城市多设备或长期 SLA。

当前产品每 2.5 秒查询空间快照，代理每 2 秒采样，任务路径存在多次串行网络往返与工件经协调中心转发。最终报告将把这些实现开销与基础网络往返分开。

部署区可用带 `X-Railway-Debug: true` 的请求检查 `X-Railway-Upstream-Zone`。边缘入口与实际部署区不同，参见 [Railway Edge Networking](https://docs.railway.com/networking/edge-networking)。修改带卷服务的部署区涉及卷迁移，参见 [Railway Regions](https://docs.railway.com/deployments/regions)；本实验不迁移、不重部署正式服务。
